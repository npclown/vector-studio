## 1. Scope

### 1.1 In scope

One new playground page that renders a scene mixing P1 primitives (rectangles, ellipses, lines) and P3 paths (fill and stroke) through the real `geometry-wasm` fill-mesh and stroke-mesh ports, in a defined paint order, and three scripted checks on it:

1. **Ordered integration.** Pixel probes in overlap regions show the color that the authoritative depth-first order predicts, for opaque overlaps and for half-opacity overlaps where the two orders give different colors. Reordering, hiding and a container change the probes as predicted.
2. **Upload and resource lifetime under scene churn.** A deterministic script adds, replaces and removes path and primitive nodes for N cycles. The published diagnostics (`WebGpuBackend.getStatistics()`, `PrimitiveRendererService.getPathMeshStatistics()` and `getPreparationStatistics()`) show no growth after a warm-up: live GPU resources and bytes, CPU mesh-cache entries and bytes, failure memo entries, kernel linear memory and pipeline counts stay at their steady values, and disposal returns live GPU resources to zero.
3. **Latest-scene device recovery.** The page destroys the GPU device through `WebGpuBackend.destroyDeviceForTesting()` (published, section 2). After recovery the latest accepted scene re-renders identically to a no-loss render of the same scene, with no new port call for unchanged paths, the lifecycle diagnostics in order, and the same live resource accounting as before the loss. This is checked on a static scene, with edits accepted while the device is lost, and in the middle of the churn script.

The page is UI and a test hook over the existing draw. It adds no draw work, no kernel work and no renderer code. It composes `createFillMeshPort`, `createStrokeMeshPort`, `PrimitiveRendererService` and `WebGpuBackend` as the V-1 page does (`apps/playground/src/viz-v1-appearance.ts`).

**What the published surface does not show, and why V-3 does not add it.** The mesh arena's range occupancy, the path-slot maps and the per-packet mesh writes are not published. The packet format is internal to `renderer-core` and `renderer-webgpu` and is explicitly not shared ([D9 boundary](d9-post-mvp1-tracks-proposal.md#boundary)), so V-3's page and its GPU spec do not read packets, even though a platform wrapper could intercept them as the P1 fixture does. The one exception is the informational Node test VZ3-A19, which reads the packets' mesh-part resource descriptors (capacity and incarnation) to count growths and repacks; it gates nothing. Instead V-3 infers range and slot leaks from arena growth (section 3.4). Packet capacities in `renderer-core` only grow, in powers of two from a minimum of 16 elements: for the P1 arena, `capacityFor` and the `Math.max` capacity rule in `primitive-scene-source.ts`; for the mesh arena, `#replaceArena` (`path-mesh-packet.ts`, lines 629-637: a region grows to `capacityFor(used)` only when its use exceeds its capacity, and `meshInstances` to `capacityFor(slotDemand)`) and `capacityFor` (lines 866-876). Growth replaces the GPU buffer with a larger one, so a sustained leak shows as a rise in the end-of-cycle `resources.liveBytes`.

**Repacking is not growth.** When no free range fits but the free totals would, the mesh packer also replaces the arena without growing it: it repacks every resident variant contiguously, with new incarnations (`path-mesh-packet.ts`, lines 545-551 and 619-642), and the backend then creates a new GPU arena of the same capacities (`native-primitive-scene.ts`, lines 789-903). That raises `byCategory.buffer.created` and, while the old arena waits for its last submitted use, possibly `peakLiveBytes`, with no leak. So V-3 gates only the end-of-cycle `live`, `liveBytes` and `byCategory[*].live` equalities and records `created` and `peakLiveBytes` without gating them (VZ3-A8). The informational Node test VZ3-A19 drives the CPU pipeline headless and counts growths and repacks after warm-up from the packets' mesh-part resource descriptors (capacity and incarnation). Its fallback reads `repacks` and `arenaReplacements` from `PathMeshPacker.getStatistics()`, which tests may import from the source module, as `tests/unit/v3b-mesh-packet.test.ts` does. A direct occupancy query would be a `renderer-core` or `renderer-webgpu` public-surface change: full tier, reviewed by both tracks and split out as a rendering-track item under the [D9 conflict rule](d9-post-mvp1-tracks-proposal.md#operations). The least invasive route is to not add it and to state the detection bound ([VZ3-Q3](#7-open-questions)).

The page's `window.__vectorStudioVizV3Integration` test hook is page-local, like the V-1 hook. It is not a shared surface.

### 3.4 Churn script

The script is deterministic and lives in the scene module. Recommended parameters ([VZ3-Q6](#7-open-questions) (a)): N = 64 cycles after the order states, warm-up W = 4 cycles. Geometry A is B2 `fill-stroke-square` with its fill and stroke; geometry B is V4 `star-nonzero`, fill only. Cycle c (1 to N) runs three change sets, each with the next revision and each followed by a settle:

1. **Add.** Insert path `ch-p-<c>` with geometry A when c is even and B when c is odd, and ellipse `ch-e-<c>` overlapping it, with fresh ids. The `orders` entry places the path above the ellipse when c is odd and below it when c is even, so ordered insertion alternates.
2. **Replace.** Update `ch-persist`'s `verbs` and `points` to the B2 `fill-stroke-circle` path (fill only) when c is odd and to `star-nonzero` when c is even. This is a geometry change, so the old fill entry becomes unreachable and the new key calls the fill port once.
3. **Remove.** Remove `ch-p-<c−1>` and `ch-e-<c−1>` (nothing in cycle 1).

The cycle has period 2, so values are compared between cycles of the same parity.

**Samples.** After each change set's settle, the hook records a sample: `backend.getStatistics()`, `service.getPathMeshStatistics()`, `service.getPreparationStatistics()` and `getSynchronizationState()`. The end-of-cycle sample is the one after step 3.

**Predicted port-call deltas per cycle**, from the renderer rules (per-node cache entries, a removed node's entries and slots released, a key change rebuilding exactly that node and paint; [V3 sections b and d](p3-v3-renderer-mesh-pipeline-contract.md#d-mesh-cache-failure-memo-and-their-bounds), [stroke contract 9.3](p3-b2-stroke-contract.md#93-cache-keys-memo-and-reuse)): fill `portCalls` +2 in every cycle (add and replace), `strokePortCalls` +1 in even cycles (geometry A has a stroke) and +0 in odd cycles, and +0 for every remove step. VZ3-A10 gates these values ([section 4.1](#41-expected-literal-rule)).

**Leak detection bound, per arena region.** After warm-up, a range or slot leak makes the retained demand of some arena region grow every cycle. Each region r is bounded separately: the P1 arena's primitive slots (`transforms`, `geometry`, `styles`) and order slots, each mesh geometry region (`meshPositions`, `meshTriangles`, `meshFeatureLists`, `meshFeatures`), and `meshInstances` (path slots). For region r, let D_peak be its peak demand within a cycle (both transient pairs present, after step 1), D_end its end-of-cycle demand, and C its capacity. Capacities are powers of two of at least 16 elements, so C ≤ max(16, 2 · D_peak), and growth is forced at the latest once the leaked total exceeds the headroom H = C − D_end ≤ max(16, 2 · D_peak) − D_end. This is conservative: the in-cycle peak forces growth earlier. Growth raises the end-of-cycle `liveBytes`, which VZ3-A8 gates.

- **Slot regions** (primitive slots, order slots, `meshInstances`). A slot leak is at least one whole slot per cycle. Expected counts, which VZ3-A2 computes exactly from the scene data and records:
  - **Primitive slots:** 7 in the order zone (`bg`, `r-band`, `l-line`, `e-dot`, `r-under`, `r-half`, `r-jbase`) plus the churn ellipses: 2 at the in-cycle peak (`ch-e-<c>` and `ch-e-<c−1>`) and 1 at the end of a cycle. So D_peak = 9, D_end = 8, C = 16 (the minimum dominates; d / D ≈ 1/8) and H ≤ 16 − 8 = 8.
  - **Path slots** (`meshInstances`; a path with fill and stroke has two): 8 in the order zone (`p-square` 2, `p-circle`, `p-star`, `p-half`, `p-solid` 1 each, `p-joint` 2), `ch-persist` 1, and the transient churn paths, which are 3 at the in-cycle peak (one of geometry A with 2 slots and one of B with 1) and 2 or 1 at the end of a cycle, by parity. So D_peak = 12 (13 if `p-joint`'s overlay variant holds its own instance record; VZ3-A2 states which, from the slot rule of V3 section f and its ST-U6 and ST-U7 amendments), D_end = 10 or 11 (or one more), C = 16 and H ≤ 16 − 10 = 6.
  - **Order slots** follow the visible order stream and are bounded the same way; VZ3-A2 records them.

  Any sustained slot leak therefore forces growth within 8 cycles, well inside the 60 measured cycles.

- **Mesh geometry regions.** Leaks here are element counts. Write d for the churn demand per cycle in the region and suppose d = D_peak / 4, so D_end = 3 · D_peak / 4 and H ≤ 2 · D_peak − D_end = 5 · D_peak / 4 = 5 · d. A leak of a fraction f of d per cycle exceeds H within 5 / f cycles, so N − W = 60 measured cycles detect a sustained leak of at least about f = 1/12 of the per-cycle churn demand. A smaller fraction, a leak that stops, or a region where d / D_peak is below 1/4 gives a weaker bound in proportion.

The mesh element counts come from the kernel, so a unit test without the kernel cannot compute them, and the published statistics do not show them. They are **recorded, not gated**, by the Node test VZ3-A19 (the real CPU pipeline with real ports, no GPU), which reports D_peak, D_end and d per region at the DPR 1 and DPR 2 tolerance exponents, the resulting bound per region, and the repacks after warm-up. The CPU cache (`entries`, `bytes`, `memoEntries`) is checked exactly, so a mesh-entry leak of any size is detected there.

### 3.5 Recovery scenarios

Each loss is induced with `destroyDeviceForTesting()` from the hook. Recovery is complete when `lifecycle` is `ready`, `generation` is the old one plus 1, `framesPresented` has increased since the loss, and the page has settled.

| R1       | At S5, capture the surface and statistics; destroy the device; wait for recovery; capture again                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | The pre-loss capture of the same revision                              |

**The loss window.** The backend sets `lifecycle` to `lost` only inside its asynchronous loss handler (`webgpu-backend.ts`, lines 771-772), so a change applied right after `destroyDeviceForTesting()` returns still lands while the state is `ready`, and its frame can be submitted to the destroyed device. The state is `lost` when `device-loss.detected` is emitted. V-3 therefore defines the loss window from the diagnostic sequence: it opens at `device-loss.detected` for the destroyed generation and closes at `recovery.succeeded` for the next one. R2's X and R3's steps 2 and 3 are applied inside the window; the hook records, for each, the index of the diagnostic after which it was applied and the `lifecycle` at that moment. Every loss is induced only after a settle, with `pendingFrameCallbacks` 0, and no change is applied between `destroyDeviceForTesting()` and `device-loss.detected`, so no frame of the page's own edits is submitted to the destroyed device. `staleGenerationSubmissions` is cumulative (`webgpu-backend.ts`, lines 1141-1148), so it is gated as a delta across each window and its value is recorded.

R2's edit X contains exactly one new key (the `p-solid` geometry change), so the recovered frame makes one fill port call and no stroke port call. The inverse of X, applied before the loss, removes the inserted rectangle and restores the old `p-solid` geometry, whose key then calls the port once more. These deltas are part of VZ3-A12. R2 follows the P1.5 precedent ("an accepted edit during loss appears in the reconstructed generation-2 packet") and V3 section i ("the first recoverable frame uses the latest accepted scene").

A run has two losses in the order zone (R1, R2) and one in the churn zone (R3), so it also checks that a second and third recovery behave as the first.

**Oracle and probe rule.** Expected probe colors come from an independent painter's-order oracle in the spec: it walks the scene snapshot's depth-first order, tests each probe point for membership in each visible node's shape, and blends the node colors source-over with node opacity, as P1's encoded-sRGB premultiplied blend does. It does not import page or renderer code. Membership:

- rectangles and ellipses analytically, and lines by their distance to the segment against half the width;
- path fills by the fill rule's winding number of the point against the path flattened by the oracle's own code: each cubic is subdivided at t = 1/2 until both inner control points lie within ε = 0.05 CSS px of the chord segment (the distance to the segment, not to its line), so the curve, which lies in the convex hull of its control points, lies within ε of the flattened polyline; lines are taken as they are;
- path strokes (only on line-only paths in this scene) by the distance to the segments against half the width, with butt caps and miter joins as the source cell defines them;
- a path with both paints at node opacity o is composed as one layer: stroke over fill, then times o, then source-over the destination, the D2 group-opacity rule that the ST-U7 joint draw implements.

**Probe rule** (V-1's 2 px rule plus ε). A boundary counts only where the oracle's color changes across it, in a state the probe is compared in. Each probe lies at least 2 CSS px plus ε from every such boundary, measured on the flattened polyline, so flattening cannot move a probe across one. A probe in a band (a stroke-over-fill band or a stroke-only band) sits at the band's centre line. The width-10 strokes of `p-square` and `p-joint` split into two 5 px bands, inner over the fill and outer over the destination, so a band-centre probe is 2.5 px from each band edge, which meets the rule and would not meet a 3 px rule. The scene keeps the source cells' widths and scale, because a scale transform would change the tolerance exponent and break the translation-only rule of section 3.2. Where a check separates two candidate colors, the spec first checks that they differ by more than twice the tolerance.

**Identity rule.** "Identical" means the decoded RGBA bytes of the whole surface screenshot are equal, byte for byte, and every probe's observed color is equal, with tolerance 0 ([VZ3-Q5](#7-open-questions) (a)).

## 6. Risks

- **A07 is not yet executable acceptance.** The P3 table reserves A07 until C03-C05 freeze fixtures, tolerances and commands. V-3's evidence may need re-running, or its fixture reshaping, once C04 fixes the final transport and lifetime lanes. VZ3-Q9 (a) keeps the X1 row honest by marking it partial.
- **Leak detection is bounded, not exact, on the GPU side.** Without an occupancy query (section 2), a mesh-region leak smaller than about 1/12 of the per-cycle churn demand (at d = D_peak / 4), or one that stops after a few cycles, does not force arena growth within 60 cycles; slot leaks are whole slots and are caught within 8 cycles. The CPU side is exact. The mesh-region d / D_peak depends on kernel output and is recorded by VZ3-A19, not gated; a lower ratio weakens the bound in proportion.
- **Repacks without growth.** A fragmentation repack replaces the mesh arena at the same capacities, raising `buffer.created` and possibly `peakLiveBytes`. They are recorded, not gated (VZ3-A8), so a repack cannot fail the run and cannot hide a leak, which shows in the end-of-cycle `liveBytes` instead.
- **Edits between `destroy()` and detection.** The backend sets `lost` only in its asynchronous loss handler, so an edit applied between `destroyDeviceForTesting()` and `device-loss.detected` can be prepared and submitted to the destroyed device, risking `render.submission-failed` and a rise in the cumulative `staleGenerationSubmissions`. V-3 makes the ordering deterministic: losses are induced only from a settled page, the script pauses until detection, in-window edits run from the diagnostics listener, and the counter is gated as a delta per window (section 3.5).
- **Allocator padding and size-dependent attachments.** `liveBytes` includes the canvas and MSAA targets, which depend on DPR; the comparisons are within one run at one DPR, so this is not a confound. A resize during a run would be, and the spec does not resize.
- **Screenshot identity across a recovery.** The identity rule assumes the same device, driver and commands give the same bytes, and that the element screenshot path is deterministic. If a run shows a non-identical surface with identical probes, the run is FAIL and the cause is investigated (for example a compositor difference); the rule is not weakened. Texture readback (VZ3-Q5 (b)) is the fallback, by a contract amendment.
- **Timing of R2.** X must be accepted inside the loss window. Applying it right after `destroyDeviceForTesting()` returns, as the P1 fixture's `recoverWithEdit` does, would land while the state is still `ready`. The hook therefore applies X from its listener on `device-loss.detected`, and the spec records the diagnostic index and the lifecycle at that moment; a run where X lands outside the window is FAIL, not PASS.
- **A lost-generation readback.** A screenshot taken while the old generation's frame is in flight could capture a stale frame. The spec captures only after recovery completes and the page settles, and checks the generation in the hook's snapshot before and after the capture.
- **Kernel-outcome coupling.** The predictions of section 4.1 depend on the current fill and stroke revisions and caps. A rendering-track change that alters them updates this spec in the same PR.
- **Host-injection tests are shared files.** The two unit-test edits change `tests/` files both tracks rely on. They are named in the Gate line under D9-Q8 (a), and each keeps its deny-list.
- **Run time.** The churn test runs 192 change sets with a settle each, per browser and DPR. It has its own timeout and is one test per combination, so a failure does not hide the other combinations.
- **Precision stays UNVERIFIED.** The probes are functional and far from edges.
- **No CI for GPU evidence.** The weekly D9 checkpoint and the per-PR headed run are the only GPU gates.
