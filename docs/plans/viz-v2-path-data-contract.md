## 1. Scope

### 1.1 In scope

An interactive playground page with a text area that takes the `d` attribute data of one SVG path. On an explicit Apply (section 3.3), the page parses the text with the grammar of section 1.2, maps the result to one scene path node (`verbs` and `points` of `ScenePathGeometry` in `packages/contracts/src/scene.ts`) and renders it through the existing ports, with a minimal subset of the V-1 appearance controls (section 3.2).

- **Grammar.** SVG 2 path data restricted to M/m, L/l, H/h, V/v, C/c, S/s, Q/q, T/t and Z/z (section 1.2). Arcs (A/a) are rejected with a clear message (recommended, [V2-Q2](#7-open-questions)).
- **Errors.** A parse error is reported with its code, offset, line and column (section 1.4). Parsing produces no partial application: on any error the scene is unchanged and the last applied path stays drawn.
- **Limits.** Input length, scene verb count and coordinate magnitude (section 1.5).
- **Coordinates.** The parsed coordinates are used raw as node-local units under an identity node transform, and the camera is fitted to the path (recommended, [V2-Q5](#7-open-questions)) automatically after an Apply that changes the path, and on a Fit button (section 3.4).

The page is UI over the existing fill-plus-stroke draw. It adds no draw work, no kernel work and no renderer code. It composes `createFillMeshPort`, `createStrokeMeshPort`, `PrimitiveRendererService` and `WebGpuBackend` exactly as the V-1 page does (`apps/playground/src/viz-v1-appearance.ts`).

### 1.2 Grammar

The grammar is the SVG 2 path data grammar (SVG 2, section 9.3.9 "The grammar for path data"), restricted to the commands below, with the number syntax of SVG 1.1 (section 8.3.9), because the SVG 2 BNF writes `number ::= ([0-9])+`, which does not admit fractions or exponents and is not what any implementation accepts. It is strict: there is no browser-lenient extension ([V2-Q7](#7-open-questions)).

```text
path          ::= wsp* ( moveto ( wsp* command )* )? wsp*
command       ::= moveto | closepath | lineto | hlineto | vlineto
                | curveto | smooth-curveto | quad | smooth-quad
moveto        ::= ( "M" | "m" ) wsp* pair-seq
closepath     ::= "Z" | "z"
lineto        ::= ( "L" | "l" ) wsp* pair-seq
hlineto       ::= ( "H" | "h" ) wsp* coord-seq
vlineto       ::= ( "V" | "v" ) wsp* coord-seq
curveto       ::= ( "C" | "c" ) wsp* triple-seq
smooth-curveto::= ( "S" | "s" ) wsp* double-seq
quad          ::= ( "Q" | "q" ) wsp* double-seq
smooth-quad   ::= ( "T" | "t" ) wsp* pair-seq
coord-seq     ::= number ( comma-wsp? number )*
pair-seq      ::= pair ( comma-wsp? pair )*
double-seq    ::= pair comma-wsp? pair ( comma-wsp? pair comma-wsp? pair )*
triple-seq    ::= pair comma-wsp? pair comma-wsp? pair
                  ( comma-wsp? pair comma-wsp? pair comma-wsp? pair )*
pair          ::= number comma-wsp? number
comma-wsp     ::= ( wsp+ ","? wsp* ) | ( "," wsp* )
wsp           ::= U+0009 | U+0020 | U+000A | U+000C | U+000D
number        ::= sign? ( digits "." digits? | "." digits | digits ) exponent?
exponent      ::= ( "e" | "E" ) sign? digits
sign          ::= "+" | "-"
digits        ::= [0-9]+
```

Rules that follow from it, each covered by a row of the V2-A3 grammar table:

- **Whitespace** is exactly the five characters above. No other character, including U+00A0, any non-ASCII character and a second comma, is accepted.
- **Commas.** At most one comma separates two numbers. A comma is not allowed after a command letter, before a command letter, after the last number, before the first number or after `Z`. The command letters are the 20 SVG path command letters `M m Z z L l H h V v C c S s Q q T t A a`. A comma that follows a complete argument group must be followed, after optional whitespace, by the first character of a number (a digit, `.`, `+` or `-`), which starts the next group of an implicit repeat. Anything else after such a comma is `unexpected-character` at the comma: a command letter, `A` and `a` included (`M 10 10, L 1 1`, `M 10 10, A`), any other character (`M 10 10, X`), a second comma (`M 10 10, ,`, at the first comma) or the end of the input (`M 10 10,`). A comma inside an incomplete group (`M 10, L`) is allowed, and the missing number is `expected-number` (section 1.4).
- **Numbers.** A number token is the longest match of `number` from its first character. So `1-2` is 1 and −2, `0.5.5` is 0.5 and 0.5, `1e-2` is 0.01, `5.` and `.5` are numbers, `+.5` is 0.5, and leading zeros are allowed. An `e` or `E` directly after a mantissa commits the token to an exponent: if no digit follows the `e` and its optional sign (`1e`, `1e+`), the token is `invalid-number` at the `e`. Any other token that starts like a number but does not match (`-`, `.`, `+.`) is `invalid-number` at its first character (section 1.4). Digits are ASCII only.
- **Conversion** is `Number(token)` on the matched token, so each value is the binary64 value ECMAScript defines. For tokens of at most 20 significant digits that is the correctly rounded value; fixtures use at most 17. A token whose value is not finite (`1e400`) is `coordinate-out-of-range`. Underflow to zero or to a subnormal is accepted.
- **Signed zero.** Every emitted point coordinate is normalized after all of its arithmetic (conversion, the relative sum, reflection or degree elevation of section 1.3): a coordinate equal to zero is stored as +0 (`v === 0 ? 0 : v`). The rule changes no nonzero value. No emitted coordinate is ever −0, so `Object.is` comparisons, `String(n)` serialization and a JSON round trip all preserve the stored values. The current point is the emitted point.
- **First command.** The first non-whitespace character must be `M` or `m`; otherwise `missing-moveto`, which also covers a first `A` or `a`. A first `m` is absolute (SVG 2): the current point starts at (0, 0), so the sum equals the argument, and an argument of −0 is stored as +0 by the signed-zero rule.
- **Implicit repeats.** Extra pairs after `M` are implicit `L`, and after `m` implicit `l`. Every other command with arguments repeats itself for each further argument group. `Z` takes no arguments, so a number after `Z` is `unexpected-character`.
- **Empty input.** Input that is empty or only whitespace is valid and maps to zero verbs and zero points, as in SVG, where an empty `d` renders nothing. The renderer treats a path with no verbs as not drawable ([V3 section b](p3-v3-renderer-mesh-pipeline-contract.md#b-port-consumption-geometry-revision-and-cache-key)).
- **Case** decides absolute (upper case) or relative (lower case) coordinates.

`A` and `a` are not in the grammar. With [V2-Q2](#7-open-questions) (a), either letter, where a command is expected (after a complete argument group or after `Z`), is reported as `unsupported-command` at its offset with the message "Arc commands (A/a) are not supported on this page. Convert arcs to curves first.", and the arguments are not read. Where a number is required, `A` and `a` count as command letters like any other, so `M 10 A` is `expected-number` at the `A`.

### 1.3 Mapping to the scene path

The parser keeps a current point `p` and a subpath start `s`, both (0, 0) initially. Relative arguments are added to `p` in binary64, one rounding per coordinate (`p.x + dx`). Each segment of an implicit repeat is relative to `p` at its own start. Every point in the table is absolute after that step.

| Command                                 | Verbs and points emitted                                                                                                                                                                                                                                                     | Afterwards                                         |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `M` (x, y)                              | `move` (x, y)                                                                                                                                                                                                                                                                | `p = s = (x, y)`                                   |
| `L` (x, y)                              | `line` (x, y)                                                                                                                                                                                                                                                                | `p = (x, y)`                                       |
| `H` x                                   | `line` (x, p.y)                                                                                                                                                                                                                                                              | `p = (x, p.y)`                                     |
| `V` y                                   | `line` (p.x, y)                                                                                                                                                                                                                                                              | `p = (p.x, y)`                                     |
| `C` c1, c2, e                           | `cubic` c1, c2, e                                                                                                                                                                                                                                                            | `p = e`                                            |
| `S` c2, e                               | `cubic` r, c2, e, where r is the reflection of the previous segment's second control point about `p` if the previous command was C, c, S or s, and `p` otherwise                                                                                                             | `p = e`                                            |
| `Q` q, e                                | `cubic` c1, c2, e by degree elevation (below)                                                                                                                                                                                                                                | `p = e`; the quadratic control `q` is kept for `T` |
| `T` e                                   | as `Q` with q the reflection of the previous quadratic control point about `p` if the previous command was Q, q, T or t, and `p` otherwise                                                                                                                                   | `p = e`; that `q` is kept                          |
| `Z`                                     | `close`                                                                                                                                                                                                                                                                      | `p = s`                                            |
| any command after `Z` other than M or m | first an implicit `move` to `s`, because the scene grammar needs a `move` after `close` (`hasPathGrammar`, `packages/renderer-core/src/scene-validation.ts`), then the command's own verbs. This is SVG's rule that such a command starts a new subpath at the current point | as for that command                                |

**Reflection** of a point c about p is computed per coordinate as `2 * p - c` in binary64 (the product is exact, so one rounding).

**Degree elevation.** The quadratic p0, q, p2 becomes the cubic with `c1 = (p0 + 2 * q) / 3` and `c2 = (p2 + 2 * q) / 3`, per coordinate, in binary64. In real arithmetic this cubic equals the quadratic exactly. In binary64 it is **not exact in general**: `2 * q` is exact, but the sum and the division by 3 each round, so each control coordinate differs from the real value `(p0 + 2q) / 3` by at most `(|p0| + 2|q|) / 3 · (2u + u²)`, with `u = 2^-53`. Under the coordinate limit of section 1.5 (`|v| ≤ 2^24`, so `(|p0| + 2|q|) / 3 ≤ 2^24`) that is at most about `2^-28` local units (`2^24 · (2u + u²)`). The signed-zero rule then applies to the result. The conversion is exact when the sum is exact and divisible by 3 in binary64, for example p0 = (0, 0), q = (3, 3), p2 = (6, 0), which gives c1 = (2, 2) and c2 = (4, 2). The deviation is a rounding of a control point, not a flattening error; precision stays UNVERIFIED (section 4).

**Faithful mapping.** The mapping simplifies nothing. A `T` or `S` with no previous curve gives a cubic whose first control point is computed by the formula above, not a `line`. Consecutive `M` commands give MOVE-only subpaths, and `Z Z` gives `close`, `move` (to `s`), `close`.

**`Z Z`: a deliberate difference from browsers.** Browsers (Skia) collapse a repeated close into one close. V-2 follows the SVG 2 text instead: the second `Z` closes a new, empty subpath that starts at `s`, so it maps to `move`, `close`. The consequence is a MOVE-only subpath. In a path that also has a cubic, the v0 fill kernel reports that as `unsupported-geometry`, so `M 0 0 C ... Z Z` draws no fill on this page where a browser would draw it. The V2-A3 row for `Z Z` pins this mapping, and the notice shows the consequence.

The kernel's handling of such input is the kernel's: for example, a MOVE-only subpath in a path with a cubic is `unsupported-geometry` for the fill in v0 ([V2 section e](p3-v2-fill-mesh-transport-contract.md#e-status-mapping-and-precedence)), and the page shows that notice and does not avoid it.

The result always satisfies the scene grammar and the point-count rule, and every point is finite, so scene validation accepts the geometry. The node is:

- `id: 'v2-path'`, `parentId: 'world'`, `transform: [1, 0, 0, 1, 0, 0]`, `visible: true`;
- `geometry: { kind: 'path', verbs, points, fillRule }`, with `fillRule` from the appearance state;
- `style` and `opacity` from the appearance state of section 3.2.

The scene is one container `world` at identity and this one path node. There is no backdrop node; the probes of section 4 use the surface's clear color.

### 1.4 Errors

Parsing stops at the first error ([V2-Q7](#7-open-questions)). The result is either `{ status: 'ok', verbs, points }` or `{ status: 'error', code, offset, line, column, message }`, never both, and an error result carries no verbs or points.

- `offset` is the 0-based index in UTF-16 code units. `line` and `column` are 1-based. LF, CR LF and a lone CR each end one line; `column` counts UTF-16 code units from the line start. A character outside the Basic Multilingual Plane is reported at its first code unit.
- A `<textarea>` normalizes CR LF and a lone CR to LF in its value, so the page only ever parses LF line ends. The CR LF and lone-CR rows are unit-only parser rows, and no GPU criterion depends on CR.
- `message` is fixed text per code, followed by the offending character or token where one exists.

| Code                      | When                                                                                                                                                                                                                                                           | Offset                                                                              |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `input-too-long`          | The text is longer than the input limit of section 1.5; checked before any parsing                                                                                                                                                                             | The first code unit past the limit                                                  |
| `missing-moveto`          | The first non-whitespace character is not `M` or `m`                                                                                                                                                                                                           | That character                                                                      |
| `unsupported-command`     | `A` or `a` where a command is expected (after a complete argument group or after `Z`)                                                                                                                                                                          | The letter                                                                          |
| `unexpected-character`    | Any other character not allowed where it stands: an unknown letter, a misplaced comma (including a comma after a complete group that is not followed by the start of a number, section 1.2; reported at that comma), a number after `Z`, a non-ASCII character | That character                                                                      |
| `expected-number`         | An argument group is incomplete: the input ends, or a command letter (A and a included) arrives, where a number is required                                                                                                                                    | Where the number was expected (after any skipped whitespace and comma)              |
| `invalid-number`          | A token starts like a number but does not match `number`                                                                                                                                                                                                       | The `e` or `E` when an exponent has no digit; otherwise the token's first character |
| `coordinate-out-of-range` | A converted token is not finite, or a computed absolute point (endpoint, control point, reflected point or elevated control point) is not finite or exceeds the coordinate limit                                                                               | The first character of the argument group that produced it                          |
| `too-many-verbs`          | The mapped verbs, implicit moves included, would exceed the verb limit of section 1.5                                                                                                                                                                          | The first character of the argument group, or the command, that would exceed it     |

The page shows the error as text: the code, "line L, column C", the message and a one-line excerpt with a caret under the offset. It also sets `aria-invalid="true"` on the text area, links the message with `aria-describedby`, moves focus to the text area and places the caret at the offset (`setSelectionRange(offset, offset)`).

**Deliberate difference from SVG.** SVG 2 renders a path up to its first error. V-2 renders nothing new on an error and keeps the last applied path, because a partial path would look like a successful parse.

### 1.5 Limits

Recommended values ([V2-Q6](#7-open-questions) (a)):

| Limit                | Value                                                 | Why                                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Input length         | 65,536 UTF-16 code units                              | Bounds parse time and the text kept in the page; checked before parsing                                                                                                                                                                                                                                                                                                                                          |
| Scene verbs per path | 4,096                                                 | Above the current kernel source caps (fill: 72 source verbs, 4 contours, 64 source segments, [B1 kernel caps](p3-fill-stroke-meshes.md#b1-kernel-caps); stroke: 1,024 source verbs, 512 segments, 256 subpaths, [stroke contract 7.6](p3-b2-stroke-contract.md#76-limits)), so the kernel's `work-limit` is reachable and shown, and far below P2's 65,536 output verbs. It bounds the mirror and port copy cost |
| Coordinate magnitude | `abs(v) ≤ 2^24` = 16,777,216 for every absolute point | Keeps the stroke bounds box finite for every width the page allows, so scene validation cannot return `invalid-value` for it ([stroke contract 5](p3-b2-stroke-contract.md#5-scene-field-and-validation)), and keeps world positions far from the binary32 range the mesh packing needs (`packing-range`, [V3 section h](p3-v3-renderer-mesh-pipeline-contract.md#h-d8-interim-failure-outcome))                 |

**Current fill caps, confirmed in review round 1** (`packages/geometry-wasm/kernel/src/cubic_fill.rs` on `origin/main`): `MAX_CONTOURS = 4` (line 22, unchanged by B1); `MAX_SOURCE_SEGMENTS = 64` (line 23); 72 source verbs (`MAX_SOURCE_SEGMENTS + 2 · MAX_CONTOURS`); `MAX_EDGE_OWNERS = 256` edge owners; and 264 flat commands (`MAX_EDGE_OWNERS + 2 · MAX_CONTOURS`). The segment, edge-owner, verb and flat-command values are B1's and have not changed since. The first three caps are on the source path and do not depend on zoom. The edge-owner and flat-command caps count flattened edges, and flattening uses the tolerance `2^e` of the zoom bucket (`tolerances`, `packages/geometry-wasm/kernel/src/fill_export.rs` line 104). So the same curved path can mesh at one zoom and give `work-limit` at a higher one.

These are page limits, not kernel limits. The page does not reject a path for exceeding a kernel cap: the kernel does that with `work-limit`, and the page shows the notice. The kernel caps are internals that the rendering track may change (B1 did), so the page does not copy them.

## 2. Shared surface

**V-2 needs no change to the shared surface.** It changes no `packages/contracts` export, no public factory or constructor of `geometry-wasm`, `renderer-core` or `renderer-webgpu`, and no operation identity. It edits no file under `packages/`. It uses the same published exports as V-1 ([V-1 contract, section 2](viz-v1-path-appearance-contract.md#2-shared-surface)), including `applyChanges` with an updated path node.

**Where the parser lives.** The parser and the mapping are page code in `apps/playground/src/viz-v2-path-data-parse.ts` (recommended, [V2-Q3](#7-open-questions) (a)). The other homes are worse for now:

- `packages/contracts` is jointly owned, and every change to it is full tier and reviewed by both tracks ([D9, shared and unassigned paths](d9-post-mvp1-tracks-proposal.md#shared-and-unassigned-paths)). A parser there would also be the first runtime code in a types-and-ports package.
- `packages/geometry-reference` is a rendering-track package that the visualization track does not edit ([D9, visualization track](d9-post-mvp1-tracks-proposal.md#visualization-track)); a parser there would be split out under the [D9 conflict rule](d9-post-mvp1-tracks-proposal.md#operations), and path text parsing is not reference geometry.
- A new package needs an `ARCHITECTURE.md` decision and a boundary-policy entry.

Each of the three is a shared-surface or ownership change, and this contract recommends against all of them. When P5 needs SVG interchange, the editor's import adapter can adopt or replace this parser under its own decision.

**Degree elevation in binary64** is page code too (section 1.3). It is not exact in floating point in general, and the contract says so rather than claiming exactness. It adds no geometry operation and no tolerance to the kernel's budget.

**The independent parser oracle** lives in the unit test (`tests/unit/viz-v2-path-data-parse.test.ts`), or in a new `tests/support/` file that only V-2's tests import. It must not import the parser module or share code with it:

- The parser is a character scanner. The oracle tokenizes with sticky regular expressions over the whole input and expands commands from a table, so a shared misreading of the grammar is less likely.
- The grammar table of V2-A3 is the primary oracle. Its expected `verbs` and `points` are literals written by hand, not computed by either implementation.
- The oracle also serializes a mapped path to canonical absolute `M`, `L`, `C`, `Z` text with `String(n)`, for the round-trip check of V2-A5. `String(n)` round-trips every finite binary64 value except −0, which it writes as `0`. The signed-zero rule of section 1.2 stores no −0, so the round trip is exact.

**Reuse of V-1 code.** V-2 may import V-1's target-agnostic exports read-only (for example `parseNotice`, `noticeMeaning`, `NOTICE_CODE`, `parseBoundedNumber` and the commit-rule helpers `CONTROL_KINDS` and `appliesOn`) and must not edit any V-1 file (recommended, [V2-Q9](#7-open-questions) (a)). V-1's `AppearanceEditor` and `TargetStatusTracker` are bound to V-1's target list, so V-2 has its own editor and status bookkeeping in `viz-v2-path-data-state.ts`.

The page's `window.__vectorStudioVizV2PathData` test hook is page-local, like the V-1 hook. It is not a shared surface.

## 3. Page design

### 3.1 Which page and which files

A **new page**, `apps/playground/viz-v2-path-data.html`, with:

- one `rollupOptions.input` entry in `apps/playground/vite.config.mjs`;
- two shared test edits, named under [D9-Q8 (a)](d9-post-mvp1-tracks-proposal.md#user-decisions-2026-10-22). The host-injection unit tests allow exactly three real-port hosts today: `tests/unit/v3a-path-pipeline.test.ts` (the test "V4: only the path page, the ST-U8 stroke page and the V-1 appearance page inject the real ports") and `tests/unit/v3b-mesh-backend.test.ts` (the "V4 host injection" test, `toHaveLength(5)`). Each gains `src/viz-v2-path-data.ts` as a **fourth host**, on the V-1 pattern. In `v3a`, the new host is checked to import `@vector-studio/geometry-wasm` and to inject `fillMesh: fill,` and `strokeMesh: strokes,`. In `v3b`, the host count becomes 6 (four pages and the two manifest edges). Both deny-lists stay in force for every other file, so `viz-v2-path-data.html`, `-parse.ts` and `-state.ts` must not contain `fillMesh`, `strokeMesh`, `geometry-wasm`, `requiresMeshPipeline` or `meshPipeline`, comments included.

The V-1, ST-U8 and V4 pages stay unchanged.

### 3.3 Edit flow and the commit rule

1. **Path text.** Typing, pasting and `input` events change the text area only. The page parses only when the user activates Apply, by pointer or by keyboard (Enter or Space on the focused button). It never parses on a keystroke, on `input` or on blur (recommended, [V2-Q4](#7-open-questions) (a)). While the text differs from the last applied text, the page shows "Edited, not applied".
2. **Apply.** The page parses the whole text into a fresh result:
   - on an error, nothing in the page state or the scene changes; the error is shown (section 1.4);
   - on success, if the parsed `verbs` and `points` equal the applied ones element by element under `===` (the mirror's replay rule, `pathDataEquals`), the page sends no change and shows "Unchanged". The mirror would keep the geometry revision, so no mesh is rebuilt either way;
   - otherwise the parsed data replaces the applied geometry, and one scene change is sent (step 4), followed by the fit of section 3.4 before the next frame.
3. **Appearance controls** follow V-1's commit rule ([V-1 section 3.3](viz-v1-path-appearance-contract.md#33-edit-flow)): radios and checkboxes apply live; the width number field applies on commit (`change`, Enter or blur). Applied edits are coalesced to at most one scene change per animation frame.
4. **The change** is V-1's one-node change: the full `v2-path` node, `revision = current + 1`, `baseRevision = current`, `updated: [node]` and empty `inserted`, `removed` and `orders`.
5. **Result handling** is V-1's ([V-1 section 3.3](viz-v1-path-appearance-contract.md#33-edit-flow), step 6): `applied` advances the revision; `resync-required` leads to one `replaceSnapshot` of the whole current state at `result.current.revision + 1` (or `current + 1` when `result.current` is null); `invalid-scene` reverts the geometry and appearance to the last applied state and lists the reason as an error (sections 1.3 and 1.5 make it unreachable, so it signals a defect); `disposed` stops edits; a failing `replaceSnapshot` disables the controls until reload with no retry.

**Cache invalidation.** A new path gives the node a new geometry revision ([V3 section b](p3-v3-renderer-mesh-pipeline-contract.md#b-port-consumption-geometry-revision-and-cache-key)), so the fill entry and the stroke entry both miss, are rebuilt on the next `prepare`, and re-notify on failure. Appearance edits follow the paint keys exactly as on V-1 ([V-1 section 3.3](viz-v1-path-appearance-contract.md#33-edit-flow)).

**Stall rule.** A port call runs synchronously in `prepare`, and a failing path can be expensive (section 6). The commit rule bounds the cost to one rebuild per Apply and one per committed width or key edit, never one per keystroke.

### 3.4 Camera and fit

The node transform is identity, so path coordinates are world coordinates, with y down as in SVG. The **fit rule**, computed in `viz-v2-path-data-state.ts`:

The steps run in this order, each in binary64, so that the GPU spec can compute the same camera independently and compare it exactly (V2-A13):

1. `minX`, `maxX`, `minY`, `maxY` are the minimum and maximum of the x values (even indices) and the y values (odd indices) of `points`, control points included. The control points bound the curve. If `points` is empty, all four are 0.
2. `h = stroke.width / 2` when the stroke is on with width above 0; otherwise `h = 0`.
3. `cx = (minX + maxX) / 2` and `cy = (minY + maxY) / 2`.
4. `hx = (maxX - minX) / 2 + h` and `hy = (maxY - minY) / 2 + h`. The half stroke width is added after the half extent. Miter tips may extend past it.
5. For each axis with a nonzero extent, the quotient is clamped at once: `zx = hx > 0 ? Math.min(Math.max(336 / hx, 2^-20), 2^20) : Infinity`, and `zy = hy > 0 ? Math.min(Math.max(276 / hy, 2^-20), 2^20) : Infinity`. Here 336 and 276 are the half sizes of the 720 x 600 CSS px surface less a 24 CSS px margin. A subnormal positive `hx` makes `336 / hx` overflow to Infinity, and the clamp turns it into `2^20`. So `zx` is Infinity only when `hx` is exactly 0. `hx` and `hy` are finite and non-negative under the limits of section 1.5.
6. `zoom = Math.min(zx, zy)`; if `zoom === Infinity`, which happens only when both `hx` and `hy` are exactly 0, then `zoom = 1`. Every other value already lies in `[2^-20, 2^20]`.
7. The camera is `{ position: { x: cx - 360 / zoom, y: cy - 300 / zoom }, zoom }`. The renderer's camera position is the world point at the surface's top-left corner, so the box center is at the surface center.

The fit runs after every Apply that changes the geometry and on the Fit button. An appearance edit, including a width edit, does not refit. Pan and zoom work as on the V-1 page (drag, wheel, zoom buttons) within `[2^-20, 2^20]`.

### 3.5 Notices and the derived status

The notice log, the notice meaning and the counts are V-1's ([V-1 section 3.4](viz-v1-path-appearance-contract.md#34-notices)) for the one node `v2-path`: every notice listed newest first with node id, paint, failure code and tolerance exponent; never cleared by an Apply, an edit or a fit; the newest 400 kept, older ones counted as "N older notices dropped from this list"; the hook keeps all; `noticesQueued` and `noticesDropped` shown.

The derived status follows V-1's amended rules ([V-1 amendment 2026-10-22](viz-v1-path-appearance-contract.md#amendment-2026-10-22-user-approved-34-per-exponent-display)):

- One record per paint, shown only while its paint is on (the stroke only with width above 0), holding the most recent notice for the current key. Per-exponent records are kept and exposed only through the test hook (`snapshot().targetStatus`).
- **V-2's key adds the geometry.** The fill key is (geometry generation, fill rule); the stroke key is (geometry generation, width, cap, join, miter limit). The page's geometry generation increases on every Apply that changes the geometry (section 3.3, step 2), because a new geometry revision rebuilds both paints and re-notifies. An Apply reported "Unchanged" keeps the generation and the records.
- The label "derived from notices; the notice log is authoritative" is always shown. After a zoom change, the status adds "may differ; the notice log is authoritative". The fit that follows an Apply is part of that Apply and does not set this label, because the new geometry is first built at the fitted zoom; the Fit button, wheel and zoom buttons set it, and the next geometry-changing Apply clears it.
- State failures are shown as "may have cleared" until the next zoom-bucket or port change, as on V-1.
- `overlay-unsupported` cannot arise, because opacity is fixed at 1.

A parse error is not a notice. It is shown in its own error region (section 1.4) and changes neither the log nor the status.

The UNVERIFIED precision label is shown on the page and written into every evidence directory, with V-1's text adapted to V-2.

### 3.6 Accessibility basics

- The text area, Apply and Fit are in a `<fieldset>` "Path data" with a `<legend>`; the appearance controls in `<fieldset>` groups "Fill" and "Stroke". Every control has a visible `<label>`.
- Everything works by keyboard with no custom key handling. Tab moves out of the text area (no Tab capture). Apply and Fit are native buttons.
- Focus is visible on every control (`:focus-visible` outline).
- A parse error sets `aria-invalid="true"` on the text area and links the error text with `aria-describedby`. The error region is `role="alert"`, so the error is announced once per Apply.
- The status region is `aria-live="polite"`. The notice log is not live.
- The canvas has an `aria-label`. The applied path's verb count, point count and bounding box are printed as text, so the state does not depend on reading the canvas.

## 6. Risks

- **Many real-world paths exceed the current fill caps (not measured).** The fill kernel admits at most 4 contours, 72 source verbs and 64 source segments per path (section 1.5; [B1 kernel caps](p3-fill-stroke-meshes.md#b1-kernel-caps)). Many icon paths have more subpaths than that, so a pasted icon may give `fill work-limit` and draw nothing. The share is not measured. Two caps also depend on zoom: 256 edge owners and 264 flat commands count flattened edges, whose number grows as the bucket's tolerance `2^e` shrinks (section 1.5). The automatic fit makes this worse for small icons: a 24-unit viewBox icon is zoomed about 23 times (`552 / 24`), which raises the leaf count of every curve. All of this is current kernel behavior, shown as a notice, not a page defect. The page states the caps in its help text with a link to the plan, and a recurring case is filed as a rendering-track item with the path as a fixture.
- **Rejecting arcs excludes much exported SVG.** Many tools emit `A` commands for circles, rounded corners and icons. With V2-Q2 (a), such a path is rejected at the first arc until the user converts arcs to curves elsewhere.
- **Main-thread stalls.** Port calls run synchronously in `prepare`. Failing crossing chord strokes of 16 or more segments spend 0.15 to 0.8 s natively before `work-limit` ([ST-U3b probe](p3-fill-stroke-meshes.md#b2-st-u3b-scaling-probe)), roughly 1.3 s in WASM by the AL-S2 factor (an estimate for that class only). A user can paste such a path. The commit rule of section 3.3 bounds this to one rebuild per Apply or committed edit; V2-A15 records the time; the rendering track's E1 early abort ([rendering track](d9-rendering-track.md#status-index)) is the remedy. A stall is filed there with the path as a fixture. The commit rule does not cover the camera: a failure is memoized per tolerance exponent, so a wheel or zoom-button change that crosses into a new bucket calls the port again for the new `e` and pays the failure cost again on an expensive failing path. Returning to an earlier bucket is a memo hit and is not repaid. A user who zooms across many buckets on such a path pays once per bucket; V2-A15 records only the Apply timings.
- **Kernel-outcome coupling.** The V2-A11 literal and the default path's literal depend on the fill and stroke revisions and on the caps. A cap raise can turn W1 into a success, and the rule of section 4.1 then replaces W1 in the PR that raises the cap.
- **Degree elevation is not exact in binary64.** Section 1.3 bounds the deviation; it is far below any served tolerance under the coordinate limit, but a review must not read the conversion as exact.
- **Reflection and relative sums round.** Long relative chains accumulate binary64 rounding, as every SVG implementation does. The oracle reproduces the same order of operations, so V2-A5 checks the defined arithmetic, not real-number geometry.
- **Strictness.** A path copied from a tool that emits browser-tolerated but non-grammatical text (for example a trailing comma) is rejected. The error names the position, so the user can fix it.
- **Derived status can be stale,** for the reasons V-1 lists ([V-1 section 6](viz-v1-path-appearance-contract.md#6-risks)). The log is authoritative and the spec loads a fresh page per scenario.
- **Scope drift towards import.** A file picker, `<svg>` parsing or `viewBox` handling would cross into the deferred "Import/export" item. Section 1.6 excludes them; the review checks the diff against it.
- **Host-injection tests are shared files.** The two unit-test edits of section 3.1 change `tests/` files both tracks rely on. They are named in the Gate line under D9-Q8 (a), and each keeps its deny-list for every other file.
- **Reuse of V-1 exports.** A later V-1 change to an imported helper changes V-2. V2-A17 keeps V-1 unchanged in this PR, and `pnpm check` runs V-2's unit tests on every later V-1 change.
- **Precision stays UNVERIFIED.** The probes are functional and far from edges.
- **No CI for GPU evidence.** The weekly D9 checkpoint and the per-PR headed run are the only GPU gates.
