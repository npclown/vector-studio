It is full tier: it fixes how the P3 exit criteria A01-A08 are evidenced, and its four questions decide what the exit gate requires. It changes no threshold and no tolerance. ## 1. Why this item exists

The [P3 private contract](p3-private-contract.md) owns C03-C05 and has been `PARTIAL` since 2026-09-29. The [P3 checkpoint table](p3-fill-stroke-meshes.md) defines them:

| ID  | Definition (quoted)                                                                                                                    |
| --- | -------------------------------------------------------------------------------------------------------------------------------------- |
| C03 | Exact private fill/stroke numeric semantics, combined error budget, work limits and error precedence fixed with deterministic fixtures |
| C04 | Mesh ABI/version/layout, ownership, cache keys and stale/dispose behavior fixed without reinterpreting P2 v1                           |
| C05 | Independent oracle, positive controls, corpus, commands and evidence rules fixed before corresponding implementation                   |

They were written for a single prospective freeze before implementation. [D8](p3-d8-parallel-tracks.md) then changed the order: a functional transport and renderer were built under the [C04 carve-out](p3-private-contract.md#private-transport-and-lifetime-requirements), and A04 became a measurement on a frozen corpus. Each later unit froze its own fixtures, limits, oracles and commands, but nothing closed C03-C05. Two rules now block the exit:

- The P3 acceptance table: A01-A08 "are not executable acceptance until C03-C05 supply exact fixtures, tolerances and commands".
- The carve-out: "acceptance evidence counts only after C03-C05 are complete, on the frozen layout and carrier". [V-4](viz-v4-a08-corpus-contract.md) (VZ4-D4, VZ4-Q1) and [V-3](viz-v3-a07-integration-contract.md) (VZ3-Q9) wait on this.

D10 makes the P3 exit the next goal, so this item is in phase R1.

## 2. Approach

E11 does not re-specify anything that a frozen contract already fixes. It:

1. defines the **exit snapshot**, the one frozen layout and carrier on which all A01-A08 evidence runs (section 3);
2. maps every C03, C04 and C05 obligation to the frozen contract that fixes it, or to a decision or deferral here (sections 4 to 6);
3. gives, per exit criterion, the fixtures, the tolerance as already approved, the command and the record (section 7);
4. names the new units that the map shows are missing (section 8).

C03-C05 are complete when this contract is approved and the exit snapshot record of section 3.2 exists. The private contract's status line and the P3 checkpoint table then point here.

### 7.1 Evidence rules for A01-A03 and A05-A08

- Every run is a valid run (section 3.2). A CI run is cited by its run URL and commit. A headed run carries the metadata of [accepted reference runs](../benchmarks/README.md#accepted-reference-runs) (OS, GPU, driver, browser and version, DPR, flags), without timing.
- Records go to `docs/evidence/p3-exit/<snapshot short SHA>/`, one file per criterion, immutable once committed. A04 and A08 keep their own record locations and are linked from there.
- A row is marked done in the [X1 index](d9-rendering-track.md#p3-exit-evidence-index-x1) only after an independent evidence review. The Primary accepts the exit; the user approves it (D10 R1 gate).
- **E11-R2 (reading, accepted by review round 1 with a caveat).** The prototype exit gate says fill-rule fixtures "match expected reference images". E11 realizes this as per-pixel expected colors from the independent oracle under Q4 and Q9, as V3-A14 and V-4 do, not as stored PNG files. No implementation output is used as an expected image. These colors match reference images outside the coverage band only; inside it, E11-Q4 decides.

### 7.2 Known defects at the exit

The exit gate requires "no crashes, invalid indices, NaN vertices, or out-of-range writes on the corpus". The private contract adds that "named ordinary fixtures must succeed" and forbids reducing "the ordinary-success corpus"; the P3 plan says "Ordinary frozen corpus must succeed". Three classes fail to mesh today: the seven ST-U3f cases (E4, kept as a known defect by D10), any E8 residue after E8-U2, and stroke `work-limit` cases (ST-U8, B2 S7), which E3 section 6 expects to persist until E2.

- **Named fixtures** are those of section 4 and the named rows of `a04-corpus/v1`. Under E11-Q2 (a), a closed list of named known defects, each with a fixture and a backlog item, is recorded in the snapshot record. Any other named fixture that fails to mesh fails A02 or A03.
- **Generated `a04-corpus/v1` rows** that are rejected are excluded from A04 under E3-Q3, and E3 section 6 leaves "whether a rejection rate is acceptable" to A02 and A03. Under E11-Q2 (a), A02 or A03 passes only if every rejected generated row falls into a class on the closed list (the E4 class, the E8 class, the stroke `work-limit` class, or a transport cap at limit + 1), with counts per class and stratum in the A01 sweep record. A rejection in any other class fails A02 or A03.

**A04 cells.** E11 does not change E3-A8: a declared cell with no measured case keeps A04 UNVERIFIED, and A04 PASS needs the coverage condition. If stroke cells stay unmeasured until E2 (E3 section 6), the exit waits, and promoting E2 becomes a user decision then.

## 9. Decisions for the user

**E11-Q1. What is "the frozen layout and carrier" for the P3 exit?**

- (a) **Recommended.** The functional v0 layout on K4, frozen by the snapshot. C04 is complete for the exit; its open parts and V-3's open A07 parts move to E12. This sets aside, for the exit, the carve-out sentence "The joint freeze above still gates C04 completion, P3 A05/A06 and any certificate claim": A05 and A06 are evidenced on v0. P3 also exits with the D8-interim placement exceptions still in force: the exact TypeScript fringe builder (V3-Q3 (c)) and the ST-U7 overlay builder run in `renderer-core`, against the private contract's "Keep Rust as the production geometry owner" and [`ARCHITECTURE.md`'s geometry contract](../../ARCHITECTURE.md#geometry-contract) (see [the anti-aliasing exception](../graphics-engine-architecture.md#anti-aliasing)), until the R2/K1 decision in E12 (E6).
- (b) The full C04 joint freeze before the exit: K1 with E1-E3, the M01-M06 certificate and product limits. This adds the R2 tiling implementation to R1.

Why (a): every R1 contract (E3, V-3, V-4) already measures v0 on K4 and records those identities. (b) moves the exit by the size of R2, which U2 never scheduled inside P3. Neither option changes a threshold.

**E11-Q2. May the exit pass with a closed list of known mesh failures (`unsupported-geometry`, stroke `work-limit`, transport caps)?**

- (a) **Recommended.** Yes, the closed list of section 7.2: the E4 class, the E8 class, the stroke `work-limit` class and transport caps at limit + 1. This relaxes, for those classes only, the private contract's "named ordinary fixtures must succeed" and "Do not … reduce the ordinary-success corpus", and the P3 plan's "Ordinary frozen corpus must succeed". The `work-limit` class also sets aside, for that class, the P3 plan's "prevent blanket NUMERIC_RANGE/WORK_LIMIT from masking unsupported geometry": the class is limited to stroke cases with a named fixture and backlog item E2, never a blanket. It answers E3 section 6's rejection-rate question by the class rule of section 7.2.
- (b) No. Promote E4 and finish E8 so every named fixture and generated row meshes before the exit. This adds E4 (a written S2 or A1 decision and its kernel change) and any E8 residue to R1, with re-runs of every identity-bound record.

Why (a): the defects cause no crash or invalid output, D10 already kept E4 as a known defect, and MVP 1 kept notice-and-not-drawn for stroke `work-limit` (B2). Under (b), E2 also joins R1.

**E11-Q3. Which failure behavior does P3 ship?** The V1 proposal says the production failure behavior "must be decided before P3 acceptance, with requirements text naming the meshes that can reach it", and the interim code then "removed or replaced"; V3 section h says it is "decided, before P3 acceptance, with requirements text naming the meshes that can reach that behavior". V3 section m: "The interim diagnostic code must be removed before P3 acceptance."

- (a) **Recommended.** Adopt the three D8-interim outcomes as P3's product behavior: a path the kernel cannot mesh is not drawn and gets a warning (V1-Q4); a path over the fringe work cap draws region-only (`fringe-work-cap`, V3 section h); an ST-U7 overlay failure hides the whole path, fill included (`overlay-unsupported`). E11-U4 writes the requirements text naming every class that reaches each outcome: the E11-Q2 list, the kernel limits, and every renderer-scope and batch-scope failure that hides a path in the V3 section h mapping table and its ST-U6 amendment (including `fringe-unsupported`, `fringe-range`, `invalid-mesh`, `invalid-response`, `packing-range`, `tolerance-range`, `port-version`, `mesh-pipeline-unavailable`, `internal-error`, `resource-limit`, `invalid-request`, `disposed` and `invalid-stroke`), and `overlay-unsupported`. It turns the interim code into product code. Because ST7-R10 says `overlay-unsupported` "must be removed with the TypeScript builder", that outcome stays tied to E12's builder placement. U2's R3, R0 and R2 continue in E12 to shrink those classes. This meets the "decided before P3 acceptance" rule but sets aside three frozen texts: U2's "No user-visible rejection is introduced by default"; V1's order "the R3, R0 and R2 direction, then R5 and U4 as last resorts"; and the private contract's D8 interim pointer scoping the diagnostic to "D8 checkpoints V2-V4 only". It is a product behavior change.
- (b) Keep the interim code and waive "must be decided before P3 acceptance" and "must be removed before P3 acceptance" for the exit; E12 decides later. No requirements text changes. This also keeps the diagnostic beyond "D8 checkpoints V2-V4 only" and leaves U2's "No user-visible rejection is introduced by default" unmet at acceptance.
- (c) Implement U2 (R3, R0 and R2, then R5 and U4) before the exit. Nothing is set aside, and R1 grows by the R2 tiling work, as in E11-Q1 (b).

**E11-Q4. What do coverage gates cover at the exit?** The private contract keeps "permitted coverage/color errors" as C03/C04 blockers and says the band tolerance "is decided after the next coverage experiment". VZ4-Q4 (a) chose report-only for strokes on V-4 and left "a stroke gate" to "its own full-tier decision"; this is that decision.

- (a) **Recommended.** Fill is gated by V3 section k (Q4 G1, G2 and G3). Band pixels and strokes are reported only. A partial-coverage tolerance and a stroke coverage gate move to backlog item **E13**, after P3. This sets aside, for the exit, the blocker status of the band tolerance and of stroke coverage errors.
- (b) Run a coverage experiment and decide both before the exit. This adds an experiment contract and a threshold decision to R1.

Why (a): the prototype plan lists the "coverage fringe and MSAA quality comparison" in P3's scope, not as an exit gate, and V-4's report gives that comparison. The exit gate's fill-rule image check is covered by the fill gates.
