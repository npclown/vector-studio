## 1. Scope

### 1.1 In scope

An interactive playground page that edits the appearance of one target path at a time and re-renders live through the existing ports. The editable fields are exactly the existing scene fields:

| Field         | Scene field (`packages/contracts/src/scene.ts`)         | Existing behavior it exercises                                                                                                                               |

| Fill color    | `PathStyle.fill` (`r, g, b, a`)                         | Color change rebuilds no mesh ([graphics architecture](../graphics-engine-architecture.md#primitive-rendering))                                              |
| Fill rule     | `ScenePathGeometry.fillRule` (`'nonzero' \| 'evenodd'`) | Fill paint key ([stroke contract 9.3](p3-b2-stroke-contract.md#93-cache-keys-memo-and-reuse))                                                                |
| Stroke on/off | `PathStyle.stroke` (`PathStroke` or `null`)             | ST-U6 stroke draw                                                                                                                                            |
| Stroke color  | `PathStroke.color`                                      | Builds no stroke mesh (stroke contract 9.3)                                                                                                                  |
| Stroke width  | `PathStroke.width` (finite, `>= 0`)                     | Stroke paint key; width 0 is accepted and draws nothing ([stroke contract 5](p3-b2-stroke-contract.md#5-scene-field-and-validation))                         |

## 2. Shared surface

**V-1 needs no change to the shared surface.** It changes no `packages/contracts` export, no public factory or constructor of `geometry-wasm`, `renderer-core` or `renderer-webgpu`, and no operation identity. It edits no file under `packages/`.

It uses only published exports:

| Package           | Used, as published                                                                                                                                                                                                                                                                                                                                                                                  |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `contracts`       | Types only, for example (the list is not exhaustive; any `packages/contracts` export may be used as published): `PathStyle`, `PathStroke`, `SceneColor`, `SceneFillRule`, `SceneStrokeCap`, `SceneStrokeJoin`, `RenderNodeSnapshot`, `RenderSceneSnapshot`, `RenderChangeSet`, `SceneApplyResult`, `RendererSceneSynchronization`, `RenderCamera`, `RendererDiagnostic`, `RendererCapabilityResult` |
| `geometry-wasm`   | `createFillMeshPort`, `createStrokeMeshPort` and the `FillMeshAdapter` and `StrokeMeshAdapter` types                                                                                                                                                                                                                                                                                                |
| `renderer-core`   | `PrimitiveRendererService` (`replaceSnapshot`, `applyChanges`, `setCamera`, `getPathMeshStatistics`, `prepare`, `acknowledge`, `requiresMeshPipeline`, `dispose`); the packet and frame-source types from the root `index.ts`; `RetainedSceneMirror` in unit tests only                                                                                                                             |
| `renderer-webgpu` | `WebGpuBackend` (`initialize`, `attachPrimitiveFrameSource`, `subscribeDiagnostics`, `getStatistics`, `dispose`)                                                                                                                                                                                                                                                                                    |

`applyChanges` with an updated path node is published API (`RendererSceneSynchronization` in `packages/contracts`), so V-1 uses it as published. Today only unit tests exercise it for path nodes (`tests/unit/st-u6-stroke-scene.test.ts`, `tests/unit/v3a-path-scene.test.ts`). The P1 fixture and runner use `applyChanges` for primitive nodes only, and the V4 and ST-U8 pages use `replaceSnapshot`. V-1 is therefore the first page to send path-node changes. `tooling/boundary-policy.mjs` already allows the playground's imports of these four packages.

**One need that could have required a change, and how it is avoided.** The page wants to show whether the target is drawn now. The renderer's rules (`packages/renderer-core/src/path-mesh-pipeline.ts` on `origin/main`) decide when notices tell it so:

- **Key changes re-notify.** `#reconcile` runs on every `prepare` (line 462) and deletes every cache and memo entry whose paint key differs from the node's current key (lines 747-758, 762-773). An edit that returns to an earlier failing key therefore calls the port again, and `#memoize` enqueues a new notice (lines 1027-1038). `fringe-work-cap` is emitted once per new cache entry (lines 1072-1075), so cap, join, width and miter edits re-notify it too. A fill entry depends on the fill rule only, so turning the fill off and on keeps it; a stroke turned off or set to width 0 has no key, so its entries are deleted and turning it on again rebuilds.
- **Three cases are silent.** (1) A zoom or bucket return with the key unchanged: the memo key includes the tolerance exponent `e` (lines 874-877), and a memo hit enqueues nothing. (2) An `overlay-unsupported` mark: it lives on the fill entry for one pair of served variants and persists across opacity edits (lines 1156-1207), so opacity 0.5, then 1, then 0.5 notifies once. (3) State failures (`tolerance-range`, `fringe-range`, `packing-range`, `port-version`) notify on entering the state only and clear with no notice (lines 612-622).

A per-node draw-state query on `PrimitiveRendererService` would answer "is this path drawn now" for every case. It would be a `renderer-core` public-surface change: full tier, reviewed by both tracks, and split out as a rendering-track item under the [D9 conflict rule](d9-post-mvp1-tracks-proposal.md#operations). V-1 avoids it. The page keeps the notice log and derives the target status from the rules above (section 3.4). Only the three silent cases need bookkeeping beyond "the latest notice for the current key". [V1-Q4](#7-open-questions) asks the user to confirm.

The page's `window.__vectorStudioVizV1Appearance` test hook is page-local, like the ST-U8 hook. It is not a shared surface.

**Parsing.** A number control applies only a finite value inside its range. The number input accepts any value inside the range, not only step multiples. Anything else (empty, NaN, out of range, a malformed hex color) is not applied: the scene keeps the last applied value, the control gets `aria-invalid="true"`, and a text message next to it names the range. These bounds are V-1's UI bounds, inside the scene contract's validity rules (width `>= 0`, miter limit `>= 1`, opacity and channels in `[0, 1]`), so a value the page applies is always valid scene data. Turning the stroke off and on restores its last fields; the page never sends a stroke of `null` fields.

### 3.3 Edit flow

1. A control event updates the page's `AppearanceState` for the target. The state is plain JSON data: no DOM node, GPU object or WASM handle ([`ARCHITECTURE.md`](../../ARCHITECTURE.md#state-classification)).
2. **When an edit is applied** (the Primary's recommendation, [V1-Q3](#7-open-questions) (b)). The commit rule: _Sliders apply live on `input`, except the width and miter-limit sliders, which apply on `change`. Every number field, including the alpha and opacity number fields, applies on commit: `change`, Enter or blur. Radios, checkboxes and color pickers apply live._ Before a commit, `input` events update the displayed value only. A slider fires `change` on release and, in Chromium, on each keyboard step (V1-A12 checks this). Color and opacity build no mesh, so live updates cost no port call. Width and miter limit are the edits that rebuild a stroke on each distinct value (section 6).
3. Applied edits are coalesced to at most one scene change per animation frame; the change carries the latest values.
4. The flush builds the target's full `RenderNodeSnapshot`, with `verbs` and `points` reused from the initial scene unchanged, and calls `service.applyChanges` with `revision = current + 1`, `baseRevision = current`, `updated: [node]` and empty `inserted`, `removed` and `orders`. This one-node rule holds for every control flush and for "Reset target".
5. "Reset all" is not a flush. It calls `replaceSnapshot` once with the initial scene at `current + 1` and resets the page state; its result is handled as in step 6 for `replaceSnapshot`.
6. Result handling:
   - `applied`: the page's revision advances by one;
   - `resync-required`: the page calls `replaceSnapshot` once with the whole current state at revision `result.current.revision + 1`, or `current + 1` if `result.current` is null (`resyncResult` in `scene-mirror.ts`, lines 530-535);
   - `invalid-scene`: the state reverts to the last applied state and the reason is listed as an error on the page (section 3.2 makes this unreachable for parsed values, so it signals a defect);
   - `disposed`: the page stops applying edits;
   - a `replaceSnapshot` result other than `applied` or `replayed`: the page lists it as an error, disables the controls and applies no further edit until reload. It does not retry.

**Cache invalidation.** The scene revision orders the changes; it is not the mesh cache key. Because `verbs` and `points` are unchanged, the mirror keeps the node's geometry revision ([V3 section b](p3-v3-renderer-mesh-pipeline-contract.md#b-port-consumption-geometry-revision-and-cache-key); `assignGeometryRevisions` in `scene-mirror.ts`). Mesh work then follows the paint keys of [stroke contract 9.3](p3-b2-stroke-contract.md#93-cache-keys-memo-and-reuse):

- a fill rule change misses the fill key only;
- a width, cap, join or miter-limit change misses the stroke key only, when the width is above 0 before and after. A stroke of width 0, or a stroke turned off, has no stroke key (`paintKeyOf`, line 1465) and builds nothing, so an edit to or from width 0 has stroke delta 0 on the way down and rebuilds on the way up;
- turning the fill off and on with an unchanged fill rule keeps the fill entry (section 2) and builds nothing, unless the cache evicted the entry meanwhile;
- fill color, stroke color and opacity changes build no mesh. At `0 < o < 1` with both paints, the joint overlay is derived from the cached meshes with no port call ([graphics architecture, P3 joint fill and stroke coverage](../graphics-engine-architecture.md#anti-aliasing)).

V1-A7 checks this through `getPathMeshStatistics()` (`portCalls`, `strokePortCalls`).

E11-U4 pointer (section 3.4), 2026-10-24: the code is renamed to `render.path-mesh-failure` with the same meaning; V1-A9, this section, its acceptance records and the notice literals stand. The notice meaning follows `pathMeshNoticeDiagnostic` by name ([E11-U4 addendum](d9-e11-u4-failure-behavior-addendum.md)).

The D8-interim notices (`render.path-mesh-interim-failure`) of the [V3 failure outcome](p3-v3-renderer-mesh-pipeline-contract.md#h-d8-interim-failure-outcome) and [stroke contract 9.8](p3-b2-stroke-contract.md#98-notices) stay visible and are never hidden or cleared:

- **Notice log.** Every notice is listed, newest first, with its node id, paint, failure code and tolerance exponent, as the ST-U8 page lists them. An edit or a reset never clears it. Like the ST-U8 page (`p3-b2-strokes.ts`, lines 39 and 64), the log keeps the newest 400 entries; older entries are dropped and counted, and the panel shows "N older notices dropped from this list". The hook keeps every notice, so the spec sees all of them.
- **Notice meaning.** It follows `pathMeshNoticeDiagnostic` (`path-mesh-pipeline.ts`): `fringe-work-cap` means "drawn without its coverage fringe", and every other code means "not drawn". The whole path is not drawn when one paint fails (stroke contract 9.6). `overlay-unsupported` has `paint: null` and a null exponent, and it applies only while the joint condition holds, that is with both paints drawable and `0 < o < 1`.
- **Target status (derived).** For the edit target, the page keeps one record per paint. A record is shown only while its paint is on: the fill while `fill` is not null, and the stroke while it is not null and its width is above 0. Each record holds the latest notice that arrived for the current key: fill rule for the fill; width, cap, join and miter limit for the stroke. Another key makes that record empty, because a key change rebuilds and re-notifies (section 2). The three silent cases of section 2 are handled as follows:
  - zoom: records are kept per tolerance exponent, and a return to an exponent shows the record kept for it. The renderer can also serve an entry built at `e − 1` or `e − 2` for a requested `e` with no new notice (`#lookup`, `path-mesh-pipeline.ts` lines 860-864), and a `fringe-unsupported` variant is silent when it is reused (lines 1108-1112). The published API does not show which entry serves a node: the packet's mesh draws (`MeshFillDraw`) carry no node id or served exponent, and the service never hands the page a `PathMeshDraw`, although that type is exported. So after any zoom change the status is labelled "may differ; the notice log is authoritative";
  - `overlay-unsupported`: kept per fill rule and stroke key, and shown as "not drawn" only while `0 < o < 1` with both paints on. At `o = 1`, at `o = 0` or with one paint off, the path draws through the ordinary draws, so the status does not show it;
  - state failures: shown from the notice until the next zoom-bucket or port change, and marked "may have cleared", because the renderer sends no clearing notice.

  The status is labelled "derived from notices". The log is authoritative.

- **Counts.** The status panel shows the notice count and the renderer's `noticesQueued` and `noticesDropped`.
- **Expected classes.** `work-limit` on cubic and crossing strokes (the open ST-U9 item, rendering track E1 and E2), and `fringe-work-cap` above 128 boundary vertices (V3-Q2 (c)). `overlay-unsupported` covers region-only fills with a sloped outer edge (stroke contract 9.6). No V-1 target is known to reach it; none has been observed. The page shows every class and does not avoid it.

The UNVERIFIED precision label is shown on the page and written into every evidence directory, with the text of the ST-U8 label adapted to V-1.

### 3.5 Accessibility basics

- Every control has a visible `<label>`. Related controls are grouped in a `<fieldset>` with a `<legend>`: target, fill, stroke, opacity.
- Enumerations use radio groups, and numbers use native range and number inputs, so every edit works by keyboard with no custom key handling. No control traps focus.
- Focus is visible on every control (`:focus-visible` outline).
- Invalid input sets `aria-invalid="true"` and links its message with `aria-describedby`.
- The target-status region is `aria-live="polite"` and announces status changes for the target only. The notice log is not live, so a burst of notices is not read out.
- The canvas has an `aria-label`. The current appearance of each target is also printed as text in the status panel, so the state does not depend on reading the canvas. Status uses text, not color alone.

## 4. Acceptance criteria

All results are functional evidence. Precision is UNVERIFIED against the 0.25 physical-pixel target until B4 has A04 evidence, and no Q4 coverage threshold is claimed.

**Methods.** "GPU spec" is the new headed spec `tests/gpu/viz-v1-appearance.spec.ts` under `pnpm test:gpu`, in the `chrome` and `edge` projects of `playwright.gpu.config.ts`, at device pixel ratios 1 and 2 ([V1-Q7](#7-open-questions)). It reuses the ST-U8 spec's helpers: the per-run evidence directory with `UNVERIFIED.txt` and `observations.json`, `p1Source()` from `tests/support/p1-evidence.ts`, the in-page PNG probe decoding, `PROBE_TOLERANCE` (12 eight-bit steps) and the background-mix expected colors, and a page `settle()` with the ST-U8 definition (12 stable frames, at most 1200). A fresh page is loaded per scenario, because notices are emitted on transitions. The helpers are **copied** into the new spec (or into a new file under `tests/support/` that only the new spec imports). `tests/gpu/p3-b2-strokes.spec.ts` is not edited (V1-A15). "Unit" is Vitest under `tests/unit/viz-v1-appearance.test.ts` in `pnpm test:unit`.

## 6. Risks

- **Kernel-outcome coupling.** The notice literals depend on the stroke and fill revisions (`+r4`, `r2`) and limits. E1, E2, E4 or a limit raise can change them, and the D9 rule makes the rendering-track PR update a visualization-track spec. [V1-Q6](#7-open-questions) chooses how tight the coupling is.
- **Main-thread stalls.** Port calls run synchronously in `prepare`.
  - The known cost comes from one class only. Failing crossing chord strokes of 16 or more segments spend 0.15 to 0.8 s natively before `work-limit` (the [ST-U3b probe](p3-fill-stroke-meshes.md#b2-st-u3b-scaling-probe)). With the WASM factor measured for fill, about 1.58 (the AL-S2 `k̂`), that class would take roughly 1.3 s. This is an estimate for that class, not a measurement, and it says nothing about V-1's targets.
  - No V-1 target is in that class. `v1-star`'s stroke is a 5-segment self-crossing pentagram, which is not known to fail. `v1-circle` is the only target known to fail (`work-limit` at zoom 1). It is a cubic stroke, and the cost of its failure is unmeasured.
  - Why it repeats: a key change deletes the old entries (section 2), so every distinct width or miter value on a failing stroke pays for a full rebuild. The renderer drops a stale request only from its isolation stack (`path-mesh-pipeline.ts`, lines 896-906), not a call already running.
  - Mitigation: the recommended commit rule (V1-Q3 (b)) applies width and miter values on release or per keyboard step, not on each `input` of a pointer drag. V1-A13 records the latency. A stall is filed as a rendering-track item with a fixture; E1 targets it.
- **Derived status can be stale.** The target status of section 3.4 is page bookkeeping over the rules of section 2. Several cases can make it differ from the renderer's state: a state failure that clears silently, a memo eviction, a resource-limit expiry, an entry built at `e − 1` or `e − 2` serving `e`, or a silently reused `fringe-unsupported` variant. The published API cannot observe the last two. The status marks the state-failure case "may have cleared" and, after any zoom change, "may differ; the notice log is authoritative". The log is authoritative, and the spec loads a fresh page per scenario.
- **Reused path data.** The targets import `B2_PATHS` and `V4_PATHS`. A change to those scenes would change V-1 silently; the pinned literal copy in V1-A3 makes it fail instead.
- **Host-injection tests are shared files.** The two unit-test edits of section 3.1 change `tests/` files that both tracks rely on. They are named in the Gate line under D9-Q8 (a), and each keeps its deny-list for every other file.
- **D8-interim builders.** The fringe and joint-overlay builders are time-bounded exceptions that E6 may remove or move. Their notices (`fringe-work-cap`, `overlay-unsupported`) and the joint draw's output can change when that happens.
- **Precision stays UNVERIFIED.** The probes are functional and far from edges. They do not measure the 0.25 px target.
- **Traceability.** `docs/requirements.md` has no IDs, so section 1.3 cites section and bullet text. A later requirements edit can break the citation silently.
- **Scope drift.** A properties panel, click selection or persistence would cross into P5 or the deferred "Full layers/properties UI". Section 1.2 excludes them; the review checks the diff against it.
- **No CI for GPU evidence.** The weekly D9 checkpoint and the per-PR headed run are the only GPU gates.
- **Linked track plan.** This contract links anchors in `docs/plans/d9-visualization-track.md` (added by PR #198, merged as `485ddd0`). If that file's headings change, the anchors here must follow.

### Amendment 2026-10-22 (user-approved): §3.4 per-exponent display

The user approved this amendment in chat on 2026-10-22, after the implementation review (PR #201) found that the implementation shows the latest record where section 3.4 says records are kept per tolerance exponent and a return to an exponent shows the record kept for it.

- The derived target status shows the most recent record for each paint while that paint is on.
- After any zoom change the status is labelled "may differ; the notice log is authoritative".
- Per-exponent records are kept and exposed only through the test hook (`snapshot().targetStatus`), not displayed as a status per exponent.
- Why: renderer-core does not publish the serving exponent, so the page cannot tell which exponent's record applies to a node. A per-node draw-state or exponent query would be a shared-surface change at full tier (see section 2 and V1-Q4 (c)).
