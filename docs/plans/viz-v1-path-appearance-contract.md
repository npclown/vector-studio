# V-1 contract: path appearance editing on the existing P3 surface

Status: DRAFT, 2026-10-22. Pending independent review and user approval. Nothing here is in force, and no product code for V-1 starts, until the user approves it in chat ([`AGENTS.md`](../../AGENTS.md#working-rules): no product code before acceptance criteria and validation methods exist).

Track: visualization. Item: V-1 of the [D9 visualization track plan](d9-visualization-track.md#v-1-path-appearance-editing). Tier: full, because V-1 adds user-visible behavior ([`AGENTS.md`](../../AGENTS.md#change-workflow)). Source decision: [D9-Q4 (a)](d9-post-mvp1-tracks-proposal.md#user-decisions-2026-10-22).

This contract owns V-1's scope, page design, acceptance criteria and validation. It does not repeat the D9 decision, the ownership boundary or the shared-surface rules, which [D9](d9-post-mvp1-tracks-proposal.md#boundary) owns. It changes no requirement, threshold, milestone order, milestone gate, port, ABI or `packages/contracts` export.

## 1. Scope

### 1.1 In scope

An interactive playground page that edits the appearance of one target path at a time and re-renders live through the existing ports. The editable fields are exactly the existing scene fields:

| Field         | Scene field (`packages/contracts/src/scene.ts`)         | Existing behavior it exercises                                                                                                                               |
| ------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Fill on/off   | `PathStyle.fill` (`SceneColor` or `null`)               | V3 fill draw                                                                                                                                                 |
| Fill color    | `PathStyle.fill` (`r, g, b, a`)                         | Color change rebuilds no mesh ([graphics architecture](../graphics-engine-architecture.md#primitive-rendering))                                              |
| Fill rule     | `ScenePathGeometry.fillRule` (`'nonzero' \| 'evenodd'`) | Fill paint key ([stroke contract 9.3](p3-b2-stroke-contract.md#93-cache-keys-memo-and-reuse))                                                                |
| Stroke on/off | `PathStyle.stroke` (`PathStroke` or `null`)             | ST-U6 stroke draw                                                                                                                                            |
| Stroke color  | `PathStroke.color`                                      | Builds no stroke mesh (stroke contract 9.3)                                                                                                                  |
| Stroke width  | `PathStroke.width` (finite, `>= 0`)                     | Stroke paint key; width 0 is accepted and draws nothing ([stroke contract 5](p3-b2-stroke-contract.md#5-scene-field-and-validation))                         |
| Cap           | `PathStroke.cap`                                        | Stroke paint key                                                                                                                                             |
| Join          | `PathStroke.join`                                       | Stroke paint key                                                                                                                                             |
| Miter limit   | `PathStroke.miterLimit` (finite, `>= 1`)                | Stroke paint key; required for every join kind                                                                                                               |
| Node opacity  | `SceneNodeBase.opacity` (`[0, 1]`)                      | With both paints at `0 < o < 1`, the ST-U7c+d joint fill draw, #193 ([addendum 4.1](p3-b2-st-u7-joint-coverage-addendum.md#41-drawable-condition-and-order)) |

The page is UI over the existing fill-plus-stroke draw. It adds no draw work, no kernel work and no renderer code. It composes `createFillMeshPort`, `createStrokeMeshPort`, `PrimitiveRendererService` and `WebGpuBackend` exactly as the ST-U8 stroke page does (`apps/playground/src/p3-b2-strokes.ts`, lines 1-15).

### 1.2 Deferred

- Dash editing, gradients and full appearance controls, as in [`docs/prototype-plan.md`](../prototype-plan.md#deferred-from-the-graphics-prototype) and its [requirement coverage](../prototype-plan.md#requirement-coverage) row "Shapes and appearance". The scene contract has no dash or gradient field, so either would also be a shared-surface change.
- Document persistence, the JSON round trip, commands, transactions and undo. They belong to [P5](../prototype-plan.md#p5-editor-integration-slice) and need its own entry decision.
- Selection: click, additive and marquee selection, hit testing and selection state. They are P5 work. V-1's "selected path" is a page-local edit-target picker, not editor selection (see [V1-Q2](#7-open-questions)).
- Geometry editing (anchors, handles, node insertion and removal), transforms, rotation and container opacity.
- Device-loss behavior beyond what the renderer already does. V-1 makes no A07 claim.
- Anything else that needs P5 entry, a new package or a change to the shared surface.

## 2. Shared surface

**V-1 needs no change to the shared surface.** It changes no `packages/contracts` export, no public factory or constructor of `geometry-wasm`, `renderer-core` or `renderer-webgpu`, and no operation identity. It edits no file under `packages/`.

It uses only what the ST-U8 page and the P1 fixture already use:

| Package           | Used, as published                                                                                                                                                                                                                                                              |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `contracts`       | Types only: `PathStyle`, `PathStroke`, `SceneColor`, `SceneFillRule`, `SceneStrokeCap`, `SceneStrokeJoin`, `RenderNodeSnapshot`, `RenderSceneSnapshot`, `RenderChangeSet`, `SceneApplyResult`, `RendererSceneSynchronization`, `RendererDiagnostic`, `RendererCapabilityResult` |
| `geometry-wasm`   | `createFillMeshPort`, `createStrokeMeshPort` and the `FillMeshAdapter` and `StrokeMeshAdapter` types                                                                                                                                                                            |
| `renderer-core`   | `PrimitiveRendererService` (`replaceSnapshot`, `applyChanges`, `setCamera`, `getPathMeshStatistics`, `prepare`, `acknowledge`, `requiresMeshPipeline`, `dispose`); the packet and frame-source types from the root `index.ts`; `RetainedSceneMirror` in unit tests only         |
| `renderer-webgpu` | `WebGpuBackend` (`initialize`, `attachPrimitiveFrameSource`, `subscribeDiagnostics`, `getStatistics`, `dispose`)                                                                                                                                                                |

`applyChanges` with one updated path node is already published behavior (the P1 fixture and runner use it, `apps/playground/src/p1-fixture.ts`, line 355). `tooling/boundary-policy.mjs` already allows the playground's imports of these four packages.

**One need that could have required a change, and how it is avoided.** The renderer emits a D8-interim notice once per transition or memo entry, and a memo hit is silent (`packages/renderer-core/src/path-mesh-pipeline.ts`, `#consultMemo` and `#memoize`). An edit that returns to an earlier failing value therefore produces no new notice. A per-node draw-state query on `PrimitiveRendererService` would answer "is this path drawn now", but it would be a `renderer-core` public-surface change: full tier, reviewed by both tracks, and split out as a rendering-track item under the [D9 conflict rule](d9-post-mvp1-tracks-proposal.md#operations). V-1 avoids it: the page keeps the notice log and derives the target's current notices by its own bookkeeping (section 3.4). [V1-Q4](#7-open-questions) asks the user to confirm.

The page's `window.__vectorStudioVizV1Appearance` test hook is page-local, like the ST-U8 hook. It is not a shared surface.

## 3. Page design

### 3.1 Which page

Recommended ([V1-Q1](#7-open-questions) (a)): a **new page**, `apps/playground/viz-v1-appearance.html`, with:

- `src/viz-v1-appearance.ts`: the host (ports, service, backend, camera, controls, notices), modelled on `src/p3-b2-strokes.ts`;
- `src/viz-v1-appearance-scene.ts`: the scene, its target paths and its views;
- `src/viz-v1-appearance-state.ts`: pure state, parsing and the state-to-scene mapping, with no DOM, GPU or WASM import, so unit tests can load it;
- one `rollupOptions.input` entry in `apps/playground/vite.config.mjs`.

The existing pages stay unchanged. The ST-U8 stroke page's spec gates frozen per-view notice sets and draw counts on a static scene, and its scene is the source of the proposed B4 stroke rows. Edits would make those outcomes depend on edit history. The V4 page is fill-only.

**Target paths.** Path data is imported from the exported specs of the existing pages, so V-1 adds no new geometry and every path has been run against the current kernel. Each initial appearance is one the ST-U8 or V4 page already draws at zoom 1.

| Target id    | Path data from                       | Initial appearance                                                                         | Shows                                                                                                                      |
| ------------ | ------------------------------------ | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `v1-square`  | B2 `fill-stroke-square` (`B2_PATHS`) | That cell's: red fill, blue stroke width 10, butt, miter, limit 4                          | Fill and stroke color, opacity and the joint draw (B2 `both-half` draws this shape at opacity 0.5 with no notice)          |
| `v1-star`    | V4 `star-nonzero` (`V4_PATHS`)       | That cell's fill, nonzero; stroke off                                                      | Fill rule: the center is filled under nonzero and empty under even-odd                                                     |
| `v1-zigzag`  | B2 `cap-butt` (`B2_PATHS`)           | That cell's: no fill, blue stroke width 14, butt, miter                                    | Caps and joins on an open polyline; a round cap at zoom 1 gives `fringe-work-cap` (ST-U8 observation `cap-round`)          |
| `v1-chevron` | B2 `miter-limit-keeps` (`B2_PATHS`)  | That cell's stroke; no fill                                                                | Miter limit next to its switch point                                                                                       |
| `v1-circle`  | B2 `fill-stroke-circle` (`B2_PATHS`) | That cell's red fill; stroke off (its width-8 round-join stroke kept as the stroke fields) | Turning the stroke on at zoom 1 gives `work-limit` (ST-U8 observation `1/overview-zoom-1`), so the whole path is not drawn |

The scene has a backdrop rectangle and the five targets in a 3 + 2 grid under one container at identity, on a 720 x 600 CSS px surface. Views: `overview-zoom-1` (default), `zoom-0.25` and `zoom-4`, plus the pan and zoom interaction of the ST-U8 page (drag, wheel, zoom buttons, range 0.01 to 64).

### 3.2 Controls and value ranges

All controls are native HTML inputs. The page adds no dependency and no framework.

| Control      | Element                                           | Range and step                                                                                                 | Maps to                                          |
| ------------ | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| Edit target  | Radio group, one radio per target                 | The five target ids                                                                                            | Which node the edits apply to (page state only)  |
| Fill         | Checkbox                                          | On or off                                                                                                      | `fill`: the color below, or `null`               |
| Fill color   | `<input type="color">` plus an alpha number input | `#rrggbb`; alpha 0 to 1, step 0.01                                                                             | `{r, g, b} = channel / 255` exactly; `a` = alpha |
| Fill rule    | Radio group                                       | `nonzero`, `evenodd`                                                                                           | `geometry.fillRule`                              |
| Stroke       | Checkbox                                          | On or off                                                                                                      | `stroke`: the fields below, or `null`            |
| Stroke color | As fill color                                     | As fill color                                                                                                  | `stroke.color`                                   |
| Stroke width | Range slider and number input, kept equal         | 0 to 64 node-local units; slider step 0.5, number step 0.125                                                   | `stroke.width`; 0 is valid and draws no stroke   |
| Cap          | Radio group                                       | `butt`, `round`, `square`                                                                                      | `stroke.cap`                                     |
| Join         | Radio group                                       | `miter`, `round`, `bevel`                                                                                      | `stroke.join`                                    |
| Miter limit  | Range slider and number input                     | 1 to 100; slider 1 to 20 step 0.1, number step 0.01; enabled for every join, labelled "applies to miter joins" | `stroke.miterLimit`                              |
| Opacity      | Range slider and number input                     | 0 to 1, step 0.01                                                                                              | Node `opacity`                                   |
| Reset        | Buttons "Reset target" and "Reset all"            | -                                                                                                              | The initial appearance                           |

**Parsing.** A number control applies only a finite value inside its range. The number input accepts any value inside the range, not only step multiples. Anything else (empty, NaN, out of range, a malformed hex color) is not applied: the scene keeps the last applied value, the control gets `aria-invalid="true"`, and a text message next to it names the range. These bounds are V-1's UI bounds, inside the scene contract's validity rules (width `>= 0`, miter limit `>= 1`, opacity and channels in `[0, 1]`), so a value the page applies is always valid scene data. Turning the stroke off and on restores its last fields; the page never sends a stroke of `null` fields.

### 3.3 Edit flow

1. A control event updates the page's `AppearanceState` for the target. The state is plain JSON data: no DOM node, GPU object or WASM handle ([`ARCHITECTURE.md`](../../ARCHITECTURE.md#state-classification)).
2. Edits are coalesced to at most one scene change per animation frame; the change carries the latest values ([V1-Q3](#7-open-questions)).
3. The flush builds the target's full `RenderNodeSnapshot`, with `verbs` and `points` reused from the initial scene unchanged, and calls `service.applyChanges` with `revision = current + 1`, `baseRevision = current`, `updated: [node]` and empty `inserted`, `removed` and `orders`.
4. Result handling:
   - `applied`: the page's revision advances by one;
   - `resync-required`: the page calls `replaceSnapshot` once with the whole current state at a new revision;
   - `invalid-scene`: the state reverts to the last applied state and the reason is listed as an error on the page (section 3.2 makes this unreachable for parsed values, so it signals a defect);
   - `disposed`: the page stops applying edits.

**Cache invalidation.** The scene revision orders the changes; it is not the mesh cache key. Because `verbs` and `points` are unchanged, the mirror keeps the node's geometry revision ([V3 section b](p3-v3-renderer-mesh-pipeline-contract.md#b-port-consumption-geometry-revision-and-cache-key); `assignGeometryRevisions` in `scene-mirror.ts`). Mesh work then follows the paint keys of [stroke contract 9.3](p3-b2-stroke-contract.md#93-cache-keys-memo-and-reuse):

- a fill rule change misses the fill key only;
- a width, cap, join or miter-limit change misses the stroke key only;
- fill color, stroke color and opacity changes build no mesh. At `0 < o < 1` with both paints, the joint overlay is derived from the cached meshes with no port call ([graphics architecture, P3 joint fill and stroke coverage](../graphics-engine-architecture.md#anti-aliasing)).

V1-A7 checks this through `getPathMeshStatistics()` (`portCalls`, `strokePortCalls`).

### 3.4 Notices

The D8-interim notices (`render.path-mesh-interim-failure`) of the [V3 failure outcome](p3-v3-renderer-mesh-pipeline-contract.md#h-d8-interim-failure-outcome) and [stroke contract 9.8](p3-b2-stroke-contract.md#98-notices) stay visible and are never hidden or cleared:

- **Notice log.** Every notice is listed, newest first, with its node id, paint, failure code and tolerance exponent, as the ST-U8 page lists them. The log is never cleared by an edit or a reset.
- **Target status.** For the edit target, the page shows its current notices. It records each notice under the target's mesh-affecting values in force when the notice arrived (fill: fill rule; stroke: width, cap, join, miter limit; with the notice's tolerance exponent). When the values return to a recorded set, the recorded notices are shown again, because the renderer's memo hit is silent (section 2). A `work-limit`, `numeric-range`, `unsupported-geometry` or `overlay-unsupported` notice is shown as "not drawn"; `fringe-work-cap` as "drawn without fringe". Notices that arrive at another zoom bucket are shown under their own exponent. This is page bookkeeping over published notices, and it is labelled as derived.
- **Counts.** The status panel shows the notice count and the renderer's `noticesQueued` and `noticesDropped`.
- **Expected classes.** `work-limit` on cubic and crossing strokes (the open ST-U9 item, rendering track E1 and E2), `fringe-work-cap` above 128 boundary vertices (V3-Q2 (c)), and `overlay-unsupported` for the joint draw's narrower sloped-edge class (stroke contract 9.6), for example a filled open zigzag at `0 < o < 1`. The page shows them and does not avoid them.

The UNVERIFIED precision label is shown on the page and written into every evidence directory, with the text of the ST-U8 label adapted to V-1.

### 3.5 Accessibility basics

- Every control has a visible `<label>`. Related controls are grouped in a `<fieldset>` with a `<legend>`: target, fill, stroke, opacity.
- Enumerations use radio groups, and numbers use native range and number inputs, so every edit works by keyboard with no custom key handling. No control traps focus.
- Focus is visible on every control (`:focus-visible` outline).
- Invalid input sets `aria-invalid="true"` and links its message with `aria-describedby`.
- The target-status region is `aria-live="polite"` and announces status changes for the target only. The notice log is not live, so a burst of notices is not read out.
- The canvas has an `aria-label`. The current appearance of each target is also printed as text in the status panel, so the state does not depend on reading the canvas. Status uses text, not color alone.

## 4. Acceptance criteria

All results are functional evidence. Precision is UNVERIFIED against the 0.25 physical-pixel target until B4 has A04 evidence, and no Q4 coverage threshold is claimed.

**Methods.** "GPU spec" is the new headed spec `tests/gpu/viz-v1-appearance.spec.ts` under `pnpm test:gpu`, in the `chrome` and `edge` projects of `playwright.gpu.config.ts`, at device pixel ratios 1 and 2 ([V1-Q7](#7-open-questions)). It reuses the ST-U8 spec's helpers: the per-run evidence directory with `UNVERIFIED.txt` and `observations.json`, `p1Source()` from `tests/support/p1-evidence.ts`, the in-page PNG probe decoding, `PROBE_TOLERANCE` (12 eight-bit steps) and the background-mix expected colors, and a page `settle()` with the ST-U8 definition (12 stable frames, at most 1200). A fresh page is loaded per scenario, because notices are emitted on transitions. The helpers are copied or moved into `tests/support/` without changing their behavior; any move keeps `tests/gpu/p3-b2-strokes.spec.ts` byte-for-byte equal in its gates. "Unit" is Vitest under `tests/unit/viz-v1-appearance.test.ts` in `pnpm test:unit`.

**Probe rule.** Each probe lies at least 2 CSS px from every boundary of the expected regions in both the before and after states of its edit. A probe compares its observed color with the expected color within `PROBE_TOLERANCE`. Where a scenario must separate two candidate colors, the spec first checks that they differ by more than twice the tolerance.

### 4.1 Expected-literal rule

V1-A9's notice sets and any draw counts are current-kernel observations, as in the ST-U8 spec. They are fixed at the first headed run, recorded in the spec with the date and the operation ids, and must be identical in Chrome and Edge. Under [D9](d9-post-mvp1-tracks-proposal.md#two-tracks), a later PR whose change alters them updates them in the same PR with a dated note. A literal is never changed to make a failing run pass without that note.

### 4.2 Scenario values left to the first headed run

V1-A8 and V1-A10 name probe kinds and edits. If a V1-A8 or V1-A10 scenario then shows a notice on its target, the scenario is FAIL, and the Primary decides whether the target or the scenario changes, with a dated note here.

### 4.3 Performance claim

## 6. Risks

- **Kernel-outcome coupling.** V1-A9's literals depend on the stroke and fill revisions (`+r4`, `r2`) and limits. E1, E2, E4 or a limit raise can change them, and the D9 rule makes the rendering-track PR update a visualization-track spec. [V1-Q6](#7-open-questions) chooses how tight the coupling is.
- **Main-thread stalls.** Port calls run synchronously in `prepare`. A width or join edit on a cubic or crossing stroke can spend up to about 0.8 s before failing with `work-limit` (the ST-U3b observation), and a dragged slider can queue several such keys. The renderer drops requests whose key changed, but the page can still stall. V1-A13 records it; a stall is filed as a rendering-track item with a fixture (E1 targets it). [V1-Q3](#7-open-questions) offers commit-only updates instead.
- **Derived status can be stale.** The target status of section 3.4 is page bookkeeping. A memo eviction, a resource-limit expiry or a bucket change can make it differ from the renderer's state. The log is authoritative; the spec loads a fresh page per scenario.
- **D8-interim builders.** The fringe and joint-overlay builders are time-bounded exceptions that E6 may remove or move. Their notices (`fringe-work-cap`, `overlay-unsupported`) and the joint draw's output can change when that happens.
- **Precision stays UNVERIFIED.** The probes are functional and far from edges. They do not measure the 0.25 px target.
- **Traceability.** `docs/requirements.md` has no IDs, so section 1.3 cites section and bullet text. A later requirements edit can break the citation silently.
- **Scope drift.** A properties panel, click selection or persistence would cross into P5 or the deferred "Full layers/properties UI". Section 1.2 excludes them; the review checks the diff against it.
- **No CI for GPU evidence.** The weekly D9 checkpoint and the per-PR headed run are the only GPU gates.
- **Unmerged dependency.** This contract links `docs/plans/d9-visualization-track.md`, which PR #198 adds. If #198 changes that file's headings, the anchors here must follow.
