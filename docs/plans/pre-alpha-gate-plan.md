## 1. What the documents say

- **"Pre-alpha gate" is a name without a plan.** It first appears in [D10](d10-roadmap-reset.md) phase R2: "P1 A09/A10 and P2 A08: re-measure, or defer to a pre-alpha gate". The user chose the deferral at the MVP exit ([M9-Q5 (a)](mvp-m9-performance-exit-contract.md#11-open-questions), 2026-11-02 11:41Z), and the [MVP exit record](../evidence/mvp-exit-2026-11-02.md#10-owed-user-actions) lists "the pre-alpha gate ... has no plan yet" as an owed action.
- **Alpha has two written conditions.** [`prototype-plan.md`](../prototype-plan.md#accepted-implementation-constraints), constraint 2: "A lower-tier GPU gate is added before alpha distribution." Its [requirement coverage table](../prototype-plan.md#requirement-coverage): "Representative mixed editor workloads and lower-tier hardware before alpha". The [MVP plan, section 1](mvp-editor-plan.md#1-goal-and-definition-of-mvp) puts lower-tier hardware after the MVP for this reason.
- **Nothing defines alpha itself** (who receives it, in what form). The requirements still say the first deliverable is an in-repository prototype, not a public package.

**Definition used here.** The pre-alpha gate is the gate the in-repository editor passes before any alpha distribution. It passes when the MVP's performance requirements hold on the reference machine, the inherited P1 and P2 performance debt is measured or closed by a recorded decision, the editor works on a lower-tier GPU, and the MVP exit's UNVERIFIED rows that can be checked are checked. What alpha distribution is (audience, packaging, licence) is not decided here (PA-Q8).

## 5. Re-entry points

- **After PA-U1.** The re-measure decides PA-U3's scope: E30 takes whatever share of PA-A01 to A04 is still missing and lies in the renderer. A share still missing that lies outside the renderer (for example a column cost PA-U1 did not remove) goes back to PA-U1 once; if it still misses, it goes to the exit card.
- **After PA-U2.** If PA-A04 still misses on long tasks that overlap the font-load change, the same rule applies to PA-U2. If PA-A01 to A04 all pass after PA-U1 and U2, PA-U3 closes E30 as "not needed for the gate" and it stays backlog.
- **After PA-U3.** If a row still misses with no remedy left in scope, the miss goes to the exit card (section 3, Gate); no new remedy item starts without the user.
- **A result within 0.1 ms of a ceiling.** The 33.3 ms reading of [MVP exit section 5.3](../evidence/mvp-exit-2026-11-02.md#53-open-reading-question-the-333-ms-ceiling) goes to the user then (PA-Q6), not before.

## 6. Exit record form (PA-U10)

`docs/evidence/pre-alpha-exit-<date>.md`, in the MVP exit record's form: verdict words (PASS, PASS with disclosure, FAIL, UNVERIFIED), one table row per PA criterion with its record link, the section 2 carried items by name, every remedy PR by number, both machines by role, the backlog after the gate, and owed user actions. It makes no claim beyond the records it cites.

## 7. Risks

- **E30 is large.** The all-visible camera encode alone is 52 to 82 ms against 33.3 ms. A full fix may need a cached or retained render path. If PA-U3's contract finds no remedy within the renderer's current design, it says so, and PA-A03 goes to the exit card.
- **A09 has had no accepted method since P1.** The PA-Q2 bound may fail only because a category cannot be measured. The record then says UNVERIFIED, not FAIL.
- **A10 depends on Windows ETW elevation**, which failed once in P1.0m. PA-Q3 keeps that failure from blocking the gate.
- **Lower-tier GPU defaults.** A laptop with two GPUs may give WebGPU either adapter. The lower-tier record names the adapter from the page's own report and runs on the integrated one.
- **Main PC contention.** Headed time is shared with other threads; the 30-minute tier 2 goal ([headed run tiers](../validation.md#headed-run-tiers)) keeps each sitting short.
