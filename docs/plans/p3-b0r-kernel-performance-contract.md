At k = 2, the initial-build budget allows t̂ ≤ 0.5 ms per path at L\* and the edit budget a p95 of 2 ms per path. Today:

The round-1 reviewer's range for the non-exact residue is 0.3-1.2 ms per path at L = 64. Section 5.4 makes the loops' work sub-quadratic in the common case: `collect_events` from all E(E − 1)/2 pairs to the box-overlapping pairs, the event sort from about n²/4 comparisons to O(n log n), the column-by-edge scans from C · E iterations to the active edges, and the section lookups from a per-candidate charge to one bulk charge. - The existing capacity `assert!`s in `fill_exact` are unreachable for validated input by the frozen width proofs. A filter decision skips an exact computation only where that computation cannot panic, so no reachable panic disappears or appears.
- Native and WASM results are identical, as today. The certificates of the [simple](p3-native-cubic-topology-contract.md), [rounded](p3-native-rounded-topology-contract.md), [transverse](p3-native-transverse-arrangement-contract.md) and [triangle-free](p3-native-triangle-free-arrangement-contract.md) topology contracts, the [rounded fill](p3-rounded-fill-mesh-contract.md) embedding and the [numeric compatibility decision](p3-private-contract.md#numeric-compatibility-decision) are therefore unchanged in meaning.

## 3. Technique 1: adaptive predicates

### 3.1 Principle

A filtered predicate first evaluates a decision procedure in binary64. If the procedure proves the result, it returns it; otherwise it calls the existing exact routine, unchanged, once. The exact routines stay in the code as the fallback and as the differential reference.

Every filter runs after the routine's existing input validation and error checks, in the same order, so error precedence is unchanged. For example, F2.5 runs only after both events are validated and each crossing has passed its `ProperCrossing` check.

Filters live at the call sites: the private helpers in `simple_cubic_topology.rs`, `fill_predicates.rs` (inside `orient2d_finite`'s callers), `fill_event_order.rs`, `fill_sections.rs` and `rounded_line_fill.rs`. The routines in `fill_exact.rs` (`multiply`, `compare_ratios`, `Signed::compare_magnitude`, `Signed::add`) are not changed by technique 1; only U1b's exact low-limb skipping (B0R-Q1, section 5.5) changes them, without changing any result. The five `p3_b0_diag` hooks stay where they are. In a B0 diagnostic run:

- the `fill_exact` counters then count only the exact work the filters could not avoid;
- the `orient2d` and `segment_relation` counters still count every top-level call, and their replayed unit costs include the filter.

### 3.2 Arithmetic facts used by every filter

Let u = 2^-53.

- **R1, outward rounding.** For a finite binary64 result r = fl(z) of one round-to-nearest operation on finite operands, `next_down(r) ≤ z ≤ next_up(r)`. Proof: z is at least as close to r as to either neighbour, so it lies within half of each gap. This also holds in the subnormal range, where rounding is gradual. If r is infinite or NaN, the filter is undecided.
- **R2, interval inclusion.** Interval addition, subtraction, multiplication and division by an interval excluding zero, on closed intervals, with each computed endpoint widened outward by R1, contain the exact result for all operands in the input intervals (Moore, _Interval Analysis_, 1966; IEEE 1788-2015 containment). Multiplication and division take the minimum and maximum of the four endpoint results.
- **R3, decision.** If an interval enclosing a real value v has a strictly positive lower endpoint, v > 0; if a strictly negative upper endpoint, v < 0. Comparisons with a threshold t decide likewise on v − t. Any NaN endpoint, an infinite endpoint, or an interval containing the threshold leaves the filter undecided. A true zero always yields an interval containing zero, so a filter never returns Equal.

### 3.3 Enclosing an exact integer

`enclose(value: Signed<N>, unit_exponent: i32) -> Option<(f64, f64)>` returns `lo ≤ value · 2^-unit_exponent ≤ hi`, or `None`.

**Invariant relied on.** Every `Signed` value the kernel builds is trimmed: `used == 0` exactly for zero, and otherwise `limbs[used − 1] != 0` (`trim`, `fill_exact.rs`; `from_finite`, `multiply`, `add`, `shift_right` and `normalize` all maintain it). The helper `debug_assert!`s it, and returns `None` rather than reading past `used` if it ever fails in release.

1. Zero gives (0, 0).
2. Otherwise read the top two used limbs as a `u128` m (one limb if `used == 1`), with e the binary exponent of the lowest limb read minus `unit_exponent`. Truncation of lower limbs gives m · 2^e ≤ |value| · 2^-unit_exponent < (m + 1) · 2^e, with m ≥ 2^64 when two limbs are read (by the invariant), so the truncation error is below 2^-64 relative.
3. Convert `m as f64` (Rust rounds `u128` to `f64` to nearest) and scale by 2^e exactly. The scaling is exact when the result is a normal finite number; it is computed by power-of-two multiplications whose intermediates lie between the start and end values, so they are normal too. Otherwise return `None`.
4. Widen by two ulps on each side: `lo = next_down(next_down(r))`, `hi = next_up(next_up(r))`, then apply the sign. Two ulps cover the truncation (below 2^-64 relative) plus the conversion rounding (half an ulp) even when r is a power of two and the gap below it is half the gap above.

Topology coordinates (`Signed<34>`) use unit exponent 1134. Plain `fill_exact` coordinates (`Signed<33>`) use 1074.

### 3.4 Ratio-unit enclosures for columns and sections

Columns (`ExactColumn`, `Signed<99>` over `Signed<66>`) and sections (`ExactSection`, `Signed<132>` over `Signed<99>`) are ratios N/W with W > 0, and `normalize` (`fill_sections.rs:194-204`) shifts N and W right by the same amount. Their units are therefore not fixed per type; only the ratio is. Every comparison in `fill_sections` treats the represented value as

value(N, W) = (N / W) · 2^-1074,

which is what `compare_column_f64` and `compare_section_f64` encode by comparing against `from_finite(v)` (unit 2^-1074) with weight one. The ratio enclosure is:

1. Let b be the bit length of W. Enclose W with unit exponent b, giving W' = W · 2^-b ∈ [1/2, 1) up to widening, and N with unit exponent b + 1074, giving N' = N · 2^-(b+1074) (section 3.3).
2. Divide the intervals (R2; W' excludes zero). The quotient encloses (N · 2^-(b+1074)) / (W · 2^-b) = (N / W) · 2^-1074 = value(N, W) directly, so it is not rescaled. Any common shift that `normalize` applied changes N and W together and leaves the quotient unchanged. If an enclosure is `None` or the quotient is not finite, the filter is undecided.

Neither step forms an intermediate outside the represented value's own magnitude, so a value inside the normal range never overflows: for example `endpoint_section(100.0)` has N = 100 · 2^1074 and W = 1 (b = 1), and N' = 100 · 2^-1 = 50, W' = 1/2, quotient 100. Step 1 must not scale N by 2^-b alone, which would leave N' near 2^1080 and overflow.

Mediant columns (`mediant`, `fill_sections.rs:50-55`) and nonvertical sections (`section_at_column`, `:57-78`) are enclosed the same way when their exact N and W exist. Section 5 also encloses them directly from their defining f64 data, without building N and W; both enclosures are valid and either may be used.

### 3.6 F1: static filter for orientation of binary64 points

Applies to every `orient2d_finite` call after F0.2: `orient2d`, `point_on_segment`, the four orientations in `segment_relation`, and through them `rounded_line_fill`, `line_fill`, `fill_intersections` and `exact_event_position`.

Compute `detleft = (ax − cx)(by − cy)`, `detright = (ay − cy)(bx − cx)`, `det = detleft − detright` in binary64. If `|det| > ccwerrboundA · (|detleft| + |detright|)` with `ccwerrboundA = (3 + 16u) · u`, the sign of `det` is the sign of the exact determinant (Shewchuk, "Adaptive Precision Floating-Point Arithmetic and Fast Robust Geometric Predicates", _Discrete & Computational Geometry_ 18(3), 1997, section 4, stage A). Only stage A is used: the existing limb accumulator replaces Shewchuk's stages B to D. The translated determinant equals the six-term expansion `orient2d_finite` evaluates, so both have the same sign.

**Guard.** Shewchuk's bound assumes that no operation overflows or underflows. F1 is used only when every input magnitude is at most 2^500 and `|detleft| + |detright|` is either 0 or at least 2^-900; otherwise the exact routine runs. The rationale, which the implementing unit writes as a code comment beside the guard:

- with inputs at most 2^500, differences are at most 2^501 and products at most 2^1002, so nothing overflows;
- a difference that falls in the subnormal range is exact (gradual underflow, Sterbenz);
- a product that underflows carries an absolute error of at most 2^-1075, which is outside the relative bound. When `|detleft| + |detright|` ≥ 2^-900, the bound itself is at least 3u · 2^-900 > 2^-955, so such errors are absorbed with a margin of more than 2^100. When the sum is 0, `det` is 0 and the exact routine runs anyway.

## 4. Technique 2: sweep-based pair candidates for topology certification

### 4.1 Scope

The three pair loops of section 1.2. Each keeps its per-pair body exactly as it is, including adjacency detection, the hull tests, the transverse certificate, the matching and triangle-free policies, and their error precedence. Only the set and order of pairs whose body runs change, and section 4.4 shows the order of everything observable stays.

### 4.2 Candidate set

For the n retained leaves of one certify call, with point sets P_i (`ExactLeaf::controls[0..4]` for the simple workspace, `RoundedExactLeaf::points[0..6]` for the others):

- **Boxes.** B_i is the box spanned by the enclosures (3.3) of all coordinates in P_i: `xlo_i` the minimum of their lower endpoints, `xhi_i` the maximum of their upper endpoints, and so on. It contains conv(P_i), which contains the leaf's hull.
- **Forced pairs.** F holds every pair in the same contour whose `contour_leaf` values differ by one, or are 0 and `count − 1`. It is a superset of the pairs on which `adjacent_shared_point` or `directed_rounded_adjacent` returns `Some`.
- **Candidates.** C = F ∪ { (i, j) : i < j, B_i and B_j overlap as closed boxes }. Two boxes overlap when `xlo_i ≤ xhi_j`, `xlo_j ≤ xhi_i` and the same for y.
- If a box cannot be formed because an enclosure is `None`, every pair containing that leaf is a candidate.

**Lemma A.** For (i, j) ∉ C, the current body returns without error and without changing any state other than the pair counter. Proof: the pair is not forced, so it is not adjacent and the body evaluates `closed_hulls_intersect` on the two hulls. The boxes are separated along an axis, so the hulls are disjoint. `closed_hulls_intersect` returns `true` only when it finds a common point (a segment intersection or a hull point inside the other closed hull), so it returns `false`. The simple and rounded bodies then continue; the transverse body yields `None` and continues.

### 4.3 Sweep

1. Compute the n boxes (n ≤ 64; 2 KiB of stack).
2. Sort the leaf indices by `xlo` with a deterministic allocation-free sort into a `[u8; 64]` stack array. Insertion sort is acceptable at n ≤ 64. Tie order does not matter, because the output is a set.
3. For each leaf a in sorted order, scan the following leaves b while `xlo_b ≤ xhi_a`, and mark (min(a, b), max(a, b)) when the y ranges also overlap.
4. Mark every forced pair.
5. The marks are a `[u64; 64]` stack bitset, row i holding bit j for j > i.

Cost: O(n log n + K_x), with K_x the number of x-overlapping pairs, plus O(n + K) to read the bitset with `trailing_zeros`. The worst case, in which every box overlaps every other, gives K = n(n − 1)/2: every body runs as it does today, plus O(n²) bit operations. Correctness never depends on K.

### 4.4 Processing order and logical pair counter

Candidates are processed in lexicographic (i, j) order by reading the bitset rows in order. This is the order of the current loops restricted to C, so the matching partners, the triangle-free crossing prefix and the crossing records are built in the same order, with the same `left_leaf < right_leaf` identities.

With T = n(n − 1)/2 and rank(i, j) = i(2n − i − 1)/2 + (j − i − 1), the pair counter of the current loop is emulated:

```text
for (i, j) in C, lexicographic:
    p = rank(i, j)
    if p >= max_pairs: pairs = max_pairs; return WorkLimit
    pairs = p + 1
    body(i, j)?              // unchanged; may return Unresolved or WorkLimit
if T > max_pairs: pairs = max_pairs; return WorkLimit
pairs = T
```

**Lemma B.** This returns the same result and the same `pairs`, success or failure, as the current loop. Proof: by Lemma A, the current loop's behaviour on a non-candidate pair is the counter check and increment only. If its first body failure is at rank p_f < max_pairs, both versions fail there with `pairs = p_f + 1`. If none occurs below max_pairs and T > max_pairs, both return `WorkLimit` with `pairs = max_pairs`. Otherwise both finish with `pairs = T`. Bodies at ranks ≥ max_pairs run in neither.

### 4.5 Which pairs still need exact checks

- **Forced pairs:** always inspected. The simple workspace's `hull_intersection_is_only` meets exact zeros at the shared knot (F0.1); rounded and transverse workspaces evaluate `rounded_projected_monotone` with F2.2.
- **Box-overlap pairs:** `closed_hulls_intersect` through filtered `orient` (F2.1). Hulls that touch or have collinear edges give exact zeros, which fall back.
- **Transverse crossing pairs:** the full borrowed certificate, through F2.1, F2.4 and the endpoint sweeps.

### 4.6 Unchanged parts of the topology stage

`build_leaves` (restriction, hulls; its `orient` and `compare_points` calls use F2), the knot preflight, `validate_minimum_leaves` and `derive_output` (O(C · n) polygon classification) keep their structure.

### 5.4 Loop restructuring (B0R-Q3 (a))

**Lemma C, bulk charge.** Let `bulk_charge(m)` do: if `work_units + m > max_work`, set `work_units = max_work` and return `WorkLimit`; otherwise add m. It is equivalent to m consecutive `charge()` calls with nothing in between: each call fails exactly when `work_units ≥ max_work`, so the sequence fails if and only if `work_units + m > max_work`, and a failing sequence leaves `work_units = max_work`. A counted variant also adds to a second counter the number of calls that would have succeeded, min(m, `max_work − work_units`).

**Corollary C1, sparse charged scan.** Take a loop `for k in 0..n { charge()?; body_k }` in which `body_k` has no effect (no state change, no error, no charge) for k outside a set A, and for k in A may change state, charge internally or fail. It is equivalent to:

```text
o = 0
for k in A, ascending:
    bulk_charge(k - o + 1)?   // the outer charges of iterations o..=k
    body_k                    // unchanged, including its own charges
    o = k + 1
bulk_charge(n - o)?
```

Proof: between two consecutive members of A, the original performs only outer charges, which Lemma C replaces exactly; each `body_k` runs at the same `work_units`, in the same order and with the same state.

**Lemma D, insertion-sort charge count.** The current stable insertion sort (`sort_events`, `:734-749`) charges once per comparison and shifts only on Greater. For the element at index i ≥ 1, let g_i be the number of earlier elements, in the input order, strictly greater than it. Inserting it makes g_i shifting comparisons, plus one stopping comparison unless all i earlier elements are greater. The total is C = Σ g_i + (n − 1) − m, where m counts the indices i ≥ 1 whose element is strictly less than every earlier element. The comparator (exact x comparison) is a total preorder, so the stable sorted order is unique and any stable sort gives the same permutation.

### 6.2 Frozen clauses this contract amends

These clauses describe how the current code computes. B0R changes that while keeping their observable semantics by section 2. Each unit that touches a clause adds a one-line dated pointer to B0R under the amended contract's status line and changes nothing else there.

**Why a filter with exact fallback is neither a "retry" nor a "rounded determinant".** In these contracts a retry means repeating or extending a computation after a failure, with growing precision, a new subdivision or a relaxed tolerance, so that the outcome can depend on the attempt. Here the filter never fails an operation and never feeds the exact path: when undecided, the unchanged exact routine runs once on the same inputs, and the returned value is a function of the inputs identical to the exact routine's. A rounded determinant means using a rounded value as the answer; here a rounded value is used only as a proof of a sign or comparison that it encloses, and the answer is always the exact one.

## 12. Risks

- **Still INFEASIBLE (plausible).** Then the user receives: the new record and the old/new comparison; the new stage split and residual cost drivers by code location (expected: the `embed_scalar` bisections, the small per-column sorts that B0R keeps, remaining exact fallbacks and the topology's forced pairs); and the gap to each budget. B0R recommends no remedy; options such as cap-aware algorithms beyond B0R, worker parallelism or a different tessellation architecture are decisions for the user.
- **INCONCLUSIVE.** Shorter per-path times make fits noisier relative to their values, so check 2 (prediction factor ≤ 2) or check 4 (linearity) can fail. Under B0-Q3 that goes to the user like INFEASIBLE. B0R does not tune the sweep or sampling to avoid it.
- **Filter unsoundness.** A subtle error in conversion, widening, ratio units or a guard would break exactness silently. Mitigations: soundness rests on R1 to R3 and the stated identities only; O1, O2, O4 and O10 compare with the exact routines and with `main`; O8 shows the oracles detect seeded defects; two independent reviews. A mismatch found after merge is a B3 defect and the unit is reverted.
- **Lazy-value errors.** T1 and T5 move when values are built. Shadow mode (O10), the sentinel's impossibility argument and the T5 consumer rule cover it; a missed path would show as an O4 difference.
- **Charge-emulation errors.** An off-by-one in Corollary C1 or Lemma D changes `work_units` only near `WorkLimit` or in the counters, which ordinary paths may not reveal. O10 compares every restructured loop with its reference copy on every case, O11 drives the budgets to every failure point, and O8 seeds the likely off-by-one defects.
