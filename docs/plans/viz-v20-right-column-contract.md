## 1. Problem

With `ui=1`, the v2 scenarios of the [M9-U2 record](../evidence/m9/u2-89393f1.md) miss: stress 83.2 to 83.4 ms against v1's 16.8 ms with equal encode, typical view 33.4 ms, pointer latency 518.6 to 1,347.9 ms. The [diagnostic traces](../evidence/m9/u3a-trace-3fd3be9.md) show stress v2 spending about 6.0 s of a 10 s window in microtasks (v1: 0.3 s) and 2.4 s in layout, pre-paint and paint (v1: 0.24 s). They are not evidence, and the column's share has not been separated by measurement.

## 2. Cause, from the code at `ecfd0f5`

These are code facts. That they explain the misses is the hypothesis section 6 tests.

- **The host re-renders on every editor event.** `Surface` in `apps/next-host/app/page.tsx` reads the whole snapshot (`useEditorSelector((value) => value)`), and its comment says it "re-renders on every editor change". A camera step is an editor event.
- **Nothing stops that render at the column.** `Surface` renders `<CanvasSide>` (`apps/next-host/src/m8-layout.tsx`, props `bench` and `height`, a boolean and a number). That renders `LayerTree`, `PropertyPanel` and `EditorPanels`, none of them memoized. `setViewport` replaces only `snapshot.viewport`, and no column component reads the viewport, so the column's own selectors do not change on a camera step: the renders come from `Surface` alone.
- **The layer tree renders every row.** `LayerTree` (`packages/ui/src/layers.tsx`) calls `layerRows` on every render. That walks the active page's top level and every expanded container, building a new row object per node, and mounts one `li` per row (two or three buttons and a `span`). The stress document has 10,000 rows, about 40,000 elements. The mixed v2 document has 655 rows with clusters f1 and g3 expanded (the M9 harness's count).
- **A drag step changes the document,** so the tree and the property panel re-render on every step of the edit drag. The panel's re-render is legitimate (it shows the moving Y); re-rendering every row is not.

## 4. Behavior change (M8-L3 and L4 amendment)

With L3, a row scrolled out of the list's viewport is not in the DOM. What the user sees is unchanged: the same height, scroll range, order, indentation and controls. M8-L3 and L4 are amended to say so. Rules:

- **Row height.** Every row has one fixed CSS height, measured once from the first mounted row (V20-Q2). Before the measurement, and when there is no layout (`renderToString`), the list mounts its first 32 rows unpositioned. An empty page has no rows and measures nothing.
- **Scrolling.** The rows in view always equal an unwindowed list scrolled to the same offset, including after expand, collapse, rename and selection changes. Expand and collapse keep the list's `scrollTop`; the browser clamps it if the range shrinks.
- **Pinned rows.** A row whose rename textbox is open (M8-L4), and a row that contains the focused element, stay mounted at their own position while scrolled out of view. A blur still commits once, and focus never falls to `body` because of scrolling.
- **Keyboard.** Tab and Shift+Tab reach every row in order, as today: focus on a control of an edge row scrolls the list so that the next row is mounted before the next Tab.
- **Accessibility.** The list keeps `aria-label="layer list"`. Each mounted row carries `aria-setsize` (the row count) and `aria-posinset` (its 1-based position).
- **Selection from the canvas** does not scroll the list, as today (V20-Q3).
- **Tests that depend on every row in the DOM** change as V20-U2 lists: the E26/M9 harness's row count (`tests/e26/e26-harness.spec.ts`, which counts `li` elements and expects 655 or 10,000) reads `aria-setsize` instead. Its clicks on `layer-toggle-f1` and `layer-toggle-g3` scroll the list to the row first. The m8-u4 unit markup test's list wrapper markup changes; its rows do not, since its fixture has fewer than 32 rows. The m8-next-host `layerOrder` checks and the m4-next-host layer steps use small fixtures inside one viewport and stay as they are.

## 9. Risks

- **Comparisons with M9-U2 move.** L1 also memoizes the `ui=0` bench aside, so the v1 control rows and the `ui=0` variant can change against M9-U2 for a reason outside the column. The V20-U3 record states this next to each comparison.
- **The walk stays.** On the drag, `layerRows` still walks the page on each step. If V20-U3 shows a remaining column share, a structural cache (keyed on the page's child lists) is the next lever, in this item.
- **Memo correctness.** A row memo that misses an input shows stale state or sends a stale command. V20-A03 and A04 test both.
- **The column may not be the whole story.** If the `ui=0` variant also misses at the V20-U2 head, the remainder goes to E30 or V-21 under the pre-alpha plan, not here.
