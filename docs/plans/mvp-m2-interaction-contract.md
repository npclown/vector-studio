## 1. Scope

In scope: zoom and pan (wheel and pinch zoom about the pointer, Space-drag, middle-drag and scroll pan, zoom to fit, to selection and to 100%); a rotate gesture with Shift snapping to 15°; snapping to object and frame edges and centres, equal spacing and rotation angles with a snap overlay in session state; align and distribute; layer ordering; Alt-drag duplication and a duplicate command; keyboard nudging; overlap-selection cycling; frame-entry editing; clipboard copy, cut and paste with fresh IDs; a configurable keymap; extension tools and bindings; a next-host page and headed spec.

Out of scope: schema changes (M2 adds no persisted field, so no migration); adopting nodes into a frame on drop (M2-Q10); path edit mode on double-click of a path (M3); plain-text paste (M6); panels (M8); viewport persistence (requirements: zoom is not restored; M5 restores content and page only); pointer-priority scheduling, the 10,000-node mixed workload and the M1-A13 isolation cost, which are rendering item [E26](d9-rendering-track.md#items) (R-P), not M2. Performance note (no gate): M1-A13 observed about 77 ms per gesture update on a 10,000-node page, and snapping adds a candidate scan per update; M2 makes no performance claim.

### 1.1 Starting point (main at c83243d)

- **Input.** `input` carries `pointerdown`, `pointermove`, `pointerup` with a page-space `point` and `keydown` with `key`, each with `modifiers`, to the active tool only, and always returns `{ ok: true, ids: [] }` for a well-formed event. `EditorCanvas` maps `page = camera.position + css / zoom` with the rendered viewport, forwards the primary button only, ignores moves without a press, and turns `pointercancel` into a synthesized Escape `keydown`. There is no wheel, key-up, double-click or keymap; undo and group are toolbar buttons in next-host.
- **Session.** Selection, active page, tool (`ToolName`, a closed union of six built-in tools), viewport (`RenderCamera`, `position` is the page point at the canvas's top-left, `zoom` CSS px per page unit, set only by `setViewport`) and overlay (`marquee`, `path`).
- **Tools and gestures.** `tools.ts` holds the box, line, path and select tools; `Tool` and the gesture API are package-internal (`internalsOf`). A gesture update (`editor.ts`, `updateGesture`) applies its command to the **live** document, so updates accumulate; only `setFrames` of a container restores the container's subtree from the pre-gesture state (`resizeBase`, `edits.ts`), and `GestureControl.edit` applies `map` edits from the pre-gesture state. The select tool sets the selection at press (`pointerDown`). `hit-test.ts` has `deepestHit`, `selectionTarget` (page or top-level frame), `marqueeHits`, `boundsOf`.
- **Extensions.** `Extension = { id, nodeTypes?, commands? }`; `ExtensionApi` is `execute` and `query`; IDs are namespaced by the extension ID and conflicts throw at `createEditor`.

## 2. Input and session state

- **M2-I1 input kinds.** `InputEvent` gains `keyup { key, code?, modifiers }`, `wheel { point, deltaX, deltaY, modifiers }` (CSS px; the host converts `deltaMode` line to 16 px and page to the canvas height), `doubleclick { point, modifiers }` (from the DOM `dblclick`) and `pointercancel { modifiers }`. `keydown` gains optional `code` (`KeyboardEvent.code`), `repeat` and `composing` (`isComposing`), each default false or absent; `pointerdown` gains optional `button` (0 primary, 1 middle; default 0; other buttons are ignored, unconsumed). A malformed event stays `editor.invalid-command` at `/event`. Points stay page-space (M2-Q1).
- **M2-I2 dispatch order.** For each `input`: (1) navigation (section 3) takes wheel events, Space `keydown`/`keyup`, middle-button drags and drags begun while Space is held; (2) `pointercancel` ends a pan, cancels an active gesture and resets the active tool, and never reaches the keymap; (3) during an active gesture every other event goes to the active tool only; (4) a `keydown` goes to the active tool first and, if the tool does not consume it, to the keymap (section 7); a `keyup` other than Space goes to the tool only; (5) `doubleclick` and pointer events go to the tool. A tool consumes a key when it has state the key acts on (Escape during a drag, Escape or Enter with pending path anchors).
- **M2-I3 consumed signal.** `CommandResult` gains an optional `consumed: boolean`, present only on `input` results. When a binding ran, `input` returns the action's result plus `consumed: true`, also when the action failed (for example `undo` with an empty history gives `{ ok: false, code: 'editor.nothing-to-undo', consumed: true }`) or did nothing (`selectAll` on an empty page gives `{ ok: true, ids: [], consumed: true }`). A key the tool or navigation consumed gives `{ ok: true, ids: [], consumed: true }`; an unbound, unconsumed key gives `consumed: false`. Pointer, wheel, double-click and cancel events report `consumed: true` when navigation or the tool acted on them, else false. A malformed event has no `consumed`.
- **M2-I4 `EditorCanvas`** forwards wheel (a non-passive listener; `preventDefault` when `consumed`, so Ctrl+wheel and pinch do not zoom the browser page), middle-button presses (with `preventDefault`, so Windows autoscroll does not start), `keyup`, `dblclick`, `code`, `repeat`, `isComposing` and `pointercancel` (replacing the synthesized Escape); the canvas and the hidden clipboard sink (section 6), when there is one, are one focus target: focus moving between them is not a blur, and when focus leaves the target or the window blurs it sends `pointercancel` and a Space `keyup`, so a lost key-up cannot leave Space held. It sends `setViewportSize` on mount and resize, maps points with `editor.getSnapshot().viewport` at event time (not the rendered value, so a pan never reads a stale camera), and calls `preventDefault` on a key event only when `consumed` is true.
- **New session state** (never history, never serialized, read through queries and `EditorSnapshot`; a change raises a `session` event with the field name): `viewportSize` (`{ width, height }` CSS px or null), `scope` (section 5), `snap` (the snap overlay, section 4.2), `snapping` (boolean, default true), `keymap` (section 7). The in-memory clipboard (section 6) is session state without a snapshot field or event; it survives loads and page switches, while `loadDocument` clears `scope` and `snap`. A session command that leaves its value unchanged succeeds and raises no event. **Cancel restores the selection:** the editor records the selection when a gesture begins, and when the gesture is cancelled (Escape, `pointercancel`, or a command that interrupts it) it restores that selection, filtered to nodes that exist on the active page, so a cancelled Alt-drag leaves the originals selected.

## 3. Viewport

The camera stays session state in `editor-core` (`viewport`), outside the document and history, and is not persisted in M2 or later in the MVP (requirements, Persistence). Every viewport change goes through the same path as `setViewport` (renderer `setCamera`, `editor.invalid-camera` leaves it unchanged); a computed camera equal to the current one (for example a wheel zoom at the clamp) sends nothing and raises no event. `zoom` is clamped to `[ZOOM_MIN, ZOOM_MAX] = [1/64, 256]` (M2-Q2).

- **Zoom about a point.** For a page point `p` and new zoom `z1` from `z0`: `position1 = p − (p − position0) · (z0 / z1)`, so `p` stays under the same screen pixel. Commands: `setViewportSize { width, height }` (finite, > 0, else `editor.invalid-command`); `zoomBy { factor, about? }` (factor finite > 0; `about` defaults to the viewport centre `position + size / (2·zoom)`, which needs a size, else `editor.no-viewport-size`); `zoomTo { target: 'fit' | 'selection' | 'actual' }` (needs a size, else `editor.no-viewport-size`).
- **Wheel.** With `ctrl` or `meta` (a mouse Ctrl+wheel, or a trackpad pinch, which Chrome and Edge report as Ctrl+wheel): `z1 = clamp(z0 · 2^(−deltaY / 100))` about the event point. Otherwise it pans: `position += (deltaX, deltaY) / zoom`, and with `shift` and `deltaX = 0` the vertical delta pans horizontally.
- **Drag pan.** A drag with button 1, or with button 0 while Space is held (a `keydown` with `key ' '` sets the hold, a Space `keyup` or `pointercancel` clears it; Space events are consumed by navigation, never the tool or keymap), is a pan: at press it records the grabbed page point `g`; each move with point `q` sets `position += g − q`, so `g` stays under the pointer. A pan is not a gesture, creates no history and ends at `pointerup` or `pointercancel`; Space pressed during a tool gesture starts no pan until that gesture ends.
- **Zoom targets.** `actual`: zoom 1 about the viewport centre. `fit` (`boundsOf` the visible children of the active page) and `selection` (`boundsOf` the selection): with bounds `b` and size `(W, H)`, `z = clamp(min((W − 64) / b.width, (H − 64) / b.height))` over the axes of nonzero size (both zero keeps the zoom; a size of 64 or less on an axis uses `W` or `H` itself), then `position = centre(b) − (W, H) / (2z)`. No bounds is a success with no change. Keymap actions `zoomIn` and `zoomOut` are `zoomBy` 2 and 0.5.

## 4. Commands and editing rules

All new document commands are one transaction each with byte-identical undo (P5 snapshots), apply the M1 group refit (M1 section 4.2) and clip and tree depth rules, and act on nodes of the active page at any depth (`editor.unknown-node` otherwise). An empty `ids` list is `editor.invalid-command` at `/ids`; listed IDs follow the M1 selection rule (a listed descendant of a listed node is ignored). A command that would change nothing returns `{ ok: true, ids: [] }` and records no step and no event. Arrange commands work in **page space**: a node's box is the page-aligned bounds of its rotated frame (`boundsOf`), and its move is a page vector rotated into its parent space (the move drag's rule), so nodes of different parents mix freely.

**Gestures (S1).** M2 names two gesture updates. `update(command)` keeps the P5 and M1 meaning (applied to the live document; absolute commands such as creation and `setFrames`). `replace(commands)` (new) restores the pre-gesture document, then applies the listed commands in order, and the result replaces the live document, discarding the effects of every earlier `update` and `replace` in the same gesture; each relative command (`rotateNodes`, `nudgeNodes`, `alignNodes`, `distributeNodes`, `reorderNodes`) inside a gesture must use `replace`, and passing one to `update` fails with `editor.invalid-command`, so a drag never compounds. A creating command (`duplicateNodes`, `paste`, creation) draws IDs on every application, so tools issue it once through `update` and then move by absolute `setFrames`.

### 4.1 Rotation

- `rotateNodes { ids, angle, pivot? }`: rotates by `angle` (radians, clockwise, finite) about the page point `pivot`, by default the centre of the `handles` box (M1 section 7). For each node: its page rotation becomes `normalize(θ + angle)` and its stored rotation that minus its parent chain's (M1-S1 normalization); its frame centre maps by the rotation about the pivot in page space and back into its parent space; size is unchanged. **Rule:** when one node is listed and `pivot` is omitted, the node's `x` and `y` are kept as stored (not recomputed). Containers rotate rigidly (children are parent-local, unchanged); ancestors refit.
- **Rotate gesture** (select tool). Press precedence: an active resize handle within 6 / zoom of the press wins; else the **rotate zone**, a press strictly outside the handle box (in the box's own axes) within `18 / zoom` page units of one of its four corners; else a node hit; else the marquee. The M1-U4 small-box rule still applies first: on a box narrower than 24 / zoom on an axis, a press inside the box on a selected node moves it. The rotate gesture fixes the pivot at the handle-box centre at press and, on each move to `q`, issues `replace([rotateNodes { ids: selection, angle: a, pivot }])` with `a = wrap(atan2(q − pivot) − atan2(press − pivot))`, `wrap` into (−π, π]. With Shift: for one node, `k = Math.round(θ' / (Math.PI / 12))` (halves round towards +∞, as `Math.round`) on its resulting page rotation `θ'`, and `a` is adjusted so the result is `normalize(k · (Math.PI / 12))`; for several nodes, `a` itself is rounded the same way. Without Shift and with snapping on, rotation-angle snapping applies (section 4.2). One gesture is one undo step; Escape or `pointercancel` cancels.

### 4.2 Snapping

Snapping applies to the select tool's move, its resize when the handle box is page-aligned (M1 modes `p5` and `map`, and a `single` box whose page rotation normalizes to 0), the rectangle, ellipse and frame tools' dragged corner, the line tool's endpoint, and the rotate gesture for one node. It is on when `snapping` is true and neither `ctrl` nor `meta` is held (M2-Q6); `setSnapping { enabled }` is a session command. All rules are in `editor-core` (MVP-Q7) and run in page space, with every result applied to each node through its parent space as a page vector.

- **Candidates.** With the scope owner `S` (the scope node, or the active page): the children of `S`; the children of every frame that is a child of the active page; and every frame that is an ancestor of a moving node. Excluded: moving nodes, their descendants, their group and mask-group ancestors (whose boxes follow them), mask sources (not hittable, M1 section 6), and nodes not visible through their ancestors. **Candidate order** is document pre-order of the active page. Each candidate's box `K` is its page-aligned bounds in the pre-gesture document, with x values `K.left`, `K.cx`, `K.right` and y values `K.top`, `K.cy`, `K.bottom`. Moving nodes of different parents use the same set.
- **Threshold.** `T = SNAP_PX / zoom` page units with `SNAP_PX = 6`, independent per axis.
- **Moving values.** `B` is the page-aligned bounds of the moving nodes in the pre-gesture document translated by the raw delta. A move offers `B.left`, `B.cx`, `B.right` (indices 0, 1, 2) and the y analogues; a resize only the edges the handle moves; a point (box corner, line end) only itself.
- **Align offers.** Every pair (moving value `m`, candidate value `c`) with `|c − m| ≤ T` is an offer `o = c − m`.
- **Spacing offers** (move only), along x: `R` is the candidates whose closed y range overlaps `B`'s (`K.top ≤ B.bottom` and `B.top ≤ K.bottom`), sorted by `(left, right, candidate order)`. The reference gaps `G` are `D.left − C.right` for each consecutive pair `(C, D)` of `R` where that value is > 0 (overlapping or nested pairs give none). `A ∈ R` is left of `B` when `A.right ≤ B.left`, right of `B` when `A.left ≥ B.right`. Only the nearest neighbours offer: the left candidate `A` with the greatest `right` and the right candidate `E` with the least `left` (ties to the earlier in candidate order). Offers: `o = A.right + g − B.left` and `o = E.left − g − B.right` for each `g ∈ G`; and, when both exist, centring `o = (A.right + E.left) / 2 − B.cx`. Only offers with `|o| ≤ T` count. Likewise for y.
- **Choice.** Per axis, the offer with the least `|o|` wins; ties go to align offers before spacing offers before centring, then (align) the lesser candidate value, then the lesser moving index, then candidate order; (spacing) the lesser target value (`B.left` or `B.right` after the offer), then the lesser `g`. The axis delta becomes raw + `o`. **Example:** candidates `[0, 10]`, `[20, 30]`, `[25, 35]` (x ranges, all overlapping `B` in y), `B = [41, 51]`, zoom 1 (`T = 6`): the align offer is `c = 35, m = 41` (`o = −6`); `G = {10}` (from `[0, 10]` and `[20, 30]`; `[20, 30]` and `[25, 35]` overlap); the nearest left neighbour is `[25, 35]` and there is no right one, so the only spacing offer is `o = 35 + 10 − 41 = 4`; the winner is `o = 4` (`B' = [45, 55]`), with gaps `10 → 20` and `35 → 45`.
- **Rotation angles.** For a one-node rotation without Shift, with `r = |q − pivot|` (no angle snap when `r = 0`), the resulting page rotation `θ'` snaps to the nearest target among the multiples of `Math.PI / 2` and the candidates' page rotations, when `|wrap(target − θ')| ≤ T / r`; ties go to a multiple of `Math.PI / 2`, then the lesser normalized target, then candidate order.
- **Snap overlay.** `snap: SnapOverlay | null`, query `{ type: 'snap' }`: `{ guides: Segment[]; gaps: Segment[]; angle: number | null }` with `Segment = { a: PagePoint; b: PagePoint }` in page space. With `B'` the snapped box and `ε(v) = 1e-9 · max(1, |v|)`: when an axis snapped by an align offer, a guide for each distinct value `v` where some moving value of `B'` equals some candidate value within `ε(v)`; for x, `a = (v, min(B'.top, K.top))`, `b = (v, max(B'.bottom, K.bottom))` over all such candidates `K`; y alike with x and y swapped. When an axis snapped by a spacing offer with gap `g`, `gaps` lists the consecutive pairs of `R` (sorted as above) whose gap equals `g` within `ε(g)`, in sorted order, then the gap between `B'` and the neighbour that made the offer; for a centring offer, the gaps `A → B'` and `B' → E`. Each gap runs from `(left box right, y)` to `(right box left, y)` with `y` the midpoint of the two boxes' common y range (x and y swapped for y). Order: x guides by `v`, then y guides by `v`; x gaps, then y gaps, each in sorted order. `angle` is the resulting page rotation when a one-node rotation snapped (angle snap or Shift step), the snapped `a` for a several-node Shift rotation, else null. The overlay is null when nothing snapped and is cleared when the gesture commits or cancels. Snapping changes only update values, so each gesture stays one undo step.

### 4.3 Arrange

- **Align.** `alignNodes { ids, edge: 'left' | 'hcenter' | 'right' | 'top' | 'vcenter' | 'bottom' }`. The target is the union of the nodes' boxes; for one node it is the page-aligned bounds of its nearest frame ancestor (one node without one changes nothing). Each node moves by a page translation so its box's edge or centre equals the target's: a page-root node with rotation 0 sets `x` (or `y`) exactly to `target.x`, `target.x + target.width / 2 − w / 2` or `target.x + target.width − w`; any other node moves by the difference of its box's value from the target's.
- **Distribute.** `distributeNodes { ids, axis: 'horizontal' | 'vertical' }`: at least 3 nodes (`editor.too-few-nodes`). Nodes sort by box centre on the axis, ties by document pre-order; the first and last stay; with span `S = last.max − first.min` and `gap = (S − Σ sizes) / (n − 1)`, the sizes summed in sorted order and `gap` possibly negative, each next box's min is the previous box's (new) max plus `gap`, in sorted order.
- **Order.** `reorderNodes { ids, op: 'forward' | 'backward' | 'front' | 'back' }`, within each node's own parent (the last child is on top, P5; several parents are handled independently). `front` and `back` move the listed children to the top or bottom in their current relative order; `forward` moves each maximal run of listed children above the next unlisted sibling above it, `backward` below the next unlisted sibling below it, so runs never pass each other. A result that leaves a `maskGroup` with a non-path first child fails with `editor.invalid-mask-source`.
- **Nudge.** `nudgeNodes { ids, dx, dy }` (page units, finite): each node moves by the page vector `(dx, dy)` rotated into its parent space; a page-root node sets `x + dx`, `y + dy` exactly. The keymap's arrow actions use 1 and, with Shift, 10 page units, independent of zoom (MVP-Q8); each key press, auto-repeat included, is one step (M2-Q9).
- **Duplicate.** `duplicateNodes { ids, offset? }` copies each subtree with fresh IDs into the same parent directly above its original (originals of one parent keep their relative order, each copy above the topmost original of that parent), then moves the copies by the page `offset` (default `{ x: 0, y: 0 }`, M2-Q12). It returns the copies' root IDs in paint order and does not change the selection. Custom nodes keep `customType` and `data` and are re-validated. Duplicates never change clip or tree depth.
- **ID order (S8).** A creating M2 command (`duplicateNodes`, `paste`) runs every check (shape, references, custom validation, clip and tree depth) before it draws any ID, so a failed command draws none (the M1-U2 note 1 precedent); it then draws IDs root by root in paint order, each subtree in pre-order (a container before its children, in `children` order).
- **Alt-drag.** A select-tool press with `alt` defers any selection change. On the first movement, the move set is the selection if the pressed target is selected, else the target; the tool issues `update(duplicateNodes { ids: moveSet })`, selects the copies and moves them by `setFrames` from their duplicated frames; the originals stay; commit is one undo step holding both. Escape or `pointercancel` restores the pre-gesture document and the pre-press selection (the originals); drawn IDs are not returned to the source. A release without movement is overlap cycling (section 5).

### 4.4 Failure codes

New codes, added to `EditorErrorCode` and accepted from extension results:

| Code | When |
| --- | --- |
| `editor.no-viewport-size` | `zoomTo`, or `zoomBy` without `about`, before `setViewportSize` |
| `editor.too-few-nodes` | `distributeNodes` with fewer than 3 nodes |
| `editor.invalid-scope` | `setScope` to a node of the active page that is not a container |
| `editor.invalid-keymap` | A malformed binding or chord, an unknown action, a duplicate chord in one layer (section 7), with a path |
| `editor.empty-clipboard` | `paste` without `text` and an empty in-memory clipboard |
| `editor.invalid-clipboard` | Marked text whose fragment fails its rules (section 6), with a fragment path |
| `editor.unsupported-clipboard` | Text without the marker, the empty string included (plain-text paste is M6) |

`setScope` with an unknown ID or a node of another page is `editor.unknown-node`; `setTool` with an unregistered ID stays `editor.unknown-tool`. When several rules fail, the first in this order wins: `editor.invalid-command` (shape, empty `ids`, a relative command in `update`), `editor.unknown-node`, `editor.unknown-tool`, `editor.invalid-scope`, `editor.invalid-keymap`, `editor.no-viewport-size`, `editor.too-few-nodes`, `editor.empty-clipboard`, `editor.unsupported-clipboard`, `editor.invalid-clipboard`, the model and M1 codes in the M1 section 4.3.1 order (`document.invalid-field`, tree depth included, first, then the `editor.*` structural codes in that table's order, so `editor.invalid-mask-source` before `editor.clip-depth`), and `editor.duplicate-id` last, when IDs are drawn.

## 5. Selection modes

- **Scope.** `scope: string | null` names an entered container (group, mask group or frame) of the active page; `setScope { id | null }` is a session command. The M1 selection target rule applies with the scope in place of the page: a hit's target is its outermost ancestor below the scope (inside a scope, a frame child does not act as an artboard), and the marquee's candidates are the scope's children (a frame child is selected when contained, as M1). A hit on the scope node itself (a scoped frame's background or border) counts as empty canvas inside the scope: a drag starts the scope's marquee, a click clears the selection, and the scope stays. A press whose hit is outside the scope's subtree, or on empty page canvas, sets the scope to null and applies the M1 rule. The scope becomes null on a page switch, a load, and when the scoped node is deleted or undone away.
- **Frame entry.** A `doubleclick` with the select tool enters the container under the point: when the hit target is a group, mask group or frame, the scope becomes that target and the selection becomes the next node down the hit chain (its child on the chain), or empty when the hit is the frame's own background or border; a top-level frame's background double-click scopes that frame with an empty selection. A double-click on a leaf target does nothing in M2 (path editing is M3). Action `exitScope` (Escape): with a scope, select the scope node and set the scope to its nearest container ancestor that is not a top-level frame (null at the page); without one, clear the selection. `enterScope` (Enter) enters a single selected container and selects its children.
- **Overlap cycling.** An `alt` press released without movement (the select tool; the press changed nothing, section 4.3): the stack is the selection targets of every node hit at the point, in reverse paint order without repeats; with the pre-press selection one node at index `i` of the stack, the selection becomes item `(i + 1) mod n`, else item 0 (M2-Q5). Four overlapping nodes reach every node in four clicks.

## 6. Clipboard (MVP-Q6)

- **Fragment.** `copy { ids? }` (session; default the selection) serializes the listed subtrees as the text `vector-studio/fragment` + `\n` + compact JSON (no whitespace, no trailing newline) of `{ fragmentVersion: 1, schemaVersion: 2, roots: string[], nodes: Record<string, NodeV2> }`, with the top-level keys in exactly that order and the `nodes` entries and node keys sorted as `serializeDocument`. A copy or cut with an empty selection changes nothing and is not consumed, so `EditorCanvas` leaves the DOM clipboard event untouched. `roots` are in document paint order (pre-order of the page tree), not selection order; each root's frame and rotation are converted to page space and its `parent` is `""` — a **fragment exception**: the empty parent is valid only for a fragment root, which is never a document node. The text becomes the in-memory clipboard; query `{ type: 'clipboard' }` returns it or null. `cut { ids? }` is copy plus `deleteNodes` as one transaction; a failed cut changes neither the document nor the clipboard.
- **Paste.** `paste { text?, at? }`: with `text`, a marked text is parsed with the model's JSON and node rules plus the fragment rules (marker exact, `fragmentVersion` 1, every listed node reachable from exactly one root once, no cycles, root parents `""`, non-root parents and `children` consistent, then each custom node's `validate`); a failure is `editor.invalid-clipboard` or the model's code, with a fragment path, and nothing is created. Unmarked text (the empty string included) is `editor.unsupported-clipboard`. Only when `text` is omitted is the in-memory clipboard used. The target parent is the scope if set, else the single selected node if it is a `frame`, else the active page; roots go on top in fragment order with page placement mapped into the target's space; `at` moves the roots' joint page bounds centre to that point. IDs follow section 4.3 (all checks, including `editor.clip-depth` and tree depth in the target, before any ID is drawn). One transaction; the pasted roots become the selection.
- **Host.** `EditorCanvas` listens for the DOM `copy`, `cut` and `paste` events while the canvas has focus, runs `copy`, `cut` or `paste { text }` (always passing `text`, the empty string when the clipboard has no `text/plain`) and writes or reads `text/plain` through `clipboardData`, so the browser's Ctrl+C, X and V use the system clipboard without a permission prompt. Whether Chrome and Edge fire these events on a focused, non-editable `<canvas>` is unverified: M2-U6 probes it headed first and records which path shipped; if they do not fire, or the probe is NOT RUN, the design is a visually hidden, read-only `<textarea>` sink beside the canvas that holds focus (keys still forwarded as above). Hangul composition may start in that sink; composing keys match by `code` (section 7). The bindable `copy`, `cut` and `paste` actions (unbound by default, M2-Q4) use the in-memory clipboard, and `EditorCanvas` also writes their text with `navigator.clipboard.writeText` when available; a host binding on Mod+C, X or V consumes the keydown, whose `preventDefault` suppresses the DOM clipboard event.

## 7. Keymap and extension contributions

- **Chords.** `KeyBinding = { chord: string; action: string | null; args?: JsonValue }`. A chord is `+`-separated modifiers (`Mod`, `Ctrl`, `Meta`, `Alt`, `Shift`, any order, each at most once) and one key token. **Canonical form:** `Mod` resolves to `Ctrl`, or to `Meta` when `EditorOptions.platform` is `'mac'` (default `'other'`; `editor-core` reads no browser global); modifiers are written in the order Ctrl, Meta, Alt, Shift; a single ASCII letter or a `KeyX` token becomes `KeyX` (upper-case X), a digit or `DigitN` becomes `DigitN`, `' '` or `Space` becomes `Space`, and any other token (`ArrowLeft`, `Delete`, `BracketRight`, `Equal`, `[`) stays as written. Two bindings are the same chord when their canonical forms are equal, so `Mod+Z` and `Mod+KeyZ` are one chord.
- **Matching.** An event's modifier set must equal the chord's. Its key token is `key`, canonicalized as above, so the user's keyboard layout is respected (Dvorak included); only when `key` is `Process` or `Unidentified`, is a single non-ASCII character (a Korean layout), or `composing` is true is the token taken from `code` instead (`KeyX` and `DigitN` canonicalize as above; other code names such as `BracketRight` stay as written). There is no general fallback from `key` to `code`. M2-Q3.
- **Actions.** Built-in action names (no dot): `setTool { tool }`, `undo`, `redo`, `delete`, `selectAll` (the scope's or page's children), `group`, `ungroup`, `maskGroup`, `duplicate { offset? }`, `nudge { dx, dy }`, `reorder { op }`, `align { edge }`, `distribute { axis }`, `zoomIn`, `zoomOut`, `zoomToFit`, `zoomToSelection`, `zoomTo100`, `enterScope`, `exitScope`, `copy`, `cut`, `paste`; selection actions run their command on the current selection and do nothing on an empty one (still consumed). Any other action is an extension command ID, run as `runCommand { id, args }`.
- **Defaults** (`DEFAULT_KEYMAP`, exported): V, R, O, L, F, P select, rectangle, ellipse, line, frame, path; Delete and Backspace delete; Mod+Z undo; Mod+Shift+Z and Mod+Y redo; Mod+A select all; Mod+G group; Mod+Shift+G ungroup; Mod+Alt+M mask group; Mod+D duplicate; Arrow keys nudge 1, Shift+Arrow 10; Mod+] forward, Mod+[ backward, Mod+Shift+} front, Mod+Shift+{ back; = and - zoom in and out; Shift+! fit, Shift+@ selection, Shift+) 100% (key tokens as a US layout produces them; a host layer rebinds them for other layouts); Enter enter scope; Escape exit scope. `align`, `distribute` and the clipboard actions are unbound by default (Alt+letter chords collide with browser menu keys on Windows); M2-U8 confirms headed that each default chord reaches the page in both browsers.
- **Layers.** The effective keymap is the defaults, then each extension's bindings in registration order, then the host layer (`EditorOptions.keymap`, default empty); per canonical chord the later layer wins and `action: null` unbinds. A layer may not bind one canonical chord twice. Two extensions binding the same canonical chord conflict, and `createEditor` throws (`editor.invalid-keymap` in the message), as for a malformed extension binding or one naming another extension's command. `setKeymap { bindings }` replaces the host layer at run time (session; `editor.invalid-keymap` with a path, nothing changes on failure); query `{ type: 'keymap' }` returns the effective frozen bindings in canonical form, sorted by chord. An invalid host layer at `createEditor` throws.
- **Extensions.** `Extension` gains `tools?: ExtensionTool[]` and `bindings?: KeyBinding[]`. `ExtensionTool = { id; input(event, api: ToolApi): boolean | void; reset(): void; overlay?(): ToolOverlay | null }` with an owned `id`; `ToolApi` is `ExtensionApi` plus `gesture: { active; begin(); update(command); replace(commands); commit(); cancel() }` (section 4; no `edit`); `true` from `input` consumes the event. `setTool` accepts a built-in name or a registered extension tool ID (`ToolId = ToolName | string`; `editor.unknown-tool` otherwise). An extension's bindings may name built-in actions and its own commands only.
