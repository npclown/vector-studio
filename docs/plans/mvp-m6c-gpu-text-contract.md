## 2. Definitions

- **Displayed size.** A run's `size` × the camera zoom, in CSS px; × DPR in device px (E28-K1's `s` at rotation 0).
- **Port origin.** A cluster's port position `(x, y)` mapped by E28-K1 to device px, `o = M(x, y)`, unquantized.
- **Ink box.** M6-S0's `ink-boxes` measures ([README](../evidence/m6-s0/README.md), (d)): coverage `255 − min(R, G, B)` over white; `offset` the larger left or top edge shift and `sizeDiff` the larger width or height difference, in CSS px; `subOffset` and `subSizeDiff` the coverage-weighted forms, ignoring coverage ≤ 2/255. Section 6 judges the horizontal and vertical components of `subOffset` separately.
- **Placed DOM cluster.** The browser's paint of one cluster alone (the per-cluster raster E28 draws), at the displayed size with text-dom's styles, in the node's text as text-dom lays it out, only the cluster painted (M6c-U3 follow-up and review r1), with its baseline on the device row of E28-K3's snapped corner `P.y` and its pen origin at `o.x` (gated read at `P.x + phaseX`, section 6.1 A06 method amendment) (section 6.1). Since M6-Q14 (a) no product DOM draws text, so it exists only under `?test=1`.
- **Flowed DOM block.** The browser's own layout and paint of the whole node at the displayed size, as M6-S0's `spans` mode (the layout term, recorded only).
- **GPU cluster.** One cluster of a projected text leaf drawn alone through the host's renderer options at the page's camera and DPR (section 6.1).

## 3. Zoom-125 % investigation (U0, first)

**Finding to explain.** Every row at browser zoom 125 % (DPR 1.25 and 1.875) gives positions off by up to 1/32 px (0.0273 px at 1.875) with identical breaks, clusters and fallbacks, in both browsers, with or without a reload; DPR 1.5 by monitor scale or zoom 150 % gives 0.0104 px; CDP `deviceScaleFactor` 1.25 passes. So the difference follows browser zoom 125 %, not DPR. The record's fifteen requests do not share one scale: the four with a size-40 run measure at `s` 32 (`measurementScale`), the rest at 64, so a page-px delta is `s` times larger in measured CSS px for one than for the other. An unverified clue: if the 1.5 maximum comes from an `s` 64 request, 0.0104 × 64 ≈ 2/3 CSS px, one device px at DPR 1.5, which would point at a whole-device-px rounding at the measured size.

**Method.** (1) Reproduce in the container first with CSS `zoom: 1.25` on an ancestor of the measurement host (the host itself starts with `all: initial`, `measure.ts:20-31`), or with `--force-device-scale-factor` and a page zoom, on the record's request set; if neither reproduces 1/32 px, diagnose on the main PC with the record's snippet extended to print the request, its `s` and the differing field. (2) Record which request, which `s` and which field (`baseline`, line `top` or `height`, cluster `x` or `advance`) give each row's maximum, and its pattern against `s`, zoom and size. (3) Test each candidate cause and record it kept or ruled out: Chromium's layout unit, 1/64 of a zoomed px, which is not a power-of-two fraction of a CSS px at 1.25; line metrics rounded to whole zoomed px at the measured size; Chromium's own limits reached in zoomed px, the 10,000 px `font-size` clamp and the 2^25 px layout extent (`scale.ts:16-31`; 2048 × 1.875 is still below the clamp, so this is expected to be ruled out); the probes' `inline-block` edges snapped in device px.

**Rule.** (a) If a text-dom change brings every manual row within 1/64 px (for example measuring under an ancestor that cancels the page zoom, or choosing `s` so that `s × zoom` keeps the rounding a power-of-two fraction) and keeps M6a-A11, A12 emulation and size linearity passing, U0 fixes text-dom (light tier unless the port's interface changes). (b) U0 takes (b) once every step-3 candidate is recorded as kept or ruled out and no fix tried under (a) passes: it amends M6a-A12's browser-zoom bound to **1/32 px**, the measured worst case (already a power of two), with the cause or "not found", as a dated amendment in M6a section 10, reviewed by both tracks, and the user confirms it (M6c-Q1), since the user accepted M6a with the failure disclosed. The DPR, emulation and monitor-scale rows keep 1/64 px. Either way the manual rows of [m6a-a12-dpr-manual.md](../evidence/m6a-a12-dpr-manual.md) are re-run on the main PC and recorded as a new dated section of that file; under (b) the re-run snippet tests zoom rows against 1/32 and every other row against 1/64. (c) Under M6c-Q1 (c), A01 is a disclosed FAIL in the exit record. Why the residual matters little for M6c: positions feed the caret and the GPU alike (M6-L1), and 1/32 page px at camera zoom 1 is below E28's quarter-device-px phase step; it matters for auto-size frames written at one zoom and read at another (M6-Q6 (a)).

**Amendment 2026-10-31 (M6c-U0 finding).** The container reproduced the record's figures under real browser zoom and under a real device scale (`--force-device-scale-factor`), not under CDP emulation ([U0 evidence](../evidence/m6c-u0/README.md)). The difference follows the layout zoom, browser zoom × the real device scale, not browser zoom alone, so the "not DPR" reading above holds only for emulation; the clue above is also wrong (the 1.5 maximum is half a device px on an `s` 32 request). Cause kept: Chromium rounds line metrics to whole layout px at the effective zoom; the other step-3 candidates are ruled out. U0 takes rule (a): text-dom cancels the layout zoom on its measurement host, and the M6a-A12 bound stays 1/64 px. ## 4. Projection (U1)

- **M6c-P1 shape.** A visible or hidden text node projects one leaf `{ id, parentId, transform, visible, opacity, kind: 'text', generation, lang, runs }`, the base fields as every leaf (`localTransform(frame, rotation)`), the rest from one `TextLayoutResult` of the node by M6a section 3.1: `generation` and `lang` of the result; one scene run per maximal sequence of clusters with the same `run` index on one line, in text order, with `fontList` `fontLists[run]`, `size` and `color` from the node's run (colour copied as fills are); clusters `{ text, x, y, advance }` with `text` the node text over `[start, end)`. Every cluster is emitted, whitespace included (E28 caches `empty` per key, so a space costs one raster call per key). An empty node projects `runs: []`.
- **M6c-P2 layouter (M6c-Q2).** `SceneProjector` takes an optional `TextLayouter` (the editor's `TextLayoutCache.layout`), and `projectPage` passes it to `projectNode` for the `text` case; expanded instance text (M7-T2, M7-T3) goes through the same case with the expanded node object, so equal-scale instances share one layout by request key (M6a section 9, cost). The projection stays synchronous. A layout call does not throw for a request built from a valid node (M6a-L2); if a port breaks that, the exception propagates out of the projection as a throwing custom projection's does today (`projector.ts:1565-1570`), and is not caught or isolated.
- **M6c-P3 no port (M6c-Q3).** Without a port text projects nothing, as today, and the editor raises a text variant of `DiagnosticEvent`, declared in `editor-core` (`types.ts`), not in `contracts`: `{ type: 'diagnostic'; code: 'editor.text-unavailable'; reason: 'no-text-layout'; nodeIds }`, `nodeIds` the sorted scene IDs of the text units left out (text nodes and expanded text). `DiagnosticEvent` becomes the union of this and the existing shape, whose `code` and `reason` are unchanged (a host switching exhaustively on `reason` as `SceneRejectionReason` sees a widened type; disclosed). It is raised at most once per renderer attachment and active page, reset by `load` and a page switch, at the first projection of that page that holds a text unit: so a text-free document that gains text later (paste, undo, a host command) raises it then, and a renderer attached after load raises it at its first projection. Never `editor.scene-rejected` or `editor.renderer-unsupported`.
- **M6c-P4 generation.** The editor's port listener calls `SceneProjector.relayout` after dropping the cache and before raising `textLayout`, so a font load re-projects every text unit on the active page, expanded text included, with no document event, step or autosave write. Other pages re-project on their page switch from the new generation.
- **M6c-P5 edit mode (M6-G5).** Nothing new: typing and each composition `replace` change the drawn document, whose text units project through the scoped change set (E26-U4); entering or leaving edit mode changes no scene node. A pending node has no node and draws nothing until its first input.
- **M6c-P6 bounds (M6c-Q4).** `visualBounds` of a text node stays its frame, so `createSymbol`'s wrap and group bounds do not see a `fixed` node's overflow (disclosed); the renderer culls by E28-K9's cluster bounds, which cover the overflow.

## 6. DOM and GPU agreement (U3)

### 6.1 Method (M6-G3 as read in section 1.2)

- **GPU side.** For each fixture cluster, the probe builds a one-cluster scene from the projected leaf (same transform, generation, `fontList`, `size`, `x`, `y`, black, opacity 1), draws it on white at the host's camera, DPR and origin (section 5) and reads it back (E10 capture), with its E28-K3 placement (pen corner `P`, `phaseX`, bucket); the agreement fixtures are unrotated at a uniform scale, so every cluster is in K3's snapped mode and has a `P`. The editor's renderer, scene and revisions are untouched.
- **Placed DOM cluster.** (Amended by the M6c-U3 follow-up and review r1, 2026-10-31: the node's whole run tree as text-dom builds it, every span transparent, the cluster in a nested span painted alone; see section 2.) Superseded original text, kept for the record: the cluster alone in its own visible span at the displayed size with text-dom's measurement styles (font list, `lang`, letter spacing in em, unitless line height, ligatures and spacing properties), no other cluster in the element, positioned so that its pen origin, read back with a baseline probe at that size, lands horizontally on `o.x` and its baseline on the snapped corner row `P.y`, the row the GPU draws its baseline on; the residual of that placement is recorded. How Chromium itself rounds the baseline then does not enter the vertical comparison. The styles come from one text-dom export (M6c-Q6), so the reference cannot drift from what text-dom measures.
- **Flowed DOM block.** M6-S0's `spans` mode at the displayed size; recorded only.
- **A06 method amendment (2026-10-31, M6c-U3 review r1).** The gated raster term compares the GPU cluster with the placed DOM cluster read (a) with its pen on the GPU's quantized pen `P.x + phaseX`, not on `o.x` (Chromium snaps a pen to its 1/64 px layout unit and Skia quantizes it to a quarter pixel, so a pen at `o.x` can round to another quarter than K3; the step from `o.x` to `P.x + phaseX` is the placement term's, checked exactly, and the read at `o.x` is recorded as `originPen`); (b) on a composited layer (`will-change: transform`), where Chromium paints grayscale coverage as the atlas has, and the gated crop must be achromatic (largest `|R − G|` or `|G − B|` at most 2/255); (c) with its baseline on the whole CSS px above `P.y` and the layer translated by the remaining whole device px (`layerShift`), since Chromium paints a baseline on a whole layout px. A06 makes no claim about the browser's ClearType (LCD) paint of DOM text: that read is recorded only (`lcd`).
- **The split, per cluster, in device px and CSS px.** (1) *Layout term* (recorded, not gated): flowed DOM block against the port origin; its expected cause is U4c's line-metric rounding at the displayed size (section 1.2), which this term names, not undoes. (2) *Placement term* (gated, exact): the probe's `P` and `phaseX` equal E28-K3 applied to `o`, so the GPU draws the port's positions and no second layout (M6-G1); the horizontal quantization is at most 1/8 device px (phase step 1/4 device px) and the vertical snap `P.y − o.y` at most 0.5 device px. (3) *Raster term* (gated, section 6.3): GPU cluster against placed DOM cluster, both pen origins at `(o.x, P.y)` up to the GPU's horizontal phase quantization. The snap `P.y − o.y` is recorded per cluster as an observation.

### 6.3 Tolerance (M6-G2, M6c-Q7)

## 12. Risks

- **The zoom cause may be Chromium's.** Then the fix is an amended bound and auto-size frames stay zoom-dependent by up to it (disclosed).
- **The DOM is not a layout oracle any more.** After U4c the flowed DOM block differs from the port by line-metric rounding; M6c gates the GPU against the port and the browser's paint at the port's positions, so a flowed-layout difference is recorded, not failed (section 1.2).
- **Agreement is against the browser's own paint.** ClearType DOM against grayscale atlas coverage can differ in size and centroid without a position error; the split keeps that from hiding a placement error, and some fixtures may need named limits.
- **Blank text after a font load** (E28 budget) is now user-visible; M9 owns any remedy.
- **Manual run is one sitting on one machine**: IME versions drift; it is evidence, not a replayable trace.
- **Main-thread cost** of layout plus rasterization while typing is observed, not bounded, until M9.
