## Frozen sources and prospective expectations

Reuse the exact source controls and order from `fixedSimpleCubicTopologyFixtures()`, ignoring its synthetic `lines`. For each of its 47 cases, emit nonzero then evenodd: 94 rows. The 45 ordinary transformed/permuted cases and MIN_VALUE linear square are mandatory successes under both rules: 92 successes. The two large-square rows with a=2^1021 must return `PATH_NUMERIC_RANGE` during sizing, without emission or mesh publication. No observed output selects rows, density, tolerance or limits.

The ordinary source Q has control-to-chord maxima sqrt(20)/3 at depth0, sqrt(26)/12 at depth1 and at most sqrt(122)/96 at depth2. The last is below1/8; the 2^20 translation guard is approximately3e-8, below its margin. D and D/2 reach depth2, D/4 and D/8 reach depth1. All ordinary source transforms and these midpoint knots are exactly representable dyadics. Relative subdivision and origin restoration therefore reproduce exact canonical restriction knots. Source orientation and nesting expectations remain the literal P3.1e labels; expected polygons must be derived from the actual ordered commands, not substituted with the old uniform-depth2 polygon.

Q has positive curvature numerator 72*(t*t-t+1). Its depth1/depth2 restricted hulls separate at their shared tangent and adjacent quarter hulls meet only at the cardinal knot. In each quadrant the whole quarter control hull has x+y in [4,6] in absolute coordinates; successive half-scale contours occupy disjoint [2,3] and [1,3/2] bands. C04's fixed closing chord and C05's horizontally separated diamonds remain embedded. Thus the existing sufficient topology proof applies also to the coarser native inner leaves.

MIN_VALUE square controls are integer multiples of a; each side is exactly linear and emits a depth0 endpoint. The guard starts from max(1,abs(control)) and is 2^-45, below 1/8. Exact endpoints and rounded section pins preserve this square. Do not classify it as numeric range merely because it is extreme. Conversely, the large square's original-coordinate guard exceeds 1/8 before flattening, which proves the separate expected sizing failure. This is a compatibility limitation of the existing kernel, not a new product support rule.

Rounded embedding feasibility is also fixed before execution. Ordinary actual knots lie on a 1/64 grid, every edge has absolute horizontal extent at most4, and every x column is an exactly representable source x. In grid units a nonvertical section y has a denominator at most256. Distinct section heights therefore differ by at least 1/(64*256*256)=2^-22 in ordinary units. All coordinates have magnitude below2^21, so a Float64 spacing is at most2^-32. Nearest rounding keeps section groups distinct, honors exact pins and displaces each nonexact height by at most2^-33, within tau/2=1/32. This is a feasible monotone assignment; the accepted complete greedy-window rule must therefore succeed. The MIN_VALUE square has only exactly pinned sections. No assumption that arbitrary close groups can be embedded is made.

## Bounded carrier and canonical path construction

Add test support under `tests/geometry/native-cubic/` and one `tests/geometry/native-cubic-fill.test.ts` bridge. Before invoking Rust, TypeScript writes the fixed source rows to a fresh ignored `.tools` directory. The native test receives that exact file via `P3_NATIVE_CUBIC_INPUT`; no output file, reference mesh or rounded expected data is fed to Rust. The input text is UTF-8, at most 512 KiB, with header `# p3-native-cubic-v1`, then `# rows 94`, then 94 rows. Each row is `id rule expectation | contour | contour ...`; expectation is OK or PATH_NUMERIC_RANGE. Each contour is semicolon-separated cubics, each cubic eight comma-separated, exactly 16-character lowercase hexadecimal Float64 bit patterns in p0x,p0y,...,p3x,p3y order. IDs use only ASCII letters, digits, slash and hyphen. The parser rejects wrong headers/counts, extra/missing fields, invalid rules/expectations/hex/nonfinite controls, empty/disconnected contours, over four contours or over 16 cubics. Source bit echoes preserve signed zero.

Each contour becomes MOVE(p0), its CUBIC(p1,p2,p3) verbs, and CLOSE only when its final canonical endpoint equals its initial point. C04 stays open. All contours belong to one complete path. Source ordinals are actual zero-based verb positions, including MOVE/CLOSE, rather than the old fixture's arbitrary ordinal7. The TS source map independently derives those positions. Mathematical equality treats both zeros equally; source echoes still compare exact bits. Fixture expectation is checked only after actual execution and must never steer the algorithm, contour collection or mesh generation.

The native test-local workspace reserves fixed arrays for at most 72 commands (4 MOVE +64 LINE +4 CLOSE), 68 contour points before terminal duplicate removal, four contour ranges and 64 edge owners. It owns one rounded workspace with the limits below. Prepare source parsing/verb/point bytes and constructor allocations outside the measured attempt. No new allocator or runtime arena is introduced. Byte evidence distinguishes the rounded workspace's actual allocated capacity from the test-local inline storage; both remain fixed across attempts.

Run sizing first, with no retained callback output. On success, run emission into bounded command storage. Plans and bounds must agree across passes; callback exhaustion or mismatch fails the test-local composition explicitly and publishes no result. Preserve the actual MOVE/LINE/CLOSE stream, every finite point and every provenance triple. Contour collection removes only a duplicate final point of a closed loop; it retains ownership of the final cubic leaf. An open contour retains its last point and gains a closing-edge owner, never fabricated cubic provenance. Rounded input references slices of owned point storage.

Each normalized source edge has a parallel owner: `{kind:"CubicLeaf",source_verb,end_numerator,depth}` or `{kind:"ImplicitClosure",contour}`. The array follows rounded source-edge order. Verify it against command endpoints, contour start/end indices and the canonical source map. Resolve every rounded contributor through that map; no contribution may lose its original leaf/closure identity. These fixtures have no zero-length emitted leaves; fail a violated premise instead of silently dropping an owner.

## Publication and output protocol

Every attempt first clears the bridge's publication marker, command/contour/owner lengths and diagnostics. A sizing failure does not run emission or tessellation. An emission/capacity/mismatch failure does not run tessellation. A rounded failure publishes neither flattened contours nor a mesh. Previous rounded internal storage may remain allocated, but no bridge getter may expose an earlier publication after any failure. Subsequent success must restore valid current output. Preserve distinct path status and RoundedFillError inside the test helper; do not collapse them into a product error.

The ignored native test `native_cubic_fill_tests::emit_native_cubic_fill` prints exactly one frame `P3_NATIVE_CUBIC_BEGIN` / `P3_NATIVE_CUBIC_END` containing 94 JSON lines in input order. Capture is limited to 32 MiB with a 300-second process timeout. Root geometry tests already select the pinned compiler and invoke release native bridges; this checkpoint adds no standalone command or toolchain.

Each JSON row has exactly these fields:

- `id`, `rule`, `source_bits` (nested contour/cubic/eight-hex arrays), `flatten_tolerance_bits`, `topology_tolerance_bits`.
- `flat_status` uses the actual numeric PATH status constants (0 for success,4 for the expected numeric-range rows). `sizing_plan` is always present after sizing, even on failure; only `emission_plan` is null when sizing fails. A plan has numeric `status`, `verb_count`, `point_count`, with point_count measured in coordinate scalars as in the actual kernel. On sizing failure flat_status equals sizing_plan.status; successful carrier rows require both plans and flat_status to be PATH_OK.
- `statistics` with `logical_cubics`, `sizing_visits`, `emission_visits`, `emitted_cubic_lines`.
- `flat_bounds`, `commands`, `edge_owners`, `rounded`: all null on either expected large-square failure, while sizing diagnostics/statistics/allocation evidence remain present. Commands have numeric `verb` (MOVE0, LINE1 or CLOSE3), `point` (null for CLOSE), and `provenance` with `source_verb`, `end_numerator`, `depth`. Successful flat_bounds is [min_x,min_y,max_x,max_y].
- `rounded` on success is the existing strict NativeRoundedRow: same id/rule, tau_bits=1/16 bits, profile I, actual collected contours, error null, complete output and stats. Reuse `parseNativeRoundedRow`; do not duplicate or relax its schema.
- `allocations`, `allocated_bytes` and `inline_bytes`: attempt allocation count, actual rounded heap capacity and `size_of::<BridgeWorkspace>()` respectively. The two byte fields account for the helper's inline storage plus heap; input parsing, serialization and construction are excluded from attempt allocation measurement. Inline storage must be below64 KiB and stable across all rows.

All numbers are finite, counters are nonnegative safe integers, enum/status values are checked and unexpected keys or extra/missing rows fail. Primary may expose only the existing test-local `print_points`, `print_output` and `print_stats` as `pub(super)` for byte-equivalent serializer reuse. Primary also extracts `parseNativeRoundedValue(value,index)` from the existing strict `parseNativeRoundedRow` body; the row function continues to JSON.parse then delegate with identical checks. The new outer parser passes its parsed nested value directly, never through JSON.stringify, which would silently replace negative zero. Product Rust modules and existing native JSON meanings stay unchanged.

## Prospective limits and evidence

At most 16 cubics with four leaves each give 64 source leaves, 112 sizing visits and 112 emission visits; the corpus's single open C04 has only 12 leaves plus closure. Hence at most 64 normalized polygon edges. P3.1e separation proves no proper crossing, so at most 128 raw endpoint events and 2016 pair checks. A generic event/edge bound permits 128*64+2*64=8320 section records.

Tighter output bounds use the frozen convex family, not arbitrary 64-edge paths. Each depth<=2 diamond has at most nine distinct x coordinates. Up to three concentric diamonds share x=0: at most 25 columns and six node groups per column, hence 150 nodes, 125 spans, 72 filled cells and 144 triangles. C05 has at most 36 columns but only one x-active diamond, hence 72 nodes, 32 filled cells and 64 triangles. C04 is convex; the extreme square has two columns, four nodes and one cell. Therefore the existing 256-vertex/256-triangle checker suffices without changing its limits. At most two incident edges per node bound ordinary sections by300. No ordinary diamond edge is vertical, so lower/upper contributors and boundaries are at most144; the linear square adds its two vertical source edges. Conservative 512 ledger caps suffice.

Freeze a separate RoundedFillLimits value: contours4, input_vertices64, edges64, pairs2016, events128, sections8320, nodes256, cells256, boundaries512, contributors512, vertices256, triangles256, work2,000,000 and bytes16 MiB. This retains the existing rounded checkpoint's conservative work/byte ceilings while sizing the source envelope explicitly. Source-loop review bounds event-sort charges by8128, scalar searches by192*(36+150), ledger edge scans by2*64*125, section lookups by the at-most12 incident records per nested column, and remaining pair/column/section/cell/mesh work well below the work ceiling. Constructor/actual-capacity accounting covers every rounded Vec; no size is inferred from a measured success or raised after observing a failure.
