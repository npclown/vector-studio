## Boundary

**The shared surface** is exactly three things:

1. the `packages/contracts` exports (scene, renderer, diagnostics and geometry);
2. the public factory and constructor surface of `geometry-wasm` (`createFillMeshPort`, `createStrokeMeshPort`; the ports are `FillMeshPort` and `StrokeMeshPort` in `packages/contracts`), `renderer-core` (`PrimitiveRendererService`, and the root `index.ts` exports of each package) and `renderer-webgpu` (`WebGpuBackend`; each package has a root `index.ts`), as the playground uses them (see `apps/playground/src/p3-v4-paths.ts`, lines 1-4);
3. the operation identities (`geometry-wasm/fill-v0+rN`, `geometry-wasm/stroke-v0+rN` and their successors).

Packet formats are not shared: they are internal to `renderer-core` to `renderer-webgpu`, both of which the rendering track owns.

- **A change to the shared surface is full tier and is reviewed by both tracks.** The review checks that the other track's consumer still works.
- **Within the shared surface, each track merges independently.** The rendering track may change kernel internals, limits and speed while the identity rules hold. The visualization track may add pages, scene features and UI that use the surface as published.
- **Revision bumps keep today's tiering.** An outcome-changing kernel fix bumps the revision under its owning contract's identity rule, as #179, #190 and #195 did, and is not full tier by D9. Only a change to the identity scheme, a port shape or the `packages/contracts` exports is full tier with both-track review.
- **Durable document data stays independent of renderer, GPU and WASM objects** ([`AGENTS.md`](../../AGENTS.md#working-rules)). Scene and document features on the visualization track store only durable data. Meshes, GPU buffers and WASM allocations remain reconstructible caches.
- **No new dependency or renderer is implied.** [`AGENTS.md`](../../AGENTS.md#working-rules) still requires a new architecture decision and explicit user approval for a runtime renderer, scene graph, path renderer or tessellation dependency.

**Enforcement is by review, not by tooling.** `pnpm check:boundaries` checks import edges only, and `tooling/boundary-policy.mjs` already allows the playground's imports of `contracts`, `geometry-wasm`, `renderer-core` and `renderer-webgpu`. The repository has no `CODEOWNERS` file and no path-ownership check. D9 therefore adds:

- a required PR Gate checklist line: "track; packages touched; shared surface changed? (y/n → full tier)";
- an optional follow-up item, not part of D9: a path-touch check or a `CODEOWNERS` file once the track plans exist.

## Operations

- **Lanes.** Each track has one development lane and one verification lane, four agents in total, under the one Primary. A verification lane runs the fixed validation commands for its track and never edits the code it verifies. The independent `reviewer` in a fresh context is still used for full-tier contracts and evidence.
- **Branch prefixes.** `claude/eng-<item>-<slug>` for the rendering track and `claude/viz-<item>-<slug>` for the visualization track, for example `claude/eng-e1-stroke-early-abort`. This is a convention that fits the existing `claude/<plan-item>-<short-slug>` pattern of [`AGENTS.md`](../../AGENTS.md#git-and-github-workflow), with the track marker as the first part of the plan item. It needs no `AGENTS.md` amendment.
- **Plan documents.** One plan per track, named per [D9-Q1](#open-questions-for-the-user). Proposed names: `docs/plans/d9-rendering-track.md` and `docs/plans/d9-visualization-track.md`. Each holds its status index, items, acceptance criteria and evidence. `docs/plans/p3-fill-stroke-meshes.md` keeps the P3 history and the P3 acceptance table.
- **Integration checkpoint.** A weekly checkpoint on shared `main`: the full GPU specs, a demo of the visualization track's current page, and a comparison against the baseline of any rendering-track claim made that week. The GPU specs are not in CI. The checkpoint runs them headed on the reference machine, by the Primary through a runner agent. It records what ran and what did not (NOT RUN with a reason), and it does not replace per-PR CI. Cadence: [D9-Q3](#open-questions-for-the-user).
- **Shared `main`.** Both tracks merge to `main` through pull requests, squash merge by default, with independent review per PR as today (full tier: contract review and evidence review; light tier: one review of the diff and CI). Each track rebases onto the updated `main` before it opens a PR.
- **Conflict rule.** If a PR needs a change in a package the other track owns, the PR is split, and the owning track merges that part first as its own PR.

## Risks

- **Shared seams.** Both tracks touch the shared surface. The boundary rule and both-track review keep it single-owner, but a change to it slows whichever track proposes it.
- **Review-only enforcement.** Ownership and the shared-surface rule are enforced by review. With no `CODEOWNERS` and no path check, a PR can touch the other track's package without a tool objecting. The PR Gate checklist line and the reviewers are the only guards until the optional follow-up exists.
- **Rendering track load.** E1-E6 and the in-flight items are mostly full tier, with contracts before code. The visualization track can run ahead, so its features may expose defects faster than the rendering track closes them. Defects go to the rendering track as items with fixtures.
- **P3 exit evidence is a long pole.** A01-A08 are all TODO, A04 needs E3, and P1 A09/A10 and P2 A08 stay open. If the exit evidence has no owner, MVP 1 can look like a finish while the gates stay open. The P3 exit evidence item in the rendering track table is that owner.
- **Verification lane independence.** A verification lane shares context with the developer lane of its track. The fresh-context `reviewer` stays the independent check.
- **Precision stays UNVERIFIED.** Until E3 has evidence, every visualization result carries the UNVERIFIED label required by D8.
