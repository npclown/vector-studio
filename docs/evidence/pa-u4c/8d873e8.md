## 2. M1: which routes hold

- **Route 1 (a committed-heap peak counter) does not exist.**
  - The only peak field in the trace is `peak_malloced_memory` in `V8.GC_Heap_Stats`, which is V8's malloc, not the JS heap.
  - The memory-infra dumps that were taken are summary-only background dumps (`GlobalMemoryDump`, `level_of_detail: "background"`). They put no per-process allocator dump (`ph: "v"`) into the trace (findings 4b).
- **Pairing holds.** In both inspected runs:
  - every `MinorGC` and `MajorGC` has exactly one `V8.GC_Heap_Stats`, emitted inside its span (183 of 183);
  - no GC runs on another thread;
  - over all 40 runs `gc.unpaired` is 0 (findings 4d), with the one unended GC not counted (below).
- **New source: the committed size at each GC start.**
  - `V8.GCTraceGCNVP` (one per GC, 183 per run) carries `start_memory_size` and `end_memory_size`.
  - In both committed traces, `end_memory_size` equals that GC's `total_heap_size` in all 183 GCs, so it is the committed heap.
  - `start_memory_size` of GC k is never below `end_memory_size` of GC k−1 (0 to 17.2 MB above in Chrome, 0 to 20.7 MB in Edge).
  - So the committed size just before each GC is reported directly. It replaces route 2's between-GC upper bound and its page and buffer slack. That bound was loose: in chrome-dpr1-v2 stress r1 it reaches 172.5 MB against a largest reported `start_memory_size` of 141.8 MB.
- **The in-GC transient is still unbounded.**
  - Committed memory grows inside some GCs: `end_memory_size` exceeds `start_memory_size` by up to 4.4 MB (Chrome) and 4.6 MB (Edge).
  - No event reports the peak while a GC evacuates. The contract's route 2 needs a confirmed bound for it, for example promoted bytes (`promoted` in the same event) for a scavenge plus the evacuated space for a mark-compact. Nothing here confirms such a bound.
- **Incremental marking moves the major GC.**
  - In each inspected stress run, one marking cycle runs in about 74 steps and ends with the single `MajorGC` event. View-edit runs have 4 to 8 major GCs and were not inspected for this.
  - That event's `usedHeapSizeBefore` is the size at the final pause, not at the start of marking.
  - This does not affect `start_memory_size`, which is taken per GC event, minor or major.
- **A GC still running at trace stop.**
  - One run (`edge-dpr2-v2` view-edit r4) has a `MajorGC` with `ph: "B"` and no end.
  - The summarizer counts only complete events, so that GC's after-sizes are missing from the record.

**Outcome.** M1 stays UNVERIFIED. What remains is one bound, the in-GC transient. The source that removes the slack is named for PA-U9 (contract section 3.1, amended).

## 3. M2: no route holds yet

- `V8.GC_Heap_Stats` gives `external_memory` only after a GC. `V8.GCTraceGCNVP` has no external-memory size; its `heap.external.*` keys are times. So route 1 does not exist.
- Route 2 needs an audit showing that the gated path detaches no buffer between sweeps. Route 3 needs an engine-side ledger. Neither was built in PA-U4b, so M2 stays UNVERIFIED.
- Observed values (the larger of `external_memory` after any GC and the end `backingStorageSize`): 7.9 to 8.1 MB in stress, 62.6 to 79.5 MB in view-edit.
- Whether `external_memory` includes the two WASM memories (the attribution rule of 3.2) is not settled here.

## 4. M7: no trace source

- No `CppGC.*` event carries a size; their args are `epoch` and `forced`.
- No memory-infra dump holds `blink_gc`.
- `V8.GCTraceGCNVP` carries `start_global_consumed_size` and `start_old_gen_consumed_size`, whose difference includes the embedder's consumed bytes at each V8 GC start. These are object sizes, not committed memory, and the difference also mixes in external memory. It is a candidate only; nothing here confirms it. M7 stays UNVERIFIED.

## 5. A floor that already exceeds the bound

A committed size that `V8.GC_Heap_Stats` reports is a value the JS heap held. So the largest one (`gc.maxTotalAfter`) is a floor of M1's high-water mark, whatever the in-GC transient adds. It covers navigation start to trace stop, a little past the last step; the difference is negligible. The sum of the exact categories and that floor is therefore a floor of the contract's sum of category maxima. It is not a floor of the true simultaneous peak: the exact sum includes M5, a stated upper bound that assumes two browser swap-chain copies (A09-Q2 (a)), and M4 counts descriptor capacities of resources not yet destroyed. MB here is 10⁶ bytes; the bound is 256,000,000 bytes.
