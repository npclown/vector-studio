## A09: a sufficient upper bound is possible in principle

The current `ResourceAccounting` in `packages/renderer-core/src/resource-accounting.ts` maintains aggregate live/peak descriptor bytes on track/release events. Buffer/texture descriptors contribute bytes; other resource categories are count-only. `packages/contracts/src/resources.ts` explicitly labels descriptor estimates. This is reusable GPU accounting, not a JS-object, shared-memory or physical-GPU memory census. P1 must validate complete allocation/lifetime coverage before using it as a bound.

[Windows process counters](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex) expose a lifetime peak of private commit. The [EX2 counter](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2) adds current shared commit, not its lifetime peak. Therefore neither a sampled working set nor private peak alone bounds all in-scope memory. CDP [getHeapUsage](https://chromedevtools.github.io/devtools-protocol/v8/Runtime/#method-getHeapUsage) is an isolate observation with separate heap/embedder/backing fields, not continuous peak evidence.

Primary's conditional proof is: for every instant in the declared lifetime, prove `CPU(t) <= P + S` and `GPU(t) <= G`, then `max(CPU(t) + GPU(t)) <= P + S + G`. Here `P` is a verified private-commit upper bound over every CPU owner, `S` covers every in-scope shared/file-backed mapping not covered by P, and `G` bounds engine-accounted GPU capacity across all generations and pending destruction. Keep an ownership inventory counting shared storage once in the actual category model; an explicitly labeled conservative bound may overcount. Do not subtract a startup or sampled baseline. Separate maxima need not occur together to establish this sufficient bound, but the plan's ownership/overlap fixtures still must exist.

If the proven upper bound is at most 256,000,000 bytes, it is sufficient for the unchanged ceiling. A larger conservative bound is inconclusive, not evidence that actual engine memory exceeded the ceiling. Missing ownership or shared-capacity coverage makes the derivation UNVERIFIED regardless of its numeric value. No bound was measured or accepted here.

The memory worker also identified [Windows Job peak accounting](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information), which tracks peak job committed memory continuously. A containing Job could avoid missing short-lived child processes, but requires verified pre-launch containment, interaction with Chromium's own jobs and coverage of shared storage. Primary did **not** select or implement a new Job-controlled launcher: it adds process-policy and compatibility work before the accounting gap is closed. Per-process lifetime peaks likewise require retained identities/handles and complete ownership; polling a changing PID list is insufficient.

V8/Chromium allocation paths are useful provenance candidates, including [heap pages](https://chromium.googlesource.com/v8/v8/+/refs/heads/main/src/heap/memory-allocator.h) and [ArrayBuffer backing allocation](https://chromium.googlesource.com/chromium/src/+/HEAD/gin/array_buffer.cc). They do not constitute an exhaustive proof for the installed build or every IPC/shared mapping. The next strict-method work must pin browser/V8 source revisions, enumerate in-scope allocations and prove shared capacities and GPU lifecycle coverage before any counter experiment can certify A09. No storage rewrite or production abstraction is approved by this investigation.

## A10: two identity joins and endpoint provenance remain missing

The inspected [Chromium trace schema](https://chromium.googlesource.com/chromium/src/base/+/c505b1aab61c4a0e444a2aefe7b98dcf6026ebda/tracing/protos/chrome_track_event.proto) carries input latency IDs, surface frame IDs, aggregated surface frame IDs and display trace IDs. These can describe input-to-compositor propagation. They do not supply an application-defined WebGPU content-generation contract or a shared PresentMon row identifier.

| Missing proof                                                                     | Why the current artifacts/source candidates do not close it                                                                                                                                                                                                       |
| --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| J1: handled fixture input and submitted WebGPU content -> actual compositor frame | A browser latency event may attach to a compositor update without identifying the queue submission/canvas texture containing the new fixture content. A nearby User Timing mark or one-outstanding-input rule alone is not an independent content identity proof. |
| J2: compositor display swap -> exact PresentMon record                            | Chromium `display_trace_id` and PresentMon process/swap-chain/QPC fields have no verified shared-ID contract. Ordered sequences, nearest timestamps and a fitted offset cannot establish identity on their own.                                                   |
| Endpoint provenance                                                               | An event named FrameDisplayed can carry estimated feedback. Hardware completion must be distinguishable from a predicted vsync or independently validated through a correctly identified display event.                                                           |
| Clock conversion                                                                  | QPC frequency alone does not map page-relative `performance.now()` or epoch time to native trace/QPC domains. An independently paired clock observation, conversion/quantization uncertainty and drift bound are still required.                                  |

[PresentationFeedback](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/ui/gfx/presentation_feedback.h) distinguishes hardware-clock provenance, hardware completion and failure. In the inspected [Viz display trace emission](https://chromium.googlesource.com/chromium/src/+/HEAD/components/viz/service/display/display.cc), the relevant displayed event does not serialize those flags. The inspected [Dawn output path](https://chromium.googlesource.com/chromium/src/+/HEAD/components/viz/service/display_embedder/skia_output_device_dawn.cc) can predict the next vblank and mark hardware-clock provenance without hardware-completion provenance. This demonstrates why a trace label/clock flag alone is insufficient; it does **not** prove that the recorded Chrome run used this path.

[Chromium Windows clock code](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/base/time/time_win.cc) includes QPC and fallback paths. [CDP clock markers](https://chromedevtools.github.io/devtools-protocol/tot/Tracing/#method-recordClockSyncMarker) provide an instrumentation mechanism, not an automatic epoch-to-QPC conversion. Clock fitting may evaluate uncertainty only after independent event pairing; it cannot manufacture J1/J2.

The [Event Timing specification](https://www.w3.org/TR/event-timing/) excludes continuous pointer/mouse movement, so replacing drag evidence with INP/Event Timing would change the tested behavior. Another unchanged PresentMon-only CSV, including selecting v2 columns, would not add the missing fixture and compositor identities. The prior CSV cannot be joined retroactively to browser trace data that was never collected.

The next strict route is a version-matched source/schema audit for an explicit content handoff identifier, an independently shared OS present identifier and hardware endpoint provenance. Only if those exist should a separately approved bounded acquisition test follow. If absent, a concrete browser instrumentation or independently verified content/optical measurement design is needed, with cost and scope approved first. Neither a browser build nor hardware acquisition is authorized here. This is a blocker for the examined method, not a claim that physical presentation is universally unmeasurable.
