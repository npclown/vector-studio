# E16-U1 evidence: source caps and topology refinement, `fill-v0+r4`, 2026-10-25

Rendering-track item E16, unit E16-U1 of the [E16 contract](../plans/d9-e16-fill-rejection-remedy-contract.md#8-units): E16-K1, E16-K2, revision `r4`, E16-F1 to E16-F9, E16-A1 to E16-A7 and the dated notes of section 5. Full tier. This is functional evidence: precision stays UNVERIFIED until E3 measures A04 on `r4`, and E16 makes no speed claim (E16-G4).

Every run below was made in the cloud container (Linux x86_64, 4 cores, Node 24.15.0, Rust 1.94.1) unless another machine is named. The tools that pin the Windows host (`tooling/test-geometry.mjs`, `tooling/compare-p3-fill-identity.mjs`) were run from uncommitted copies with only the host string changed to `x86_64-unknown-linux-gnu`, as for E14-U1.

## What changed

- `cubic_fill.rs`, E16-K1:
  - Rung 0's S1 prefix has its own source caps: `MAX_FAST_CONTOURS` = C0 = 512 and `MAX_FAST_SOURCE_SEGMENTS` = S0 = E0 = 8,192. Verbs, scalars, flat commands and contour points derive from these as before.
  - The exact rung takes `line_caps` on a path with no cubic verb: 64 contours, 256 segments, 384 flat commands and 320 contour points (`MAX_EXACT_FLAT_COMMANDS`). A cubic path keeps `B1_CAPS`.
  - The source arrays (`source_verbs`, `sources`, `source_ranges`, `contour_ranges`) are heap buffers sized for rung 0 and counted in the workspace bytes.
  - `certify_topology` and `attempt_body` check their fixed arrays' lengths first and return `SourceLimit`.
- `fill_export.rs`, E16-K2:
  - `exact_rung` runs V2's cascade at e. After `KnotMismatch` or `Unresolved` it retries at e − 1 … e − 16 (`refinement_exponents`, none below `MIN_TOLERANCE_EXPONENT`).
  - It keeps the first retry that succeeds with `PATH_OK`. On any other path failure it keeps the cascade at e's outcome, and an internal error propagates. A pre-B1 workspace does not retry.
  - `build_path` and `fill_ladder::exact_cascade` both call it.
  - `BuiltPath` carries `depth` and the exact rung's unmapped `error`. `ExactOutcome` carries `depth` and `stop`, the last retry's depth and error when no retry succeeded.
  - `FILL_V0_REVISION` = 4, and `FILL_V0_LIMITS.max_contours` = 64.
- `fill_ladder.rs`: `boundary_records(points, contours)` and `FillLadder::reserve(records, points, contours)` follow C0. `MAX_BOUNDARY_RECORDS` = 3·(E0 + C0 + 2·C0 − 2).
- Identity: `geometry-wasm/fill-v0+r4` in `fill-adapter.ts`, its tests, the analysis harnesses and the five GPU specs. The three configuration hashes are pinned anew, as recorded in the P3 plan's AL-S1/AL-S2/AL-OB5 note. `tooling/p3-exit-a05-a06.mjs` and `tests/unit/p3-exit-a05-a06-map.test.ts` keep their `r3` strings, which are test data and comments, not pins of the current revision.
- Size pins: the bridge workspace's heap grows from 3,498,880 to 4,514,304 B and its inline size drops from 24,304 to 16,928 B. This applies in `native_cubic_fill_tests.rs` and in the native mixed and triangle-free verifiers.
- Diagnostics: `e14_fill_limit_diag` also prints `exact`, `depth` and `retryStop` (contract §4 item 4). `pnpm e16:fill-diag` gains an `r4` column, and its input check gains an all-requests mode (`E16_FILL_ALL=1`, deduplicated as the sweep is) for the E16-G2 input.
- `tooling/compare-p3-fill-identity.mjs`: the combined mode also allows `unsupported-geometry` → `ok` on cascade and WASM records. The self-test covers it and adds a failing case.

### Departures from the contract's fixture table

- **E16-F3 (a)** uses 64 squares read with `exact_only`, not 64 bowties through the ladder. At E = 256 edges the exact rung's event cap (`max_events` = 2E, filled by the endpoint events alone) leaves no room for a crossing event, so 64 bowties end at `Rounded(EventLimit)`. No crossing path can mesh exactly at the inclusive source caps. The squares still test the caps' inclusive bounds.
- **Rung 0's reason** is `MONOTONE` on E16-F3 (b), E16-F3 (c), E16-F5 and E16-F6, and `STRUCTURE` on E16-F7. The table above records each actual reason. FR4 runs before FR5's crossing check, as E14-F5 found.
- **E16-F9's exact error** is `SourceLimit`, not an edge cap. The path is line-only with 321 segments, which is over the line cap of 256, so decoding refuses it. E11 #251's cap-stop class names this case.
- **`line_caps`** derive from the workspace's rounded limits: contours are clamped to [4, 64] and edges to [64, 256]. `FILL_V0_LIMITS` gives exactly 64 and 256, and the frozen native `LIMITS` of the older native tests give `B1_CAPS`, so those tests see the caps they were written for.
- **Identity entry rule.** The tool keeps every entry record strict, which is AL-I1 unchanged. The contract's set-aside for line-only entries over B1's source caps was not needed: the randomized corpus has no such entry, and the run below shows no entry difference.

## Seeded defects (E16-A5)

All four are caught in `e16_fill_remedy_tests.rs`:

- **E16-D1** (`with_line_caps_on_cubic_paths`): without the defect, E16-F4 fails in decoding (`SourceLimit`, `emission_invoked` false); with it, the attempt passes decoding, runs emission and stops at `certify_topology`'s guard (`SourceLimit`, `emission_invoked` true), as the contract describes.
- **E16-D2** (`RetryOwnResult`): E16-F8 becomes `work-limit` with `CommandLimit`.
- **E16-D3** (`RetryAfterSuccess`), module level through `exact_rung`: an ellipse whose cascade succeeds at e gets depth 1 and a different rounded vertex count. It is not run through `build_path` or the identity tool.
- **E16-D4** (`NoExponentBound`): the schedule at e = `MIN_TOLERANCE_EXPONENT` + 2 goes below the minimum, whereas the bounded schedule ends at it.
