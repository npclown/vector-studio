# M6-S0 automated runs on the main PC (2026-10-29)

This record holds the results of the M6-S0 automated runs (a) to (d) of the [M6 text plan](../../plans/mvp-m6-text-plan.md) (section 8, light tier), as the main-PC session reported them on 2026-10-29. The scripts and decision rules are in [this folder's README](README.md). It makes no performance claim: it is not a benchmark under [`docs/benchmarks/README.md`](../../benchmarks/README.md), and the plan sets no layout budget.

**Not committed yet.** The eight raw JSON reports were moved out of the repo on the main PC and are kept byte-identical in its scratchpad; their SHA-256 hashes are in the [reports table](#reports). The README expects them to be committed unchanged ("Prettier skips these JSON files, so commit them unchanged"), so they are still owed; they will be committed to `docs/evidence/m6-s0/runs/` together with the IME traces. This record copies the figures from the session's report, not from the files.

**NOT RUN.** The manual Korean IME recordings (plan section 9 recorder cases, both Microsoft IME versions, in Chrome and Edge) need the user at the main PC. They are still open, and `docs/evidence/m6-s0/traces/` is empty.

- After the first pass, laying out one node (about 61 clusters on average) takes about 0.4 ms, about 6.5 µs per cluster, in both browsers. Pass 0 is about 18 % slower; per the README, it includes the first use of each font after the warm-up.

## (b) DPR hypothesis: holds under emulation in both browsers

- DPR 1.25, 1.5 and 2 were each compared with DPR 1. For all 1,000 nodes, `lineBreaksIdentical` and `positionsIdentical` are true.
- `maxDeltaCssPx` is 0 for every field (cluster x, y, w and h, node width and height). No value is above 0, and there are no mismatches.
- **The container failure does not reproduce on hardware.** An earlier container run (headless Chromium, SwiftShader; a hint, not evidence) failed this check: y moved by up to 7 px on 305 of 1,000 nodes. On the main PC's hardware GPU, with Windows and DirectWrite, the hypothesis holds under `deviceScaleFactor` emulation.
- **Scope.** Only `deviceScaleFactor` emulation was run, on the main PC only. Browser zoom and moving the window to another monitor (the README's manual checks, with the page's download button) were not run. This record does not settle M6-Q3 (page units or a reference scale); the M6a contract does. Until the manual checks or the M6a headed DPR spec (plan section 9) have run, the plan's rule that a `devicePixelRatio` change bumps the layout `generation` (section 4.1, M6-F4) stays.

- `totalWithin1_64` is true on 21 of 24 rows. The three false rows are the document-only alias rows, which test the worker on purpose: family `M6S0 Document Alias` with `Vector Studio` at 12, 16 and 24 px. There the worker width is larger than the DOM width (for example 73.12 against 71.39 px). With those rows left out, 21 of 21 are true.
- **The worker does not see `document.fonts` faces.** `aliasProbe` gives 156 in the worker and 156 for `monospaceReference`, so the worker fell back to monospace. `worker.selfFonts.size` is 0, `documentFontsSize` is 1, and `canvasLangSupported` is true. System fonts are seen: the worker matches the DOM within 1/64 px on all 21 non-alias rows. Faces registered only in `document.fonts` are not. This was measured as advances (`measureText`), not as rasterized pixels. Under M6-F2, rasterization therefore stays on the main thread, unless R-T registers the same faces in the worker's `self.fonts`.
- The largest per-cluster differences are 2.6445 px (DOM against main-thread canvas) and 2.9844 px (DOM against worker). They come from kerning pairs and the alias rows. Per the README, per-cluster widths of a kerned pair differ by design, so whole-run widths are the measure.

## (d) Ink boxes: identical in both browsers

The tolerance M6-G2 proposes is an offset of at most 0.5 CSS px and a size difference of at most 1 CSS px. `offset` and `sizeDiff` are on integer pixel bounds; `subOffset` and `subSizeDiff` are on the subpixel (coverage-weighted) measures, which the README names as the figures to set the M6c tolerance from.

Maxima by mode and DPR:

| Mode | DPR | Offset / size diff | Sub offset / sub size diff | Centroid | `layoutDelta` | `allShownVsPlainPx` |
| --- | ---: | --- | --- | ---: | ---: | ---: |
| spans | 1 | 3 / 4 | 1.0 / 0.7451 | 1.1611 | 0.0781 | 0 |
| spans | 2 | 1 / 1 | 1.0 / 0.3706 | 1.0 | 0.0781 | 0 |
| highlight | 1 | 3 / 4 | 1.0 / 2.2196 | not reported | not reported | 63 |
| highlight | 2 | 1 / 2.5 | 1.0 / 2.5235 | not reported | not reported | 190 |

`blank` is 0 on every row. The `spans` rows are the measurement; the `highlight` rows are a method check (Chrome clips highlight painting to the range box). Per the README, integer boxes at DPR 1 move in whole pixels and cannot decide a 0.5 px tolerance; the subpixel columns are the ones to read.

**What this bounds.** The canvas side draws with `fillText` over opaque white at the exact fractional DOM origin, so it may use LCD (ClearType-style) antialiasing and is not quantized. The planned `r8` atlas rasterizes alpha on a transparent surface, which gives grayscale antialiasing, and places glyphs at quantized subpixel phases. So these figures bound canvas `fillText` against DOM painting, not the atlas route against DOM.

Maxima by fixture, `spans` mode:

| Fixture | Offset / size diff | Sub offset / sub size diff |
| --- | --- | --- |
| `latin-kerning` | 1 / 1 | 0.3765 / 0.7412 |
| `hangul` | 1 / 2 | 0.3725 / 0.7176 |
| `hangul-in-latin` | 1 / 2 | 0.3765 / 0.7451 |
| `han-in-latin` | 1 / 2 | 0.3725 / 0.7451 |
| `mixed-sizes` | 1 / 2 | 1.0 / 0.7176 |
| `small-12` | 1 / 1 | 0.3725 / 0.6235 |
| `small-9` | 3 / 4 | 0.3725 / 0.5961 |

- `hangul-in-latin` and `han-in-latin` fall within the `hangul` fixture's range on both the integer and the subpixel bounds, so decision rule 3 holds.
- **The proposed M6-G2 tolerance is exceeded.** On integer bounds, `small-9` reaches an offset of 3 and a size difference of 4 (against 0.5 and 1), and `hangul`, `hangul-in-latin`, `han-in-latin` and `mixed-sizes` reach a size difference of 2. On subpixel bounds, `mixed-sizes` has a sub offset of 1.0, against 0.5; every other fixture stays within 0.5 and 1. The `mixed-sizes` offset is exactly 1.0 at both DPRs (centroid maxima 1.1611 and 1.0); its cause is not diagnosed and may be positional, for example baseline placement in a mixed-size line, rather than rasterization. `small-9` is the 9 px fixture the minimum-font-size probe exists for; the reports' `page.minimumFontSize` and `clampSuspected` were not checked as a possible cause of its 3/4. The by-fixture table does not say at which DPR each maximum occurs; the raw reports do. The M6c contract owes the tolerance decision (M6-G2, M6-Q20), set from these subpixel figures and from the committed test font, which this run did not use.
