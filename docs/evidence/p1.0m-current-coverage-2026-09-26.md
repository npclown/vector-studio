For the full-visible S2 population, slot and order capacities are 16,384. The five persistent typed backings total `16384 * (32 + 48 + 48 + 4) + 32 = 2,162,720` bytes. This excludes every object/transient/native category above and is not the combined peak. Cull workloads may have smaller order capacity, so this is not a universal formula for every scenario's current allocation.

The already committed [Chrome S2 functional record](p1.6a/20260926-functional/chrome-p1-pan-zoom-10k-v1.json) exposes a descriptor peak of `18,939,948 = 4,194,348 buffer + 14,745,600 texture` bytes. Its [Edge counterpart](p1.6a/20260926-functional/edge-p1-pan-zoom-10k-v1.json) records the same descriptor values. These are historical functional observations, not a new A09 run. Adding the typed backing total does not produce a complete CPU/GPU bound and cannot pass or fail the 256,000,000-byte gate.

Primary verified the worker's overlap claims against actual copy/publication, slice, retirement and accounting code. `ResourceAccounting` computes an event peak for the tracked descriptors; non-buffer/texture categories contribute zero bytes by contract, not because their physical cost is zero. The worker's list of unobserved browser/driver allocations is a coverage question, not an automatic expansion of engine ownership.

## Strict-method requirements and present limit

An accepted method still needs all of: a complete required-category ownership inventory; a continuous peak or demonstrably sufficient bound including JS object overhead and transient copies; shared-storage attribution; native GPU capacity/destruction coverage; and reproducible phase/overlap evidence. Isolate samples and typed/native descriptor ledgers alone satisfy only subsets.

The conditional `CPU(t) <= P + S`, `GPU(t) <= G`, hence `peak(CPU+GPU) <= P + S + G` argument from the earlier assessment remains valid only if coverage is proven. An upper bound above the ceiling is inconclusive. Microsoft's [EX2 counter documentation](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2), rechecked on 2026-09-26, exposes lifetime private-commit peak but current shared commit; it does not supply the missing continuous shared bound. No counter experiment was performed.

The smallest remaining useful strict-method work is version-matched runtime/allocation coverage research and a prospectively specified observer. Additional static create/track/release tests could strengthen the explicit GPU subset but cannot close A09. No already approved local implementation task was identified that closes the missing whole criterion.
