## 1. Dispatches per load

Every run shows the same sequence. Of the five bumps in a record, the first two (generations 2 and 3) are the page's own text font at startup, before the renderer is ready (`path: none`). The load's three bumps follow:

| Source        | Generation | Relayout path | Layout calls | Equal to previous | Nodes updated |
| ------------- | ---------- | ------------- | ------------ | ----------------- | ------------- |
| `add`         | 4          | whole page    | 207          | 207               | 212           |
| `settle`      | 5          | whole page    | 207          | 207               | 212           |
| `loadingdone` | 6          | whole page    | 207          | 207               | 212           |

- **Three dispatches, each a full relayout**, in all six runs. The bench's `bumps` reads 3 and generation 3 to 6, except `r3/busy`: its measure ended 0.2 ms before `loadingdone` dispatched (3 ms after the settle bump), so `bumps` reads 2 there although the third dispatch ran (V21-A05's window point).
- **Order.** The settle dispatch comes before `loadingdone` in all six runs. The `loadingdone` dispatch starts 285 to 381 ms after it, as soon as it ends: the event waited behind it. That is this browser's order only; the contract's L1 does not depend on it.
- **No layout changes.** All 207 new layouts equal the previous generation's, in every dispatch. Section 2's last point holds: the bench's face is the fallback's file.
- **Every text node is still sent.** Each dispatch updates 212 scene nodes while no layout changed, because the scene's text carries the layout `generation` (`packages/editor-core/src/projector.ts`, `textContent`, M6c-P1).
- **207, not 212, layout calls.** The relayout walks 200 text units (memo entries). 207 requests reach the port; the other requests hit the cache within the same generation. The contract's "212 layouts per dispatch" (section 2) counts text units plus instance texts, not port calls. V21-A02 compares U2's count with this measured 207.

## 2. Where a dispatch's time goes

Per dispatch, in ms, over the 18 load dispatches (6 runs × 3):

| Part                                 | Range      | Share of the dispatch |
| ------------------------------------ | ---------- | --------------------- |
| Whole dispatch                       | 264 to 427 | —                     |
| Port `layout` calls (207)            | 222 to 372 | 81 to 87 %            |
| Projection walk, without the layouts | 28 to 44   | 8 to 12 %             |
| Change-set diff                      | 0.9 to 8.2 | under 3 %             |
| Renderer `applyChanges`              | 7.7 to 17  | 2 to 5 %              |
| Cache drop and `textLayout` event    | under 1    | —                     |

- **Measurement is the larger share.** Section 2's hypothesis holds: almost all of a dispatch is the port measuring text again. L2 removes the layouts of text that does not name the changed family.
- **V21-Q2 (a) applies: L3 is not taken.** The walk and diff without the layouts are at most about 50 ms of a dispatch, against at least 222 ms of layouts. V21-U2 therefore implements L1 and L2 only. If U2's counters show the walk as the larger share after L2, Q2 is asked again.
- These times are SwiftShader's. The M9-U2 and V20-U3 records on the main PC show 170 to 250 ms per task; the split's shape, not its size, is what this record gives.

## 3. Pointer moves during a load

- In the busy runs, only the `add` dispatch fell inside the drag. It held the next move by its whole length (`gapMs` 297, 303 and 321 ms).
- The settle dispatch came 3.8 to 4.2 s after the call, after the drag had ended, against 0.6 to 0.7 s idle. The page's own move loop kept the main thread busy: each move took 10.5 to 11.1 ms (median) against an 8 ms cadence, so the moves fell behind by about 1.1 to 1.3 s (median delay).
- So this headless path cannot say how the settle and `loadingdone` dispatches overlap moves on the reference PC. The contract's question "whether any key latency overlaps a relayout" stays with V21-U3, whose records carry the latency samples and the long tasks flagged `fontLoad`.

## 4. What this means for V21-U2

- L1 (one deferred dispatch per registration) removes two of the three dispatches.
- L2 (family-scoped invalidation) shrinks the remaining dispatch's layouts from 207 calls to the 50 text nodes that name `M9 Font Load`. The 12 instance texts name the test family, not the changed one, so they keep their results (V21-A02).
- With all layouts equal, a family-scoped relayout should also send far fewer than 212 nodes. Whether unchanged layouts still carry a new `generation` into the scene is the E28 amendment's question (contract section 4.3); U2's counters record the nodes sent.
