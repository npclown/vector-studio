## Known limits and disclosed findings

- **Zero-delta provenance amendment** (M3-U1 note 2): section 3.1 value provenance was amended during U1 so that a coordinate whose node-local `δ` component is exactly zero is copied, not computed. A move by `(0, 0)` is therefore a no-op, and a drag that ends at its press point records no step when the issued delta, snap offset included, is exactly `(0, 0)` ("F2: a drag that ends at its press point records no step and raises no document event"). Without it about 12% of coordinates drift by one ulp through `(u·W + 0)/W`.
- **A `lerp` between equal stored values is computed** (M3-U3 note 2): section 3.1 lists a `lerp` as computed without exception, so an inserted anchor between two equal stored coordinates can differ from them by one ulp in the box-unchanged case; this is the one exception to the bit-for-bit statements in the A02 and A03 rows and the bullet above.
- **Implicit form merge** (contract section 8): moving the last anchor of an implicit subpath exactly onto anchor 0 (snapping can do it) makes the subpath read back in the explicit form with one anchor fewer; retention clears the anchor selection ("clears it when the structure changes (the implicit-form merge, section 8) and back").
- **Symmetry without a stored mode** (contract section 8, M3-Q1 (a)): an independent anchor whose handles happen to be exactly symmetric passes the section 2 test and acts as mirrored, so a later handle drag moves its opposite handle unless Alt is held. An anchor inserted at `t ≠ 0.5` is independent until an Alt-drag re-pulls its handles.
- **Exact removal into the explicit form** (M3-U3 note 6): an exact removal can leave an implicit subpath whose new last anchor equals anchor 0 bit for bit; M3-P2 writes it as given and it reads back in the explicit form with one anchor fewer (removing anchor 4 of `move (0,0) line (1,0) line (1,1) line (0,0) line (0,1) close` reads back as three anchors, not four), and retention then clears the anchor selection. Tested in "a removal that lands the new last anchor on anchor 0 reads back in the explicit form". An insertion at `t` near 1 on an implicit closing segment could in principle round onto anchor 0 the same way; this belongs to the section 8 rounding class, was not seen in probes and has no test. The related box-changed rounding of a last anchor onto anchor 0 after an unrelated edit (section 8) is likewise untested.
- **An Alt-drag that returns to its start still records a step** (M3-U2 note 11): pulling handles with `to: q` turns the anchor's lines into cubics, so the result differs from the stored node even when the pointer ends at its press point (section 5 as written).
- **An opened one-anchor loop becomes a lone `move`** (M3-U3 note 1): opening removes its only segment, read literally from section 3.4; keeping a curve would invent an anchor ("a one-anchor loop opens to its anchor; move-close loses close only").
- **Kernel rejections stay P3 disclosed defects** (contract section 8): edited shapes reach fill and stroke paths that P3 disclosed as defects (cracks, the A04 class, the E14 fill `work-limit`); the projector excludes a rejected node and reports `editor.scene-rejected`. M3 does not work around them, and the headed fixture uses shapes the kernel accepts. Contract section 12 records no reproducible case, and the headed run raised no `editor.scene-rejected` diagnostic. P3 exited on 2026-10-27 with disclosed defects ([X1 index](../plans/d9-rendering-track.md#p3-exit-evidence-index-x1)); precision of renderer output stays UNVERIFIED, and M3 changes no renderer code.
- **Headed evidence is from the main PC only** (Windows, Chrome and Edge 156). Other headed runs are NOT RUN (M3-A12 method). The spec turns snapping off so drags land on the pointer (snapping is A10's, unit-tested only), and its insertion checks allow 0.5 px (cubic) and √2 px (line) for the pointer (M3-U4 note 3). Pointer and key events are sent by Playwright. The headless `chromium-smoke` project of `playwright.m3-next-host.config.ts` (under `M3_NEXT_HOST_CHROMIUM`) is a spec check, not evidence.
- **Host caveats** (M3-U2 notes 9 and 10): a host command that ends edit mode during an edit-mode drag does not cancel the drag (as in M2); `pathOverlay` is computed on each query, so a host must not pass it straight to `useSyncExternalStore` (next-host memoizes it).
- **The toggle-closed button repeats the action in the host** (M3-U4 note 2): no command dispatches an action, so the next-host button runs the pure helper `toggleClosedCommand`, checked against the bound `togglePathClosed` action in "M3-U4 toggle-closed button".
- **No performance claim.** By design a path edit re-projects only the edited node (contract section 1), but this is not measured; M3 measures nothing; the M1-A13 isolation cost stays open as [E26](../plans/d9-rendering-track.md#items) (R-P, Backlog, needed by M9).
- **Deferred scope** (contract section 1, out of scope): the `aligned` symmetry mode (M3-Q2); editing `line`, `rectangle`, `ellipse` and `custom` nodes as paths and a flatten-to-path command (M3-Q7); continuing a path from an endpoint, joining endpoints and splitting an open subpath (M3-Q5); snapping handles or to the path's own anchors (M3-Q6); Shift constraints on anchor and handle drags; curve fitting on removal (M3-Q3); property-panel path controls (M8).
- The M3 exit does not establish MVP completion; M4 to M9 remain.
