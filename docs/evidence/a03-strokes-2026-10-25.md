## 3. Corpus stroke rejections

E11 section 7.2 admits a rejected stroke row only in the E4 class, the stroke `work-limit` class (backlog E15) or a transport cap at limit + 1, and the port outcome decides only the second and third (the port reports a stroke source cap at limit + 1 as `work-limit`, SC17). So:

- the A01 sweep now writes `strokeRejections` (id, outcome, label) and `strokeClassCounts` per stratum and named or generated row, labelling `work-limit` as `stroke-work-limit` and keeping every other code (`tests/geometry/p3-exit-sweep/stroke-class.ts`);
- `pnpm a03:stroke-diag <corpus.json>` rebuilds every other failed stroke request from the frozen corpus, runs the native stroke dump (`emit_stroke_dump`, which reports the kernel's unmapped error) and assigns the class.

**Readings confirmed by the E11 thread on 2026-10-25** (dated E11 section 7.2 note in #251):

1. The E4 class is decided on the native outcome: stroke `unsupported-geometry` with `Rounded(TopologyAmbiguous)`, the error the kernel pins on ST-U3f (`st_u3f_chev_1_40625_is_a_known_topology_ambiguous_defect`). Generated rows with that error are in the class.
2. A named row that returns its B2 section 11.2 literal status is a pass, not a rejection: ST-F24 at `L = 2^30` is `numeric-range` (ST-G3), and ST-F7, ST-F8 butt and ST-F9 are `empty`.
3. The stroke `work-limit` class's backlog item is E15 (E2 is done).
