The first `pnpm test:geometry` run passed 119 native tests and failed two new raw-input test groups before reaching WASM/TS checks. Their intended SourceLimit/UnsupportedSource paths instead returned sizing PATH_NUMERIC_RANGE with two logical cubics and one sizing visit. The exact C05 24/104 input and 72-command/64-leaf/2016-pair boundary had already passed within the same run.

Primary, implementer and independent reviewer traced both failures to the new unit fixture's length-one `append_linear` segments. For the translated 1->2 segment, packed control bits `3ff5555555555555`/`3ffaaaaaaaaaaaaa` become relative `3fd5555555555554`/`3fe5555555555554`; the derivative's computed quadratic coefficient is 2^-52 rather than zero. Existing P2 `Cubic::bounds -> extrema` conservatively rejects its uncertain near-degenerate root bound before flatten visits. Returning 1->0 has the same translated-third issue. Initial source review had incorrectly assumed these represented Float64 controls were exactly parameter-linear.

The correction preserves the tests' decoder/cap purpose and every expected status: use length-three integer segments with exactly represented trisection controls, giving relative [0,1,2,3] or [0,-1,-2,-3] and exactly zero higher derivative coefficients. The 17-cubic source remains 18 verbs/104 scalars; returning-open becomes 0->3->0. Matching source-cap/mixed-precedence raw controls use the same exact construction. Neither runtime/P2 logic nor C05, the original 94-row corpus, error budgets or limits change. Both reviewers approved this construction correction before rerun; it is not a claim that P2 now accepts the earlier near-linear inputs. That conservative P2 numeric limitation remains relevant to later general-corpus readiness.
