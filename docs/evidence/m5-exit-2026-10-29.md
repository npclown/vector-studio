## Known limits and disclosed findings

- **Silent overwrite across tabs** (M5-Q7 (a), contract section 6): two tabs of one origin share the one entry and are not coordinated. Each tab restores what was stored when it opened, and the last completed write wins, so one tab's edits can replace another's without notice. An entry is never torn (one atomic `put` per write). Coordination (Web Locks or a write generation, M5-Q7 (b) and (c)) is backlog.
- **Restore race** (contract section 5.3): edits made before the restore finishes are replaced by a successful restore; the status shows `restoring` until then. With no record, the attach schedules one write if the revision has moved since the page loaded, so those edits are saved ("replaces edits made during the read with the stored document; with no record it saves them").
- **Autosave off after a failed restore** (contract section 5.2, M5-Q11 (a)): after a failed IndexedDB restore the entry is kept and autosave stays off for the page's lifetime, so later edits are lost on reload unless the user saves a file or uses "Discard stored document". An entry written by a newer build (`envelope.unsupported-version` or `document.unsupported-version`) is kept for that build.
- **Discard rules** (M5-U4 notes 4 and 5): Discard is offered only after a failed read, parse or load, or a failed discard; not for `persistence.unavailable` (no store is open) or a failed write. A failed discard offers Discard again and attaches nothing. After a successful discard autosave attaches with the empty-store rule, so edits made while the entry was corrupt are saved.
- **Lost last edits** (contract section 9): a debounced write pending when the tab closes may not complete. `flush` on `visibilitychange` to `hidden` is best effort and `maxWaitMs` (2,000 ms) bounds the window under continuous edits; this is not a durability guarantee.
- **`written: false` counts as saved** (M5-U4 note 3): the status `saved <n>` counts successful write results, including writes the store skipped as unchanged, since the entry then equals the document.
- **Connection closed by the browser** (M5-U3 note 7): a connection the browser closes on its own (`onclose`) is not handled, so later calls give `persistence.read-failed` or `persistence.write-failed` rather than `persistence.unavailable`.
- **A version 1 database without the `envelopes` store** (M5-U3 note 7): every call fails the same way (`read-failed` or `write-failed`); the store does not repair it. The restore case "read fails (no envelopes store at version 1): persistence.read-failed" tests it.
- **Viewport, hover and the rest of the session are not restored** (contract section 5.1, requirements): after a reload the camera is the page's start `{ position: { x: 0, y: 0 }, zoom: 1 }`, selection and history are empty, and scope, path edit mode, snapping, hover and panels are not restored; after "Open file" the camera keeps its current value (M5-U5 note 3). Undo history does not survive a reload.
- **The page's React lifecycle is covered only headed** (M5-U4 note 9): the visibility flush, the test hook and the fixture precedence in `apps/next-host/app/page.tsx` have no unit coverage; they rest on the M5-A10 spec. The flush test cannot tell a flush write from a 500 ms trailing write (M5-U5 note 6); flush semantics are unit-tested in M5-A05.
- **Fake fidelity** (contract section 9): `fake-indexeddb` may differ from Chrome and Edge in event timing and errors; M5-A10 runs the real IndexedDB, but quota (`QuotaExceededError`), eviction and `navigator.storage.persist()` are not exercised.
- **Headed evidence is from the main PC only** (Windows, Chrome and Edge 156). Other headed runs are NOT RUN (M5-A10 method). The spec adds page 2 by the `addPage` command through the test hook, since the page has no add-page control (M5-U5 note 2), and writes corrupt entries from `/?test=1` before a full load of `/?test=1&persist=1` (M5-U5 note 4). Pointer and key events are sent by Playwright. The headless `chromium-smoke` project of `playwright.m5-next-host.config.ts` (under `M5_NEXT_HOST_CHROMIUM`) is a spec check, not evidence.
- **Host-local and lenient readings** (M5-U1 note 2, M5-U4 notes 6 and 8): an `envelopeVersion` written as `1.0` is the JSON number 1 and is accepted; any throw during the restore is reported as `persistence.read-failed` at stage `restore`; a file read error in Open file shows the host-local status `file.read-failed`, which is not a public code.
- **No performance claim.** Every autosave serializes the whole document (contract section 1); M5 measures nothing (M9).
- **Envelope churn** (contract section 9): a later requirement that restores the viewport bumps `envelopeVersion` and needs a migration in `parseEnvelope`.
- **Deferred scope** (contract section 1, out of scope): restoring selection, hover, zoom, viewport, tool, scope, path edit mode, panels or history; undo history across reloads; multi-tab coordination beyond M5-Q7 (a); several documents in one store (a document list or picker); `navigator.storage.persist()` and eviction handling; server or cloud persistence, and import and export formats other than the envelope; collaboration; a schema change or migration.
- The M5 exit does not establish MVP completion; M4 and M6 to M9 remain.
